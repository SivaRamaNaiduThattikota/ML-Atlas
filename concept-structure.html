Code, mathematics, and visuals

Use the representation that exposes the mechanism.

Every lesson explicitly considers all three. Their depth changes with the concept; none is silently skipped.

VISUAL

See the flow

Architecture skeletons, flowcharts, decision boundaries, geometric diagrams, tables, or interactive animations show where information moves and decisions occur.

MATH

Explain the quantity

Equations include notation, derivation, assumptions, interpretation, and a worked calculation whenever the concept has meaningful mathematics.

CODE

Expose and apply it

From-scratch code (usually NumPy) reveals the essential mechanism; current-library code shows realistic implementation with scikit-learn, XGBoost, Optuna, SHAP, or MLflow.

VERIFY

Run, test, debug

Code includes inputs, expected outputs, inspection points, edge cases, tests, and a debugging task. If code would add no learning value, the lesson states why it is not applicable.

Visual explanation standard

A diagram must teach—not decorate.

Every concept receives visual support wherever spatial relationships, sequence, branching, comparison, state change, or system placement are easier to understand visually than through prose alone.

REQUIRED VISUAL CONTRACTOpen the diagram design and explanation checklist+
01

Choose the relationship

Use a flow for sequence, branches for decisions, lanes for parallel stages, a hub for one reusable component with many uses, and a table for exact comparisons.

02

Highlight the lesson’s concept

Show the complete relevant context, but visually emphasize only the component or transition currently being taught.

03

Explain how to read it

Every substantial diagram includes a caption plus a short reading key explaining its input, transformation or decision, output, and practical consequence.

04

Keep notation consistent

Node names, arrow direction, colors, equations, and architecture boundaries must agree with earlier lessons and the continuing CFPB project.

05

Make it accessible

Provide a descriptive label, visible text for meaning, keyboard access when horizontally scrollable, and never rely on color alone.

06

Test every viewport

Reflow simple diagrams vertically. Contain dense diagrams in an explicit horizontal scroller on mobile so the page itself never overflows or clips.

Quality gate

Lesson quality loop

Every lesson must pass roadmap, scope, duplication, progression, project-continuity, and responsive-interface checks before it is presented.

REQUIRED FOR EVERY LESSONOpen the complete inspect → verify → revise → re-test checklist+
01

Before writing

  • Verify the exact concept against the canonical roadmap.
  • Confirm the previous, current, and next concepts.
  • Define what this lesson owns and what belongs later.
  • Allow later material only as a clearly labelled preview.
  • Check the required prerequisites.
02

While writing

  • Build intuition before technical detail and connect new knowledge to the previous lesson.
  • Reuse an example only when it adds a genuinely new perspective.
  • Keep terminology, notation, examples, and architecture diagrams consistent.
  • Connect to CFPB's relief-risk and narrative-triage models only where relevant.
  • Separate classification, regression, clustering, and deterministic evaluation correctly.
03

Content audit

  • Compare beginner and advanced sections with all earlier lessons.
  • Detect repeated sentences, examples, equations, code, diagrams, exercises, and interview questions.
  • Keep useful reinforcement; remove repetition that adds no new conceptual layer.
  • Check that no future concept is accidentally taught in full.
  • Confirm the title is answered completely and both depth levels agree.
04

Learning-progression audit

  • Confirm prerequisites are sufficient and difficulty rises gradually.
  • Explain notation before mathematics; place code after the mechanism.
  • Make exercises test this lesson rather than a later topic.
  • Keep the concept card and interview questions inside the taught scope.
  • Match the next-lesson section exactly to the roadmap.
05

Project-continuity audit

  • Record the new capability this concept adds to CFPB's models.
  • Extend the existing pipeline instead of re-teaching earlier responsibilities.
  • Preserve the boundaries between EDA, feature engineering, modeling, evaluation, and deployment.
  • Verify that project mapping is relevant rather than forced.
06

Website and interaction audit

  • Inspect desktop, tablet, and mobile layouts in light and dark modes.
  • Use internal horizontal scrolling only where it is genuinely needed.
  • Detect clipping, unintended page overflow, or unreadable type.
  • Test beginner and advanced navigation, collapsed defaults, links, anchors, arrows, labs, and controls.
  • Check keyboard access, focus visibility, touch targets, and readable font sizes.
07

Final learner-journey pass

Inspect the complete path as a learner would:

Roadmap→Previous lesson→Current lesson→Exercise→Completion→Next lesson

If any step feels disconnected, duplicated, premature, misleading, or visually broken, revise it and run the checks again before presenting the lesson.
