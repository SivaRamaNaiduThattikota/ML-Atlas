01 · CONCEPT FIRST

The eight-item checklist, stated once, in order

(1) Is there a real target/label and is the task genuinely learnable? (2) Have I correctly identified supervised, unsupervised, or reinforcement learning? (3) Am I optimizing for generalization, not training fit alone? (4) Have I checked for overfitting or underfitting's error signature? (5) Do I understand the bias-variance tradeoff driving that signature? (6) Is my train/validation/test split honest and never peeked? (7) Have I named and scored a baseline before looking at my candidate? (8) Have I audited for all four leakage types?

First memory: a checklist, not a lesson — every item already has a full lesson behind it.
02 · WHY IT EXISTS

Under deadline pressure, order gets skipped first

Each of Concepts 01–08 is easy to agree with in isolation and easy to silently skip under real deadline pressure — nobody sets out to skip a train/test split, but a rushed script that fits a scaler before splitting does exactly that, unnoticed. A checklist run before writing the first line of modeling code is the only defense that doesn't rely on remembering all eight ideas perfectly under pressure.

NO CHECKLIST

Each concept has to be independently remembered and applied — easy to drop one under time pressure.

ONE ORDERED PASS

All eight items get checked in the same order, every time, before modeling starts.

03 · CONCRETE EXAMPLE

A first-draft CFPB Model 1 plan, audited

A colleague proposes: "We'll predict relief risk using XGBoost. I'll shuffle the complaints and split 80/10/10, then fit a scaler on the full dataset first for consistency, then compare our tuned model's accuracy against 95% and call it done." Running this through the checklist surfaces at least three real problems before a single line of modeling code runs: no realistic baseline was named (item 7), the scaler is fit before splitting (item 8, preprocessing leakage), and a shuffled split ignores the weekly-pull time structure (item 8, temporal leakage).

SOUNDS REASONABLE

Read as one paragraph, the plan sounds like ordinary, competent project setup.

CHECKLIST-AUDITED

The same plan, run item by item, surfaces three concrete failures before any code is written.

07 · COMMON MISTAKES

What beginners often misunderstand

"This checklist teaches something new."

It teaches nothing new — every item is a citation back to Concepts 01–08, not a new technique.

"Only complex projects need this."

Section 03's failure (unfit scaler, shuffled split) is a small, easy-to-write script — checklist failures aren't reserved for complex pipelines.

"Running the checklist once at the very start is enough forever."

A project that changes its data source, features, or timeline should re-run the checklist, not just once at kickoff.

04
INTUITION

A pilot's pre-flight checklist

A pilot doesn't relearn aerodynamics before every flight — they run a fixed pre-flight checklist, because the danger isn't ignorance, it's skipping a known step under time pressure. This checklist is the identical idea applied to starting an ML project: every item is already known; the checklist's only job is making sure none of them get silently skipped.

Analogy boundaryA pre-flight checklist has a hard external enforcement mechanism (a control tower, a co-pilot). This checklist's enforcement is entirely self-imposed — the analogy conveys "fixed order, run every time," not any external accountability.

08
ARCHITECTURE

Where this sits in the full ML lifecycle

Checklist (this concept)↓Data↓Features↓Model↓Prediction↓Evaluation↓Deployment↓Monitoring

This checklist runs once, before "Data" begins — the earliest possible point in the lifecycle. Every later stage's tools (cross-validation, hyperparameter search, SHAP, drift monitoring) assume items 1–8 were already satisfied; none of them are designed to catch a checklist failure after the fact.

09
MATHEMATICS

No new formalism — a pointer back to eight already-derived ones

This concept deliberately introduces no new equation. Item 3's generalization gap (R(f) − R̂ₙ(f)), item 5's bias-variance decomposition (Bias² + Variance + σ²), item 6's split discipline (D_train, D_val, D_test disjoint), item 7's lift (Δ = L(b, D_test) − L(f_θ*, D_test)), and item 8's point-in-time condition (θ = fit(D_train), never D_train ∪ D_test) are each fully derived in their own concept and simply cited here by name.

BOUNDARY CASE

A checklist item that's "not yet checkable"

Items 3–5 can't be evaluated before any model exists — deferred, not failed, at the framing stage.

MISTAKE TO AVOID

Treating a deferred item as a pass

"Not yet checkable" must be revisited once a model exists, not silently counted as satisfied.

12
CODE

A checklist auditor, from scratch

PYTHON · SCORE A PROJECT DESCRIPTION AGAINST THE EIGHT ITEMS 
def audit_project(plan):
    results = {}
    results['item_1_2_framing'] = plan.get('has_real_label', False) and plan.get('paradigm_correct', False)
    results['item_3_5_generalization'] = 'deferred' if not plan.get('model_fit', False) else plan.get('checked_train_true_gap', False)
    results['item_6_split'] = plan.get('split_is_chronological_or_iid_correct', False) and not plan.get('split_was_shuffled_incorrectly', False)
    results['item_7_baseline'] = plan.get('baseline_named_before_candidate', False)
    results['item_8_leakage'] = not any([
        plan.get('preprocessing_fit_before_split', False),
        plan.get('has_post_outcome_feature', False),
        plan.get('duplicates_uncontrolled', False),
    ])
    return results

first_draft = {
    'has_real_label': True, 'paradigm_correct': True,
    'split_was_shuffled_incorrectly': True,
    'baseline_named_before_candidate': False,
    'preprocessing_fit_before_split': True,
}
print(audit_project(first_draft))
# {'item_1_2_framing': True, 'item_3_5_generalization': 'deferred',
#  'item_6_split': False, 'item_7_baseline': False, 'item_8_leakage': False}
assert audit_project(first_draft)['item_6_split'] == False
assert audit_project(first_draft)['item_8_leakage'] == False
13
ECOSYSTEM

Where this discipline shows up in real tooling

No single library runs this checklist end to end — it is a human judgment pass, not an automated one. Pieces of it are supported: scikit-learn's Pipeline makes item 8's preprocessing discipline mechanical once decided; MLflow's experiment tracking (Module 18) is where a named baseline (item 7) gets logged so it can't be silently dropped later; but the decision that a baseline is needed, and which one, is this checklist's job, not a library's.

16
DIAGNOSIS

Failure modes

CHECKLIST THEATER

Running it without acting on failures

Naming a checklist failure and proceeding anyway defeats the entire point.

ONE-TIME RUN

Never re-auditing after a project changes

A new data source or feature should trigger a fresh pass, not just one at kickoff.

DEFERRED-AS-PASSED

Treating items 3–5 as satisfied before a model exists

They can only be marked pass once a model has actually been fit and checked.

18
REALITY

Production implications

  • Attach the eight-item audit to a project's kickoff document, not just to memory.
  • Re-run it whenever the data source, feature set, or deployment cadence changes.
  • Treat "deferred, not yet checkable" honestly for items 3–5 rather than marking them passed early.
19
RECALL

Knowledge check

Which checklist item would have caught Section 03's shuffled-split mistake?
Item 6 — the train/validation/test split must be honest and respect any real time structure.
Why can't items 3–5 be marked "pass" before any model exists?
They concern generalization and bias-variance behavior, which can only be observed once a model has actually been fit and checked against held-out data.

FEEDBACK

Solution and teach-back

Open one defensible reasoning pattern
Items 1, 2, 6, and 7 pass. Item 8 fails: "support tickets in the 30 days before cancellation" cannot be computed at the moment a still-active customer needs a churn-risk prediction, since it depends on already knowing the cancellation date — target-via-proxy leakage, identical in structure to Concept 08's post-resolution response-category example.

Teach-back: explain why this exercise's leak is easy to miss even though the split and baseline are both handled correctly.
