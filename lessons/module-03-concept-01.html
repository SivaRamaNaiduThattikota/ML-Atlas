01 · CONCEPT FIRST

EDA is a habit of asking, not a list of five plots

Exploratory data analysis (EDA) is the practice of looking at a dataset before trusting anything built on it — checking what it actually contains, where it might be wrong, and what it might be hiding. A checklist treats that as a fixed routine: run .describe(), count the nulls, draw a correlation heatmap, glance at a couple of histograms, done — the identical four or five outputs regardless of what the dataset actually is. A discipline treats it as a loop: look at something specific, ask whether it could hurt a model or mislead a decision, and if the answer might be yes, dig into exactly that finding before moving anywhere else.

First memory: a checklist runs to completion no matter what it finds. A discipline stops and digs the moment it finds something worth digging into.

03 · CONCRETE EXAMPLE

Two analysts, the same raw CFPB pull

Both open the same raw complaint export — tens of thousands of rows, well over a dozen columns, most of them categorical or free text. Analyst A runs four checks off a template: row count, percent missing per column, a correlation heatmap, a couple of histograms. All four come back looking clean. Analyst A calls EDA done in ten minutes. Analyst B starts from one question: what could this specific data structure be hiding that would matter for a relief-risk model? Every answer becomes the next question, and the same four checks Analyst A ran come back with a name attached to something underneath each one.

ANALYST A · CHECKLIST

Four fixed outputs, all reassuring, EDA "complete" — the same four outputs a template would have produced on any dataset at all.

ANALYST B · DISCIPLINE

The same four checks, plus one follow-up question on each — and every follow-up finds something the first pass alone couldn't show.

THE GAP

Neither analyst is lying. Analyst A's numbers are correct. They're just the end of the investigation instead of the start of one.

04 · TECHNICAL MECHANISM

What makes an investigation a loop instead of a list

1 · FIXED SCOPE

A checklist's steps don't depend on the data

The same four or five outputs run whether the dataset is complaint text, sensor readings, or transaction logs — the routine was decided before the data was seen.

2 · SINGLE PASS

A checklist has no follow-up built in

Each step runs once and reports a number. Nothing in the routine itself asks whether that number is actually safe to trust.

3 · SUMMARY, NOT JUDGMENT

A checklist's output is a statistic, not a verdict

"38% missing" and "no strong correlations" are correct descriptions. Neither one says whether that fact is dangerous for this specific model.

4 · DISCIPLINE'S LOOP

Every finding either closes or opens a question

A disciplined pass keeps asking "could this be hiding something" until an honest answer is no — which is why it has no fixed length.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"I ran .describe() and nothing looked wrong, so the data's fine."

.describe() only summarizes numeric columns, and only ever reports central tendency and spread — never shape. Concept 02 shows exactly how two very different distributions can share the identical mean.

"An automated profiling report gives me EDA for free."

A report answers the same generic questions on every dataset it's pointed at. It has no way to know that, for CFPB specifically, a 38%-missing field matters because of when it was added — only a question aimed at this data can catch that.

"We already used a clean, fixed CFPB test set in Modules 01-02, so there's nothing left to investigate."

That 1,000-row set was already curated before this course ever saw it. The raw pull it was built from — with its own missingness patterns, cardinality, and timing artifacts — has never been examined here at all.

"EDA is a box you check once, before modeling starts."

The same disciplined habit — look, ask, dig if it matters — resurfaces every time production data could have quietly changed, which Module 17's drift monitoring picks up later as this same discipline in a different setting.

INTUITION

A building inspector with a clipboard, versus one without one

One inspector walks every room, ticks a fixed set of boxes — smoke detector present, outlet count, ceiling height — and signs off once the sheet is full. Another inspector notices a suspiciously fresh patch of paint on one wall and opens the panel behind it before ticking anything else. Both inspectors visited the identical rooms. Only one of them found the wiring problem, because only one of them let what they noticed change what they did next.

Analogy boundaryThe clipboard captures "fixed scope versus a loop that reacts to findings" — it doesn't capture the actual statistical tools EDA uses. Section 10's worked example is the real mechanism; the inspector is only the shape of the behavior.

PRECISION

Formal definitions

TermDefinitionBoundary
Exploratory data analysis (EDA)Open-ended investigation of a dataset with no hypothesis fixed in advance, aimed at discovering structure, anomalies, and risk before modelingCoined by John Tukey; distinct from confirmatory analysis, which tests one pre-stated hypothesis
Confirmatory (statistical) analysisTesting a specific, pre-registered hypothesis against data, with a formal significance procedureConcept 09 (Module 02) already used this mode — this concept is squarely the exploratory mode instead
Checklist EDA (this lesson's term for the anti-pattern)A fixed, dataset-independent sequence of summary outputs, run once, with no step that reacts to what an earlier step foundNot wrong on its own terms — every number it reports can be accurate — only bounded in what it can surface
Disciplined EDAAn iterative loop: observe → ask whether the observation threatens a downstream decision → if so, investigate that specific finding → repeat until no open question remainsHas no fixed length or fixed set of outputs — its shape depends entirely on the data
06
MECHANISM

Tracing the loop, abstractly

Observe — look at one specific thing: a column, a summary statistic, a slice of rows.
Ask — could this plausibly hurt a model or mislead the business decision built on it?
Branch — if the honest answer is "no, clearly not," move to the next thing. If it's "maybe," dig into exactly that finding.
Update — whatever the dig reveals becomes the next thing to observe.
Stop — only when a full pass produces no new "maybe" — not when a predetermined list of outputs has been printed.

09
MATHEMATICS

No new formula — just checking whether one number was ever enough

This concept introduces no metric and no estimator. The only arithmetic below is the plain mean of a small set of numbers, exactly as taught in any introductory statistics course, used to make one point: a mean by itself cannot distinguish a genuinely typical value from an average of two extremes that never actually occur.

mean(x) = (sum of all values) / (count of values) — the only formula this concept uses, and it is not new
10
EXAMPLE

Two four-row samples, identical mean, opposite shape

SampleDays to respondMeanMinMax
X5, 5, 15, 15(5+5+15+15)/4 = 10.0515
Y10, 10, 10, 10(10+10+10+10)/4 = 10.01010

A checklist step that reports only the mean prints the identical "10.0" for both samples. Sample X is two fast complaints and two slow ones — nobody's complaint actually took 10 days. Sample Y is genuinely, uniformly average. The mean can't tell these apart; only looking at more than the mean can.

12
CODE

A checklist function and a discipline function, on the identical data

PYTHON · NO LIBRARIES 
sample_x = [5, 5, 15, 15]
sample_y = [10, 10, 10, 10]

def checklist_summary(values):
    return {"mean": sum(values) / len(values)}

def disciplined_summary(values):
    mean = sum(values) / len(values)
    spread = max(values) - min(values)
    return {
        "mean": mean,
        "min": min(values),
        "max": max(values),
        "spread": spread,
        "flag": "nothing sits near the mean" if spread > 0 and mean not in values else "typical",
    }

checklist_x, checklist_y = checklist_summary(sample_x), checklist_summary(sample_y)
disc_x, disc_y = disciplined_summary(sample_x), disciplined_summary(sample_y)

assert checklist_x == checklist_y == {"mean": 10.0}          # a checklist can't tell them apart
assert disc_x["flag"] == "nothing sits near the mean"        # X: split at the extremes
assert disc_y["flag"] == "typical"                            # Y: genuinely average

Neither function computes anything exotic — disciplined_summary only asks one more question of the identical numbers. That one extra question is the entire gap Section 10 describes.

13
ECOSYSTEM

Automated profiling tools are a checklist, packaged

Tools such as ydata-profiling generate a full report — missing-value counts, distributions, correlations, cardinality — for every column in a dataset with one function call. That's genuinely useful as a fast first pass, and Concept 02 onward will actually use tools like pandas and matplotlib to do real work. But a profiling report answers the same generic questions on any dataset it's pointed at; it has no way to know that, for CFPB specifically, a missing-value pattern lines up with a 2019 schema change, or that an "unremarkable" correlation coefficient never looked at 16 of the dataset's 19 columns because they aren't numeric. The report is Section 05's checklist EDA, automated — a starting point this module's later concepts build past, not a finish line.

DIAGNOSIS

Failure modes

FIXED-LIST BLINDNESS

Running the same four checks regardless of what the data is

A checklist built for numeric sensor data misses almost everything relevant about a mostly-categorical, mostly-text complaint dataset.

FALSE CONFIDENCE FROM A CLEAN REPORT

Treating "the report has no red flags" as "the data is fine"

Section 10's sample X shows a completely clean-looking mean sitting on top of a real problem.

ONE-TIME MINDSET

Believing EDA happens once, before modeling, and never again

Upstream data changes — a new product line, a schema update — need the identical loop re-run, not just at training time.

"WE ALREADY HAVE A CLEAN TEST SET"

REALITY

Production implications

  • What a disciplined EDA pass finds — not just what a checklist ran — belongs in a dataset's documentation or a model card, so the next person doesn't re-discover the same 2019 schema cutoff from scratch.
  • New data sources, schema changes, or new product categories each restart this exact loop; a one-time EDA pass at project kickoff does not cover data that arrives a year later.
  • Module 17's drift monitoring is this same observe-ask-dig discipline, automated and run continuously against live production data rather than once against a training pull.

PORTABLE MEMORY

Concept card

The rule

  • Checklist EDA: a fixed, single-pass list of outputs, the same regardless of the dataset
  • Disciplined EDA: observe → ask if it matters → dig if it might → repeat until nothing new surfaces
  • The gap: both can report accurate numbers; only one asks whether those numbers are safe to trust

Memorable example

Sample X (5, 5, 15, 15) and Sample Y (10, 10, 10, 10) share the identical mean, 10.0 — a checklist step reports the same number for both; only asking "does anything actually sit near that number" tells them apart.

23
CAREER PRACTICE

Interview questions

How would you explain the difference between EDA and confirmatory statistical analysis to a junior analyst?
EDA is open-ended — no hypothesis is fixed going in, and the goal is to discover structure or risk. Confirmatory analysis tests one pre-stated hypothesis with a formal procedure, the mode Concept 09 (Module 02) already used on candidate A and B's recall gap.
A teammate says "I ran the profiling report, EDA is done." How do you respond?
Ask what the report's findings imply for this specific model and business decision — a report describes the data generically; it can't know which description is dangerous for the problem at hand (Section 13).
Why can two datasets share an identical mean, minimum, and count while being fundamentally different for modeling purposes?
A mean collapses every value into one number regardless of where those values actually sit — Section 10's sample X and sample Y prove the point directly with four numbers each.
System design: how would you make disciplined EDA repeatable across a team, not just a habit for careful individuals?
Document findings (not just outputs) in a data dictionary or model card, and treat any new data source or schema change as a trigger to re-run the same observe-ask-dig loop, mirroring how Module 17 automates the identical discipline for drift monitoring.
