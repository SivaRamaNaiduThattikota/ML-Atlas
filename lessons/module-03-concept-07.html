MODULE 03 · CONCEPT 07

Count the labels
before you trust the accuracy.

Concept 06 asked what a correlation between two fields is allowed to claim. This concept drops relationships entirely and looks at one column on its own: the target. Class imbalance means the label you're trying to predict is skewed -- one outcome far outnumbers the other -- and a model trained on it can look deceptively good by raw accuracy alone. The fix belongs to Module 05. This concept is only the diagnosis: tally the counts, convert to percentages, compute the majority:minority ratio, classify severity against a stated rule of thumb, and check the absolute minority count, because a percentage alone can't say whether you have enough minority rows to do anything useful with. The worked example reuses CFPB Model 1's own real numbers -- 223 relief-granted, 777 not, out of the canonical 1,000-row test set -- and explains, for the first time in this course, exactly why that split produced Module 02 Concept 01's 77.7% majority-class floor.

02 · WHY IT EXISTS

A skewed target lets a model look good while doing nothing useful

A model trained on a skewed target can report a high accuracy while never learning to recognize the rare outcome at all -- Concept 07 of Module 02 already proved this with CFPB's own numbers. EDA's job is to catch that skew before any model gets trained on it, name how severe it is, and flag it for later. Fixing it -- resampling, reweighting, moving a decision threshold, cost-sensitive learning -- is a modeling-stage decision. That toolbox belongs entirely to Module 05. This concept only diagnoses.

03 · CONCRETE EXAMPLE

1,000 rows, two classes, one number two modules already leaned on

CFPB Model 1's real 1,000-row test set, reused exactly from Module 02 Concept 01: 223 rows are relief-granted (the class this model actually needs to catch), and 777 are not. As a fraction of the whole: 223/1,000 = 22.3% minority, 777/1,000 = 77.7% majority. As a ratio: 777/223 ≈ 3.48, reported as roughly 3.5 majority rows for every 1 minority row.

Majority over minority

Not just the percentage

Four things that sound like the same problem and aren't

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"High accuracy means there's no imbalance problem."

Module 02 Concept 01's own majority-class floor hit 77.7% while catching zero real relief cases -- accuracy alone hid the skew completely.

"22.3% minority isn't THAT skewed."

Against real severe cases -- credit-card fraud under 0.1%, a rare-virus diagnosis under 0.01% -- 22.3% is genuinely mild, but it's not nothing, and Section 15's contrast table makes the gap concrete.

"I should resample right now, during EDA."

Premature. Resampling before a train/test split risks leaking test rows into training (Module 01 Concept 08's leakage trap) -- the fix belongs after the split, in Module 05.

"The percentage alone tells the whole story."

It doesn't -- a rare class can look survivable by percentage yet leave almost nothing in a held-out test set once split, as Section 04's own count check shows.

MECHANISM

Tally, percentage, ratio, severity, absolute count, flag

Step 1 — tally raw counts per class from the target column (here, 223 relief-granted, 777 not).
Step 2 — convert each count to a percentage of the total (22.3% and 77.7%).
Step 3 — compute the imbalance ratio, majority over minority (777/223 ≈ 3.48:1).
Step 4 — classify severity against this course's stated bands (22.3% → MILD).
Step 5 — check the absolute minority count against a realistic split (223 × 0.15 ≈ 33 survive a 15% hold-out).
Step 6 — flag the result for Module 05 -- nothing gets resampled, reweighted, or threshold-adjusted here.

09
MATHEMATICS

Why the majority-only floor is exactly 1 − p

Let p be the minority proportion, n_minority / N. The majority proportion is exactly 1 − p, since the two classes cover every row. The imbalance ratio follows directly from the same two counts:

ratio = n_majority / n_minority = (1 − p) / p

A classifier that always predicts the majority label is correct on every majority row and wrong on every minority row -- it never has to learn anything. Its accuracy is therefore exactly the majority row count over the total:

Acc_majority-only = n_majority / N = 1 − p

Plugging in CFPB's real numbers, p = 223/1,000 = 0.223, so Acc_majority-only = 1 − 0.223 = 0.777 = 77.7% -- reproducing Module 02 Concept 01's majority-class floor exactly. That number was never a coincidence; it is the direct arithmetic consequence of the class ratio this concept diagnoses. The same identity applied to the Section 20 transfer exercise's billing-dispute tag (70.0% share) predicts a majority-only accuracy of exactly 70.0% -- Section 21 confirms it.

CODE

Tally, ratio, severity, from scratch

PYTHON · NO LIBRARIES 
from collections import Counter

def diagnose_imbalance(labels):
    counts = Counter(labels)
    n = len(labels)
    if len(counts) < 2:
        return {"error": "fewer than two classes present"}

    majority_label, majority_n = max(counts.items(), key=lambda kv: kv[1])
    minority_label, minority_n = min(counts.items(), key=lambda kv: kv[1])

    if minority_n == 0:
        return {"error": "minority class has zero rows -- ratio undefined"}

    minority_pct = minority_n / n * 100
    majority_pct = majority_n / n * 100
    ratio = majority_n / minority_n

    if minority_pct >= 40:
        severity = "balanced"
    elif minority_pct >= 20:
        severity = "mild"
    elif minority_pct >= 5:
        severity = "moderate"
    else:
        severity = "severe"

    return {
        "majority_n": majority_n, "minority_n": minority_n,
        "majority_pct": round(majority_pct, 1), "minority_pct": round(minority_pct, 1),
        "ratio": round(ratio, 2), "severity": severity,
    }

cfpb_labels = [1] * 223 + [0] * 777
result = diagnose_imbalance(cfpb_labels)
assert result["minority_pct"] == 22.3 and result["majority_pct"] == 77.7
assert result["ratio"] == 3.48
assert result["severity"] == "mild"

# edge case: a class with zero examples must not raise ZeroDivisionError
edge = diagnose_imbalance([1] * 50 + [0] * 0 + [2] * 1)
# with three "classes" and one at zero rows the min() picks the true minority (n=1);
# a genuinely empty class is caught explicitly by the minority_n == 0 guard above

REALITY

Production implications

  • Class balance can drift in production even when it was diagnosed correctly at training time -- Module 17's monitoring stage is where that drift actually gets caught, named here only.
  • Document which ratio and severity were diagnosed, and when, alongside the dataset itself -- CFPB's regulatory context makes this kind of paper trail a real requirement, not a nice-to-have.

19
RECALL

Knowledge check

Why is CFPB's majority-class floor exactly 77.7%, and not some other number?
Because a majority-only classifier is correct on exactly the majority rows and wrong on every minority row, its accuracy is n_majority/N = 1 − p. With p = 0.223, that's exactly 1 − 0.223 = 0.777.
Why can 22.3% minority and 0.99% minority both matter, even though one is "only" mildly imbalanced?
Severity is relative to this course's own stated bands, not a universal cutoff. 22.3% is mild by that rule of thumb; the point of the contrast table is to show how much further real severe cases (sub-1% or sub-0.1% minority) can go, not to claim 22.3% is nothing.
What's the difference between the imbalance ratio and the absolute minority count, and why do you need both?
The ratio is scale-invariant -- it doesn't change if every count is multiplied by the same factor. The absolute count tells you how many actual rows you have to work with, which does change with N, and determines whether a class survives a train/test split at all.

PORTABLE MEMORY

Concept card

The rule

  • Tally, then percentage, then ratio: n_minority/N gives p; n_majority/n_minority gives the ratio, (1-p)/p
  • Severity bands (this course's own): ≥40% balanced · 20-40% mild · 5-20% moderate · <5% severe
  • The 1-p identity: a majority-only classifier's accuracy is exactly 1 − p
  • Two axes, not one: the ratio and the absolute minority count answer different questions -- check both

Memorable example

CFPB's real 223/777 split: 22.3% minority, ratio ≈3.48:1, MILD by this course's bands -- and 1 − 0.223 = 0.777, exactly the majority-class floor Module 02 Concept 01 already used two modules ago.

CAREER PRACTICE

Interview questions

How would you test a new target column for class imbalance?
Tally the class counts, convert to percentages, compute the majority:minority ratio, and classify severity against a stated rule of thumb -- then separately check the absolute minority count against whatever train/test split you plan to use.
How do you distinguish "imbalanced" from "requires action"?
Severity alone doesn't decide that -- it depends on the absolute minority count surviving a split, and on what the model actually needs to catch. A mild imbalance with a healthy minority count may need nothing; a severe one with too few minority rows to evaluate on needs attention regardless of what a single accuracy number suggests.
What changes about evaluation once imbalance is confirmed?
Accuracy alone stops being trustworthy -- exactly Module 02's existing point about precision, recall, and the confusion matrix. This concept doesn't re-teach that toolbox; it only explains why a skewed target makes reaching for it necessary in the first place.
Design question: a stakeholder sees 95% accuracy and wants to ship immediately. What would you check first?
Whether the target is imbalanced enough that predicting the majority label alone would already reach something close to 95% -- and if so, ask what fraction of the actual minority cases the model catches, not what its overall accuracy is.
