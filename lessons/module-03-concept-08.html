MODULE 03 · CONCEPT 08

How many buckets
before the buckets become the problem.

Concept 07 asked how skewed the target's own labels are. This concept drops the target entirely and looks at a feature field instead: how many distinct values does it actually take, and what happens once that count gets large? Cardinality means the number of distinct categories, K, that a categorical field holds. It has nothing to do with class imbalance -- that was a question about the target column; this is a question about a feature column, and a field can have any cardinality regardless of how balanced or skewed the label is. The fix -- one-hot encoding for low K, out-of-fold target encoding for high K -- belongs to Module 04. This concept is only the diagnosis: tally K, compute the cardinality ratio K/N and classify severity against a stated band, then check a genuinely separate question -- does K stay bounded as N grows, or does it grow right along with N. The worked example reuses CFPB Model 1's own 1,000-row test set across three real fields spanning the full severity range, from a 5-category Product field to a 340-company Company field to a fully degenerate, one-value-per-row Complaint ID field.

02 · WHY IT EXISTS

An uninspected high-K field breaks quietly, not loudly

A categorical field with a large number of distinct values, K, either gets naively one-hot encoded into hundreds of mostly-empty columns, or naively ordinal-encoded in a way that implies a false order between categories that never had one. Worse, a category that never appeared during training can show up for the first time at inference and silently produce a broken or degraded encoding. EDA's job is to count K now, classify how severe it is, and flag it -- before any encoding choice gets locked in. Building the actual fix -- one-hot encoding, out-of-fold target encoding -- belongs entirely to Module 04.

CFPB Model 1's real 1,000-row test set, the same set reused from Module 02 Concept 01 and Concept 07. 07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"One-hot encoding always works."

It works fine at K=5. At K=340 it produces 340 mostly-empty columns per row -- Section 15's contrast table names the point where it stops being practical.

"A high-K field is basically an ID, so it doesn't matter."

Only true in the true-identifier case, like Complaint ID. Company has K=340 but still carries real, cross-row generalizable signal -- the fix there is smarter encoding, not deletion.

"High cardinality is the same thing as class imbalance."

Direct callback to Concept 07 -- one is a feature's distinct-value count, the other is the target's own label skew. A field can have any cardinality regardless of how balanced the target is.

"Counting K on the full dataset is enough."

It ignores the unseen-category risk that only appears once train and test are actually split (Module 01 Concept 06) -- a company seen only in the test fold looks entirely new to an encoder fit on train.

MECHANISM

Tally, ratio, severity, scaling check, flag

Step 1 — tally the number of distinct values, K, in the feature column (here, 5 for Product, 340 for Company, 1,000 for Complaint ID).
Step 2 — compute the cardinality ratio, K/N (5/1,000 = 0.5%, 340/1,000 = 34.0%, 1,000/1,000 = 100%).
Step 3 — classify severity against this course's stated bands (0.5% → LOW, 34.0% → HIGH, 100% → DEGENERATE).
Step 4 — check whether K stays bounded as N grows, or grows right along with it -- a question the ratio alone cannot answer.
Step 5 — flag the result for Module 04 -- nothing gets one-hot encoded or target-encoded here.

09
MATHEMATICS

Why an identifier field can never accumulate signal, no matter how much data arrives

For a closed-vocabulary field, K(N) is bounded above by some fixed ceiling K_max, independent of N -- a US-state field never exceeds 51 no matter how large the dataset grows. As N grows with K(N) capped, the cardinality ratio necessarily shrinks toward zero:

closed-vocabulary: K(N) ≤ K_max for all N, so K(N)/N → 0 as N → ∞

For an identifier-like field, by construction every row gets its own unique value, so K(N) = N for every N, not just at the current sample size:

identifier field: K(N) = N for all N, so K(N)/N ≡ 1 and N/K(N) ≡ 1, forever

The second identity is the formal reason such a field carries zero cross-row generalizable signal: average rows per category, N/K, stays fixed at exactly 1 no matter how much more data arrives, so no category ever accumulates a second example to generalize from. Company sits between the two extremes -- it grows slowly as N grows (new companies keep appearing) but it never saturates at a fixed ceiling the way a closed-vocabulary field does, and it never degenerates to K=N the way an identifier does. That in-between behavior is exactly why Company needs a real encoding fix rather than either extreme's easy treatment: no naive rule that works for state or for a raw ID handles it correctly.

CODE

Tally, ratio, severity, and a growth hint, from scratch

PYTHON · NO LIBRARIES 
from collections import Counter

def diagnose_cardinality(values):
    counts = Counter(values)
    n = len(values)
    k = len(counts)

    if n == 0:
        return {"error": "no rows to diagnose"}

    ratio_pct = k / n * 100

    if ratio_pct >= 50:
        severity = "degenerate"
    elif ratio_pct >= 10:
        severity = "high"
    elif ratio_pct >= 1:
        severity = "moderate"
    else:
        severity = "low"

    # growth_hint is a diagnosis-time flag, not a proof: a field where
    # K == N on the SAMPLE you have is treated as identifier-like; a
    # true bounded/open-vocabulary call needs the same field checked
    # again as N grows, which this single-sample function can't see.
    growth_hint = "identifier-like (K == N)" if k == n else "check as N grows"

    return {
        "k": k, "n": n,
        "cardinality_ratio_pct": round(ratio_pct, 4),
        "avg_rows_per_category": round(n / k, 4),
        "severity": severity,
        "growth_hint": growth_hint,
    }

company_values = [f"company_{i % 340}" for i in range(1000)]
result = diagnose_cardinality(company_values)
assert result["k"] == 340
assert result["cardinality_ratio_pct"] == 34.0
assert result["severity"] == "high"

# edge case: a true identifier column, K == N exactly
complaint_ids = [f"id_{i}" for i in range(1000)]
edge = diagnose_cardinality(complaint_ids)
assert edge["k"] == edge["n"] == 1000
assert edge["severity"] == "degenerate"
assert edge["growth_hint"] == "identifier-like (K == N)"

REALITY

Production implications

  • Wide one-hot matrices cost real memory and compute at serving time, not just at training time -- a factor worth weighing before the encoding choice is locked in, not after.
  • An open-vocabulary field's taxonomy keeps growing after deployment -- new companies keep appearing -- which eventually forces an encoder retrain or an explicit "other" fallback bucket, a real operational cost this concept only flags.
  • Encoding by a field like Company could indirectly correlate with a protected attribute -- flagged here as a real concern, not resolved or built in this concept.
19
RECALL

Knowledge check

Why is Company flagged HIGH while a field like US state almost never is, even though both are "categorical"?
State is closed-vocabulary -- K is capped at 51 no matter how much data arrives, so its ratio shrinks toward zero as N grows. Company is open-vocabulary -- new companies keep appearing, so K keeps climbing with N, and at CFPB's real N=1,000 it already sits at 340, a 34.0% ratio.
Why is K==N treated as degenerate rather than just "very high cardinality"?
When K equals N, every row has its own unique value by construction, so average rows per category is fixed at exactly 1 forever -- no category can ever accumulate a second example to generalize from. That's a qualitatively different situation from merely "a lot" of distinct values.
Why aren't the cardinality ratio and the bounded-vs-growing check the same question?
The ratio is a single snapshot at the current N. Bounded-vs-growing asks how K behaves as N changes -- two fields can share an identical ratio today and still diverge completely as more data arrives, one saturating and the other climbing without limit.

Concept card

The rule

  • Tally, then ratio, then scaling: count K, compute K/N, then check whether K stays bounded as N grows or grows with it
  • Severity bands (this course's own): <1% low · 1-10% moderate · 10-50% high · ≥50% (K≈N) degenerate/identifier-like
  • Reciprocal relationship: the cardinality ratio K/N and average rows per category N/K are algebraic reciprocals, not two independent checks
  • Flag and hand off: one-hot encoding and out-of-fold target encoding are Module 04's job, not diagnosed here

23
CAREER PRACTICE

Interview questions

How would you diagnose a new categorical feature's cardinality before choosing an encoding?
Tally the distinct value count K, compute the cardinality ratio K/N, and classify severity against a stated rule of thumb -- then separately check whether K stays bounded as more data arrives or grows right along with it, since the ratio alone can't answer that.
How do you distinguish high cardinality from class imbalance?
Cardinality measures how many distinct values a feature column holds. Class imbalance measures how skewed the target column's own labels are. They're different axes -- a feature's distinct-value count says nothing about how balanced the target is, and vice versa.
What's the red flag that a categorical field might actually be an identifier and not a real feature?
K equal to, or very close to, N -- every row (or nearly every row) taking its own unique value. That field carries no cross-row generalizable signal and risks the same leakage and overfitting trap as training on a row's own ID.
Design question: a categorical feature that worked fine in training starts throwing errors in production. What would you check first?
Whether a brand-new category -- one absent from the training data -- is now appearing at inference time. A one-hot or ordinal encoder fit only on the categories seen during training has no defined behavior for a category it never saw, exactly the unseen-category failure mode this concept flags.
