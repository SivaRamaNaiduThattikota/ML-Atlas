07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Running each check once, in isolation, means EDA is done."

Misses that a real dataset needs all eight run together on the same pull, not sequentially and separately on convenient small examples.

"A check that found nothing this pull will find nothing next pull."

Violates Concept 09's own production note -- every check needs re-running on every new pull, not assumed clean forever.

"A clean, 0-gap pass isn't worth documenting."

A clean pass is still evidence, not an excuse to skip the write-up -- the point is proving the check ran, not just that it passed.

09
MATHEMATICS

A tally, not a new formula

This concept introduces no new statistical mechanism -- unlike Sections 09 of Concepts 04 through 09, there is no derivation here. The only expression this concept adds is a bookkeeping identity over the eight naive/honest pairs already derived:

gap_count = Σ 1[naive_i ≠ honest_i], for i in {C02, C03, C04, C05, C06, C07, C08, C09}

Evaluated against Section 05's table, every one of the eight indicator terms equals 1 -- naive_i never matches honest_i for any of the eight checks -- so gap_count = 8. That is the entire mathematical content of this concept: a count over eight already-verified pairs, flagged explicitly as bookkeeping, not a statistical mechanism of its own.

CONCRETE USE

Shipping into Module 04 with a partial pass

CODE

A thin checklist runner, calling out to Concepts 02-09's own logic

PYTHON · CALLS OUT, DOESN'T RE-DERIVE 
# One function per concept. Each one is a thin call-out to that
# concept's own already-published logic -- the z-score/IQR math lives
# in Concept 04's Section 12, the KS statistic in Concept 05's, the
# Pearson correlation in Concept 06's, the as-of filter in Concept 09's,
# and so on. Nothing here re-derives any of that internal math.

def check_univariate(df):      return c02.summarize(df)       # Concept 02
def check_missingness(df):     return c03.missing_rates(df)   # Concept 03
def check_outliers(series):    return c04.z_and_iqr(series)   # Concept 04
def check_shift(train, prod):  return c05.ks_statistic(train, prod)  # Concept 05
def check_correlation(df):     return c06.pearson_by_group(df)       # Concept 06
def check_imbalance(labels):   return c07.class_ratio(labels)        # Concept 07
def check_cardinality(df):     return c08.k_over_n(df)               # Concept 08
def check_leakage(df, cutoff): return c09.as_of_filter(df, cutoff)   # Concept 09

CHECKS = [check_univariate, check_missingness, check_outliers, check_shift,
          check_correlation, check_imbalance, check_cardinality, check_leakage]

def run_eda_pass(naive_readings, honest_readings):
    """naive_readings and honest_readings are 8-element lists, one
    entry per check above, already produced by CHECKS. This function
    adds nothing statistical -- it only tallies where they disagree."""
    disagreements = sum(1 for n, h in zip(naive_readings, honest_readings) if n != h)
    assert disagreements == 8, "expected all 8 checks to disagree on CFPB's real data"
    return disagreements

RECALL

Knowledge check

Why does EDA need a running checklist of independent checks rather than one summary number?
Because the eight checks are independent of one another -- a clean univariate read says nothing about whether missingness is MAR, and a clean missingness read says nothing about temporal leakage. One summary number can only ever speak to one of the eight; running all eight is the only way to actually know where the dataset stands.
Why does this concept introduce no new mechanism?
Every number in its synthesis table was already derived by Concepts 02-09, using their own already-taught methods. This concept's only original contribution is the tally -- counting where the naive and disciplined readings disagree -- which is bookkeeping, not a statistical derivation.
What does the 8-for-8 finding prove, and what doesn't it prove?
It proves that, on these eight specific checks run on CFPB's real Model 1 data, every single one exposed a naive-versus-honest gap. It does not prove that every check on every dataset will always find a gap -- that would be a much stronger, unearned claim this concept explicitly avoids making.

FEEDBACK

Solution and teach-back

Open the worked solution

Missingness (Concept 03's check): naive -- 3 of 10 rows missing overall (30%), looks random enough to drop. Honest -- all 3 missing rows are on the phone channel (3 of 5 phone rows, 60%); the web channel has 0 of 5 missing (0%). That's MAR by channel, not MCAR.

Outliers (Concept 04's check): on the 7 non-missing scores [2,7,8,8,8,9,9], mean=7.2857, sample std (ddof=1)=2.4300, so z for the value 2 is (2-7.2857)/2.4300 = -2.175 -- under 3 in magnitude, naive reading is "no outlier." Honest: Q1=7.5, Q3=8.5, IQR=1.0, lower bound = Q1-1.5×IQR = 6.0 -- the value 2 sits below 6.0 and is flagged. The z-score sits close to its own small-sample ceiling of (n-1)/√n = 2.268 and never had a real chance to cross 3, the same gap Concept 04 first showed.

Temporal leakage (Concept 09's check), cutoff = Feb 1: known-as-of-Feb-1 scores are [7,8,9,8,9] (Jan 5, Jan 9, Jan 16, Jan 24, Feb 1), sum=41, honest mean = 41/5 = 8.20. Naive (all 7 non-missing scores, ignoring the cutoff) = 51/7 = 7.2857. Bias = 7.2857 − 8.20 = −0.9143, an 11.15% deflation rather than an inflation -- because the two future rows (Feb 12's score of 2, Feb 20's score of 8) pull the naive mean down instead of up, the mirror image of Concept 09's own worked example.

Teach-back: explain why the temporal-leakage bias came out negative here when Concept 09's own worked example came out positive, and what that sign difference is telling you about the direction the metric was moving over time.

CAREER PRACTICE

Interview questions

Conceptual: why does EDA need a running checklist of independent checks rather than one summary number?
Because none of the eight checks implies any of the others -- a dataset can pass a univariate sanity check and still hide MAR missingness, an uncontrolled confounder, or a leaked future row. Only running all of them, every time, actually closes the gap.
Math: state the tally identity and apply it to a hypothetical 5-check pass with 3 disagreements.
gap_count = Σ 1[naive_i ≠ honest_i] over the checks run. For 5 checks with 3 disagreements, gap_count = 3, meaning 3 of the 5 checks found a naive-versus-honest gap and 2 agreed -- a 3-for-5 result, not the 8-for-8 this concept found on CFPB's real data.
Coding: sketch the checklist-runner structure without re-deriving any internals.
One thin function per concept (check_univariate through check_leakage), each calling out to that concept's own already-published logic -- Section 12's structure. The runner itself only zips the naive and honest outputs and counts where they differ; it never reimplements a z-score, a KS statistic, or a Pearson correlation.
Debugging: a report claims "EDA complete," but Module 04 later finds a leaked feature. What would you check first?
Whether all eight checks actually ran on this specific pull, or only the ones that seemed relevant to whoever wrote the report -- the exact failure mode Section 16 names, and precisely the corner Concept 09's leakage check exists to close.
System design: how would you enforce "all 8 checks ran" as a build-time gate on a recurring CFPB pull?
Extend Concept 09's Section 18 idea: parameterize every check by the pull's own run date and dataset hash, and fail the pipeline build if any of the 8 check functions in Section 12's CHECKS list didn't produce a logged result for that run -- turning an honor-system checklist into an automated gate.
