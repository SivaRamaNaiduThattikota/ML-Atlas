MODULE 04 · CONCEPT 05

A timestamp isn't one feature.
It's several, hidden until you pull them apart.

Concept 04 fixed a numeric field's scale. It never opened up what a timestamp actually holds. date_received on its own is just an epoch number to a model -- but inside it are a day-of-week rhythm, a month of seasonal position, a weekend flag, and however much time has elapsed since something else happened. Calendar parts are deterministic and free to extract. Elapsed-time features are not always free -- they carry the same leakage risk Module 03 Concept 09 diagnosed in a summary statistic, now showing up inside a single engineered feature instead.

MODULE 04 · CONCEPT 05 ACTIVE (5/10)

PROGRESSIVE BEGINNER CORE

Calendar parts are always safe. Elapsed-time features are safe only sometimes.

A raw timestamp bundles several signals a model can't see until you unbundle them. Day-of-week, month, and is-weekend are deterministic functions of the timestamp alone -- no fitting, no risk. An elapsed-time feature subtracts two dates, and that second date -- the anchor -- has to already be in the past relative to the moment you're predicting at, or the feature is leakage.

01 · CONCEPT FIRST

One timestamp, four hidden features.

CALENDAR PARTS

Day-of-week, month, is-weekend -- pure deterministic functions of a single timestamp. No parameters, no fitting, always safe to compute on any row.

ELAPSED-TIME FEATURES

The gap between the timestamp being predicted at and some anchor date. Safe only if that anchor date was already known BEFORE the prediction moment -- otherwise it's leakage.

First memory: calendar parts need nothing checked. Elapsed-time features need one thing checked, every time: is the anchor date before the point I'm predicting at?
02 · WHY IT EXISTS

Concepts 02-04 never opened up a timestamp's own structure.

Categorical encoding (Concepts 02-03) reshaped labels into numbers. Numerical scaling (Concept 04) fixed a numeric field's magnitude and shape. Neither one ever looked INSIDE date_received -- a field that, left as a raw epoch number, hides a weekday rhythm, a seasonal position, and a weekend flag from any model that only sees one big integer.

04 · TECHNICAL MECHANISM

Same six rows, one feature that fails the anchor check

Complaint 101 eventually resolves on 2023-01-25, 19 days after its 2023-01-06 intake. Suppose a feature case_age_days = date_resolved − date_received = 19 gets fed into a model that must predict something AT INTAKE TIME (relief-risk, before the case has even been worked). The validity rule is: anchor date must be ≤ the moment you're predicting at. Here the anchor is date_resolved (2023-01-25), which is strictly AFTER intake (2023-01-06) -- the feature cannot exist yet at the moment the prediction is actually needed. This is the exact failure Concept 09 diagnosed in a naive full-dataset mean that silently included 3 future rows past a stated cutoff, inflating 5.00 days to 6.60 days (a 32% inflation) -- now recurring inside one engineered feature instead of an aggregate statistic.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Just feed the raw timestamp number into the model."

False -- a raw epoch value has no meaningful linear relationship to most targets. A model sees one big integer, not a weekday rhythm or a seasonal position.

"Any date subtraction is a fine elapsed-time feature."

False -- the M03C09 leakage callback. If the anchor date lies after the moment you're predicting at, the feature literally does not exist yet when you'd need it in production.

"Calendar parts need fit-on-train like Concept 04's scalers."

False -- day-of-week, month, and is-weekend are parameter-free functions of a timestamp alone. There's nothing to fit, and nothing that can leak from train into test.

04
INTUITION

A timestamp is a compressed bundle, not one number

A single date_received value is really several different signals folded into one integer: which day of the week it fell on, which month of the year, whether it landed on a weekend, and how much time has passed since something else happened to that same consumer. A model handed the raw epoch number sees none of that -- unbundling it is the entire point of this concept.

Analogy boundaryThe bundle image explains why extraction matters. It doesn't by itself explain why SOME extracted features (elapsed-time ones) carry a timing risk that others (calendar parts) simply don't -- Sections 05 and 09 make that case formally.

MECHANISM

Parse, extract, and gate before using anything

Step 1 — parse the raw timestamp into a structured date/time value.
Step 2 — extract calendar parts freely -- weekday, month, is-weekend need no validation.
Step 3 — for any elapsed-time feature, identify its anchor date explicitly.

09
MATHEMATICS

Weekday as a parameter-free function, and a leakage proof

A date maps to an integer day-count since a fixed epoch, and weekday = (epoch_day_count + offset) mod 7 -- a deterministic, parameter-free function of the date alone. Contrast this directly with Concept 04's z-score, z = (x − μ) / σ, where μ and σ are parameters ESTIMATED from training data and therefore have to be fit before use. Weekday has no such estimation step, ever.

weekday(date) = (days_since_epoch(date) + offset) mod 7 -- no fitted parameters

Small formal claim: "days to resolution" is unconditionally leakage as an intake-time feature. CFPB's own process guarantees date_resolved ≥ date_received for any real case -- a complaint cannot resolve before it's received. So anchoring an intake-time feature to date_resolved means t_anchor > t_predict for every row where resolution takes any nonzero time, which violates anchor ≤ predict-time by construction, not by some unlucky accident of the data.

12
CODE

From-scratch calendar-part extraction and an anchor-validity assertion

PYTHON · EXPLICIT DATE ARITHMETIC, NO BLACK-BOX CALL 
from datetime import date

def day_of_week(d):
    """Monday=0 ... Sunday=6, via Python's own proleptic Gregorian
    ordinal -- an explicit, parameter-free calendar computation."""
    return d.weekday()

def month(d):
    return d.month

def is_weekend(d):
    return day_of_week(d) >= 5

def days_since(anchor, predict_time):
    """Elapsed-time feature. Raises if the anchor is not safely in
    the past relative to the moment being predicted at."""
    assert anchor <= predict_time, (
        f"leakage: anchor {anchor} is after predict_time {predict_time}"
    )
    return (predict_time - anchor).days

intake_103 = date(2023, 2, 10)
prior_101 = date(2023, 1, 6)
assert days_since(prior_101, intake_103) == 35

intake_101 = date(2023, 1, 6)
resolved_101 = date(2023, 1, 25)
try:
    days_since(resolved_101, intake_101)  # anchor is AFTER predict_time
    raise SystemExit("expected the leakage assertion to fire")
except AssertionError:
    pass  # correctly rejected: resolution isn't known yet at intake

16
DIAGNOSIS

Failure modes

LEAKAGE ANCHOR

An elapsed-time feature anchored after predict-time

This concept's core warning -- the M03C09 pattern recurring inside a single feature instead of an aggregate statistic.

TIMEZONE-INCONSISTENT PARSING

An off-by-one weekday

Parsing a timestamp in one timezone at training time and another at serving time can silently shift which calendar day -- and therefore which weekday -- a record lands on.

DAY-OF-YEAR EXPLODED INTO 365 COLUMNS

One-hot on the wrong granularity

One-hotting a 365-value day-of-year field produces mostly-empty sparse columns; month or week-of-year is almost always the right granularity instead.

18
REALITY

Production implications

  • Serving-time anchor computation must use only data that already existed as of the request -- the same as-of discipline Module 03 Concept 09 established for EDA now applies to every elapsed-time feature at inference time.
  • Timezone consistency between training data and live serving matters -- a calendar-part function applied to the same instant in two different timezones can disagree about which day, and therefore which weekday, it falls on.
  • An elapsed-time feature like days_since_last_complaint belongs in a feature store computed from live history, not baked into a static offline table that can go stale.
19
RECALL

Knowledge check

Why is days_since_last_complaint valid while case_age_days from date_resolved is leakage, when both are date subtractions?
The anchor's timing is what matters, not the subtraction itself. days_since_last_complaint anchors to a PRIOR date_received, which by definition already happened before the current intake. case_age_days anchors to date_resolved, which for a real case happens AFTER intake -- so it fails anchor ≤ predict-time.
Why don't calendar parts need Concept 04's fit-on-train discipline?
Weekday, month, and is-weekend are deterministic functions of a timestamp alone -- no mean, std, min, or max is ever estimated from data, so there's no fitted state to leak between train and test in the first place.
Why is "days to resolution" fine as a model target but not as a Model 1 feature?
As a target, the model is only asked to predict it -- it's never assumed to be known as an input. As an input feature for a model that must predict at intake time, it requires information (the resolution date) that doesn't exist yet at that moment.

CAREER PRACTICE

Interview questions

Conceptual: why is a raw epoch timestamp a poor feature on its own?
It's one large, roughly linear integer with no explicit calendar structure -- a model can't recover weekday rhythm, seasonal position, or a weekend effect from it without those being extracted as separate features first.
Math: prove that "days to resolution" is leakage as an intake-time feature.
CFPB's process guarantees date_resolved ≥ date_received for any real case. An intake-time feature must satisfy anchor ≤ predict-time where predict-time = date_received. Anchoring to date_resolved makes anchor ≥ predict-time, with strict inequality whenever resolution takes any nonzero time -- violating the validity condition by construction, not by an unlucky draw of data.
Coding: write the assertion that guards an elapsed-time feature against leakage.
assert anchor <= predict_time, f"leakage: anchor {anchor} is after predict_time {predict_time}" -- raised before the feature is ever computed, not caught downstream.
Debugging: a live model's elapsed-time feature behaves oddly in production. First thing to check?
Whether the anchor used at serving time is genuinely available before the prediction request -- a common bug is a feature pipeline that was validated offline against historical data (where the anchor always happened to be in the past) but pulls a not-yet-available value live.
System design: how would a feature store keep an elapsed-time feature leakage-free at serving time?
Compute the elapsed-time value from a point-in-time consumer-history store that only exposes records that existed as of the request timestamp, matching Module 03 Concept 09's as-of discipline -- never precompute it offline against a table that could include later-arriving rows.
