MODULE 04 · CONCEPT 06

Combining two features can create a new one.
It can also combine two problems into one.

Concepts 02 through 05 each transformed exactly one existing feature at a time -- reshape a category, rescale a number, decompose a timestamp. This concept does something genuinely different: it builds a NEW feature by combining two or more existing features, as a ratio, a product, or a categorical-grouped statistic. That combining step doesn't reset anything. If either input already carried leakage, the derived feature carries it too, no matter how innocent the arithmetic looks -- and even when neither input is leaky, combining two features that already overlap can add redundancy instead of signal.

POSITIONSixth concept of Module 04 -- the first to combine two or more existing features into something new, rather than transform one feature at a time
PREREQUISITEModule 04 Concept 05's anchor-validity rule, generalized to either input; Module 04 Concept 03's target encoding, named then distinguished -- this groups a feature by another feature, not by the label

MODULE 04 · CONCEPT 06 ACTIVE (6/10)

PROGRESSIVE BEGINNER CORE

Combining features doesn't clean them. It inherits whatever was already wrong.

An interaction or derived feature is built by combining two or more existing features -- a ratio, a product, or a statistic computed within groups of a category. The combining step itself has no opinion about validity: a derived feature is only as safe as its inputs. And even when both inputs are safe, combining two that already overlap can add redundancy rather than new signal.

01 · CONCEPT FIRST

Concepts 02-05 transformed one feature. This one combines two.

ONE FEATURE AT A TIME (Concepts 02-05)

Encode a category, target-encode a high-cardinality category, scale a number, decompose a timestamp -- every one of those operates on a single existing feature and reshapes it.

INTERACTION / DERIVED FEATURES (this concept)

Take TWO existing features and combine them into a new one: a ratio (A/B), a product (A×B), or a statistic of one feature computed within groups of another (a categorical-grouped mean).

First memory: a derived feature's validity is never its own. It's inherited entirely from the features it was built out of.
02 · WHY IT EXISTS

A model can't reliably discover "the ratio of A to B" on its own.

Handed feature A and feature B as two separate columns, a linear model can only ever combine them additively through its own coefficients -- it has no built-in way to represent A divided by B or A times B unless that exact term is supplied as an input. A tree-based model can approximate an interaction through a sequence of splits, but only approximately, and only with enough depth and data to find it. An explicit derived feature hands the relationship over directly instead of hoping the model rediscovers it.

04 · TECHNICAL MECHANISM

The inheritance rule, and a second risk that isn't about timing at all

Rule: derived.leaky = inputA.leaky OR inputB.leaky -- true regardless of which operator combines them. contact_rate combines prior_contact_attempts (self-reported at intake, safe) with days_since_last_complaint (validated safe back in Concept 05) -- neither input is leaky, so contact_rate is SAFE. engagement_score multiplies prior_contact_attempts (safe) by case_age_days -- and case_age_days already failed Concept 05's anchor check, because it's anchored to date_resolved, which isn't known at intake. "Multiply two numbers" sounds like innocent arithmetic, but it launders nothing: engagement_score inherits case_age_days' leakage wholesale. Row 102 is a useful boundary case -- prior_contact_attempts is 0 there, so engagement_score numerically evaluates to 0, yet it's still structurally leaky. A leaky feature doesn't become safe just because it happens to compute to zero on one row.

There's also a second, independent risk that has nothing to do with timing. prior_contact_attempts and case_age_days already move together across these six rows -- their Pearson correlation is r = -0.4923. Even setting the leakage problem aside entirely, multiplying two features that already overlap adds some redundancy on top of whatever else is wrong, not just new information.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Combining two features resets leakage risk."

False -- the inheritance rule. A derived feature is exactly as leaky as its worst input, no matter what operator combines them.

"A ratio or product is obviously safe because it's just arithmetic."

False -- arithmetic doesn't launder timing. engagement_score is "just" a multiplication, and it's leaky anyway, because case_age_days was leaky before the multiplication ever happened.

"If it's not leaky, it's automatically useful."

False -- multicollinearity is a separate failure mode. contact_rate can clear the leakage check completely and still be redundant with features already in the model.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

Recite the inheritance rule

derived.leaky = inputA.leaky OR inputB.leaky, true for a ratio, a product, or a grouped statistic alike -- the operator never matters.

Name multicollinearity as a separate risk

Two inputs can already share information regardless of either one's leakage status -- that's a redundancy problem, not a timing problem, and it needs its own check.

Distinguish this concept's grouping from Concept 03's target encoding

04
INTUITION

Mixing two ingredients doesn't fix a spoiled one

Think of combining two features like mixing two ingredients into one dish. If one ingredient was already spoiled, mixing it with a fresh one doesn't make the dish safe to eat -- it just spreads the problem through the whole plate. Ratio, product, and grouped-mean are three different recipes, but none of them can cook the spoilage out of an input that was already bad.

Analogy boundaryThe recipe image explains WHY inheritance happens -- spoilage spreads, it doesn't dilute away. It doesn't by itself state the formal OR-rule or the separate multicollinearity axis; Sections 05 and 09 make those precisely.

06
MECHANISM

Check both inputs, combine, then check redundancy separately

Step 1 — pick the candidate input features to combine.
Step 2 — check each input's OWN validity independently -- reuse whichever earlier gate already flagged it (Concept 01, 03, or 05).
Step 3 — combine via ratio, product, or a categorical-grouped statistic.
Step 4 — derived validity = NOT(either input leaky) -- the OR-gate, applied regardless of which operator was used.
Step 5 — run a separate correlation check between the inputs -- an independent redundancy gate that clearing Step 4 does not clear for free.
07
VISUALIZATION

Two inputs, two independent gates

Two feature inputsA and B, each already independently validated or flagged
Leakage-inheritance gate (OR)Fails if EITHER input was already leaky
Correlation / multicollinearity checkIndependent of the OR-gate -- flags redundancy even between two safe inputs

Both branches run off the same two inputs, but they answer different questions. The OR-gate asks "is this derived feature allowed to exist at prediction time at all?" The correlation check asks "does it add anything new, or mostly repeat what's already there?" A derived feature can pass one and fail the other.

09
MATHEMATICS

The inheritance proof, and a second axis: correlation

Claim: if f(A, B) is any derived feature and t_anchor(B) > t_predict for one of its inputs, then f(A, B) cannot be computed at t_predict either, regardless of what f is. Proof sketch by contradiction: suppose f(A, B) could be computed at t_predict. Computing f requires the value of B, which by definition is not yet available until t_anchor(B), and t_anchor(B) > t_predict by assumption. So B's value does not exist at t_predict -- contradiction. The operator f never enters the argument; a ratio, a product, and a grouped mean all require the same thing, the value of B, so all three fail identically when B is unavailable.

ratio = A / B product = A × B grouped_mean(X, g) = (1/|G_g|) Σ X_j, j ∈ G_g

Multicollinearity is measured with the same Pearson correlation coefficient reused from Module 03 Concepts 02 and 06, r = Σ(x_i − x̄)(y_i − ȳ) / √(Σ(x_i − x̄)² Σ(y_i − ȳ)²). Across the 6-row sample, prior_contact_attempts = [2, 0, 3, 1, 4, 2] and case_age_days = [19, 13, 14, 21, 9, 15] give r = -0.4923. The plot below places each row at its own (attempts, case_age) position -- the downward drift is the correlation made visible, independent of either feature's leakage status.

VIF (variance inflation factor) is the formal quantitative version of this check: VIF_j = 1 / (1 − R_j²), where R_j² comes from regressing feature j on all other features. It's named forward here, via statsmodels' variance_inflation_factor, not derived in full -- the simple pairwise Pearson check above is this concept's bounded scope.

CODE

From-scratch combine, group, and correlate

PYTHON · EXPLICIT INHERITANCE CHECK, NO BLACK-BOX CALL 
def combine_features(a, b, a_leaky, b_leaky, op):
    """A derived feature inherits leakage from EITHER input, regardless
    of which operator combines them -- ratio, product, or otherwise."""
    derived_leaky = a_leaky or b_leaky
    if op == "ratio":
        if b == 0:
            return None, derived_leaky  # undefined ratio, not a silent 0
        value = a / b
    elif op == "product":
        value = a * b
    else:
        raise ValueError(f"unknown op: {op}")
    return value, derived_leaky

# contact_rate (row 103): both inputs already safe -> derived feature safe
rate, leaky = combine_features(3, 35, a_leaky=False, b_leaky=False, op="ratio")
assert round(rate, 4) == 0.0857 and leaky is False

# engagement_score (row 101): case_age_days already failed Concept 05's anchor check
score, leaky = combine_features(2, 19, a_leaky=False, b_leaky=True, op="product")
assert score == 38 and leaky is True  # leaky regardless of the number itself

def grouped_mean(values, groups, target_group):
    picked = [v for v, g in zip(values, groups) if g == target_group]
    return sum(picked) / len(picked)

case_age = [19, 13, 14, 21, 9, 15]
product = ["Mortgage", "Credit reporting", "Mortgage",
           "Debt collection", "Credit reporting", "Mortgage"]
assert round(grouped_mean(case_age, product, "Mortgage"), 4) == 16.0

def pearson(xs, ys):
    n = len(xs)
    mx, my = sum(xs) / n, sum(ys) / n
    cov = sum((x - mx) * (y - my) for x, y in zip(xs, ys))
    vx = sum((x - mx) ** 2 for x in xs)
    vy = sum((y - my) ** 2 for y in ys)
    return cov / (vx * vy) ** 0.5

attempts = [2, 0, 3, 1, 4, 2]
r = pearson(attempts, case_age)
assert round(r, 4) == -0.4923  # matches the worked example, computed here from scratch

ECOSYSTEM

scikit-learn's PolynomialFeatures builds the combination, not the checks

scikit-learn's PolynomialFeatures is the real production tool for exactly the mechanical part of this concept -- with degree=2, interaction_only=True, it builds every pairwise product across a feature matrix automatically, instead of hand-writing one interaction at a time. It performs neither the leakage-inheritance check nor a multicollinearity check -- both stay the engineer's job, before and after PolynomialFeatures ever runs. Feeding it a leaky column produces leaky interaction terms just as fast as safe ones.

CONTRAST

Ratio vs. product vs. grouped-mean vs. letting a tree find it vs. formal VIF

ApproachWhat it actually doesWhen it wins
Ratio (this concept)Divides one feature by another -- a rate or intensity measureWhen the RELATIONSHIP between two quantities matters more than either alone, e.g. attempts per day since last contact
Product (this concept)Multiplies two features togetherWhen an effect is amplified by both factors jointly, not additively
Grouped-mean (this concept)Averages one feature within groups of anotherWhen a category's typical behavior on some numeric field is itself informative

DIAGNOSIS

Failure modes

INHERITED LEAKAGE

A derived feature built on an already-leaky input

This concept's core warning -- the operator never matters, only the inputs' own validity.

SILENT MULTICOLLINEARITY

Near-duplicate features inflating a linear model's coefficient variance

Neither input alone gets flagged leaky, yet combining them adds redundancy a leakage check will never catch.

UNDEFINED RATIO

A first-on-file row with no prior gap to divide by

Needs an explicit N/A convention, matching Concept 05's "-- (first on file)" -- not a silent 0 and not a crash.

18
REALITY

Production implications

  • Training/serving skew risk: if the derived-feature computation (which operator, which fields) drifts between the training pipeline and the serving pipeline, the model sees a different feature in production than the one it was trained on.
  • Grouped-mean features need the same group statistics computed on the training split only and then applied at serving time -- the same fit/transform split Concept 01 and Concept 04 required, even though no label is involved here.
  • A ratio's undefined-denominator case needs the exact same explicit convention in production as in training -- an N/A that's handled consistently, not a value that silently becomes 0 in one pipeline and crashes in the other.
19
RECALL

Knowledge check

State the leakage-inheritance rule in one line.
derived.leaky = inputA.leaky OR inputB.leaky -- true for a ratio, a product, or a grouped statistic alike, because the operator never changes whether the underlying information was available at prediction time.
How is multicollinearity different from leakage, given that both can make a feature "bad"?
Leakage is about TIMING -- whether the information existed yet at the moment you'd need it. Multicollinearity is about REDUNDANCY -- whether an input already overlaps with another input. A feature can fail one, the other, both, or neither.
Why does avg_case_age_by_product still need a fit-on-train discipline even though it groups by a feature, not the label?
Grouping by a feature instead of the label removes Concept 03's specific self-inclusion-of-the-target risk, but the group means themselves are still statistics estimated from data -- computing them from the full dataset instead of the training split alone would let test-set values leak into a "training-only" statistic, the same general concern Concepts 01 and 04 raised for any fitted parameter.

Interview questions

Conceptual: why can't a linear model "discover" a ratio feature on its own?
A linear model only combines its inputs through a weighted sum of the raw columns it's given -- it has no built-in mechanism to represent A divided by B unless that exact ratio is supplied as an input feature.
Math: prove that a derived feature inherits leakage from either input, regardless of the operator.
If f(A, B) requires the value of B, and B is not available until t_anchor(B), which is after t_predict, then f(A, B) cannot be computed at t_predict either -- computing f requires B's value, and that value does not exist yet. This holds for any f, so a ratio, a product, and a grouped mean all fail identically.
Coding: write the check that flags a derived feature as leaky.
derived_leaky = a_leaky or b_leaky -- computed once from each input's already-established validity, before the ratio/product/groupmean value itself is even used.
Debugging: a "safe" derived feature is underperforming in production relative to offline validation. What's a likely cause beyond leakage?
Multicollinearity -- if the derived feature is highly correlated with another feature already in the model, it may be adding little genuine signal even though it passed the leakage check cleanly; check pairwise correlation or VIF, not just the anchor rule.
System design: how would a feature store keep a grouped-mean feature leakage-free and skew-free at serving time?
Compute the group statistics once from the training split only, store them as a lookup keyed by the group category, and apply that same fixed lookup at serving time -- never recompute the group mean live from data that includes the row being predicted on, and never let the training and serving pipelines diverge on which rows fed the lookup.
