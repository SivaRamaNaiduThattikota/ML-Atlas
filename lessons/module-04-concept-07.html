Five warnings so far.
They were always the same question.

Concepts 01, 03, 04, 05 and 06 each raised a leakage warning specific to its own technique — a train/holdout gate, an out-of-fold rule, a fit-on-train rule, an anchor rule, an inheritance rule. 02 · WHY IT EXISTS

The five rules don't compose automatically

Without a portable master test, a genuinely new feature idea -- one that doesn't obviously match Concept 01's train/holdout gate, or Concept 03's target-encoding pattern, or Concept 05's timestamp pattern -- has no home to be checked against. An engineer needs one thing to reach for, not five specialists to consult.

03 · CONCRETE EXAMPLE

A feature that passes one rule and fails another

A new field on the familiar 6-row CFPB table (same IDs, consumers, and dates as Concepts 05-06): relief_granted (101=1, 102=0, 103=0, 104=1, 105=1, 106=1). Three ways to build recovery_rate_by_consumer from it: Tier 1 (fully naive -- includes the row's own label), Tier 2 (leaves the row's own label out, but still averages over same-consumer rows regardless of date), and Tier 3 (leaves the label out AND restricts to same-consumer rows dated strictly before the current one).

04 · TECHNICAL MECHANISM

One principle, stated as a 4-check list

General principle: a feature is legitimate if and only if every value and every fitted parameter it depends on would already exist at the real moment of prediction. As a checklist:

CheckQuestionGeneralizes
1 · Origin timingIs this raw field actually known at the moment you'd predict?Concept 01
2 · Fitted-statistic isolationWas any fitted number (a mean, a rate, a scaler) estimated without using this row's own label or test-set data?Concepts 03 + 04
3 · Anchor validityIs every date or event this feature references already in the past relative to prediction time?Concept 05
4 · Inheritance through combinationIf this feature combines other features, did EVERY one of them already pass?Concept 06

Fail any single check and the feature is leakage — exactly the same "fail one gate, reject the feature" structure Concept 01 already used, now generalized past correlation-based signal checks alone.

06
MECHANISM

Trace origin, then three more checks, reject on any single failure

Step 1 — trace the feature's origin -- is the raw field known at prediction time?
Step 2 — check fitted-statistic isolation -- did any fitted number see this row's own label or test data?
Step 3 — check anchor validity -- is every referenced date or event already in the past?
Step 4 — check inheritance -- if this feature combines others, did every one of them already pass?
Step 5 — reject the feature on ANY single failure -- passing three checks never compensates for failing the fourth.

09
MATHEMATICS

A recursive generalization of Concept 06's inheritance proof

A feature f depending on components c_1..c_n and fitted parameters θ_1..θ_m is available at t_predict if and only if every c_i is available at t_predict AND every θ_j was estimated using only data available at t_predict — applied recursively, since any c_i can itself be a derived feature with its own components and parameters. This is exactly Concept 06's OR-inheritance rule, generalized from two inputs to arbitrarily many, and to fitted parameters as well as raw components.

f available at t_predict ⟺ (∀i: c_i available at t_predict) ∧ (∀j: θ_j estimated only from data available at t_predict)

This is exactly what Checks 2 and 3 formalize separately for Tier 2 of recovery_rate_by_consumer: Check 2 (fitted-statistic isolation) asks whether θ used the row's own label — it does not, so Check 2 passes. Check 3 (anchor validity) asks whether every c_i referenced (the other same-consumer rows averaged in) was itself available at t_predict — for row 101, rows 103 and 106 were not, so Check 3 fails. The two checks are logically independent conditions in the same conjunction; satisfying one says nothing about the other.

CODE

A from-scratch audit function

PYTHON · EXPLICIT 4-CHECK AUDIT, NO BLACK-BOX CALL 
def audit_feature(origin_known_at_predict, fit_uses_only_train_excludes_own_label,
                   anchor_leq_predict, all_inputs_already_passed):
    """Returns (verdict, failed_check) -- rejects on the FIRST failing
    check, mirroring Concept 01's own fail-any-one-gate structure."""
    if origin_known_at_predict is False:
        return "LEAKY", "Check 1 (origin timing)"
    if fit_uses_only_train_excludes_own_label is False:
        return "LEAKY", "Check 2 (fitted-statistic isolation)"
    if anchor_leq_predict is False:
        return "LEAKY", "Check 3 (anchor validity)"
    if all_inputs_already_passed is False:
        return "LEAKY", "Check 4 (inheritance through combination)"
    return "SAFE", None

# prior_contact_attempts: raw, safe, unfitted, non-combined
assert audit_feature(True, True, True, True) == ("SAFE", None)

# Tier 1 of recovery_rate_by_consumer: fails Check 2 (own-label included)
assert audit_feature(True, False, True, True) == ("LEAKY", "Check 2 (fitted-statistic isolation)")

# Tier 2 of recovery_rate_by_consumer: passes Check 2, fails Check 3
assert audit_feature(True, True, False, True) == ("LEAKY", "Check 3 (anchor validity)")

# engagement_score: fails Check 4 because case_age_days already failed
assert audit_feature(True, True, True, False) == ("LEAKY", "Check 4 (inheritance through combination)")
13
ECOSYSTEM

scikit-learn's Pipeline catches part of Check 2, nothing else

scikit-learn's own data-leakage documentation and its Pipeline + cross_val_score combination automatically prevent one specific class of Check 2 violation -- fitting a transformer on combined train+test data. It does NOT catch Check 1 (origin timing), Check 3 (anchor validity), or the own-label half of Check 2 -- that specific case still needs category_encoders' out-of-fold-aware TargetEncoder, already cited in Concept 03. Google's ML glossary entry on label leakage states the master principle this concept generalizes to. For a per-consumer statistic used inside cross-validation specifically, scikit-learn's GroupKFold is the real tool that keeps one consumer's rows from crossing fold boundaries -- ties Check 2's isolation requirement to Concept 03's fold machinery without re-deriving it.

DIAGNOSIS

Failure modes

THE TIER-2 TRAP

Passed the check you thought of, shipped anyway

The single most dangerous pattern this concept names -- verifying one specific rule and stopping there.

ASSUMING A NEW RULE IS NEEDED

"This feature idea is unusual, so it needs its own new leakage rule"

False in every case this module has covered -- the 4-check list already generalizes far enough.

CONFLATING CHECK 2 AND CHECK 4

Treating fitted-statistic isolation and inheritance as the same failure surface

They are not -- Check 2 is about a statistic seeing its own label; Check 4 is about a combined feature inheriting an already-leaky input.

18
REALITY

Production implications

  • Feature audits belong in CI as an explicit checklist gate before a new feature reaches training data, not as an ad hoc manual review that happens inconsistently.
  • Feature lineage documentation should record which check number a feature passed and why, so a later engineer doesn't have to re-derive the reasoning from scratch.
  • The Tier-2-style trap is exactly the kind of bug that survives a code review focused on only one familiar rule -- the audit needs to be run as a checklist, not from memory.
19
RECALL

Knowledge check

Why is Tier 2 dangerous despite passing Concept 03's own-label rule?
Passing Check 2 (no self-label) says nothing about Check 3 (anchor validity). Tier 2 excludes each row's own label but still averages over same-consumer rows dated after the current row -- a completely separate failure that Check 2 was never designed to catch.
Why is Concept 02 not one of the five cited concepts?
One-hot and ordinal encoding reshape an already-safe category into numbers without looking at time, the label, or any other feature -- they introduce no timing risk of their own for this checklist to catch.
Why does this concept introduce zero new leakage types?
Every one of the 4 checks is a direct generalization of a rule Concepts 01, 03, 04, 05 or 06 already established -- this concept's contribution is the unification, not a new failure mode.

The rule

23
CAREER PRACTICE

Interview questions

Conceptual: why is one general test better than remembering five specific rules?
A genuinely new feature idea rarely announces which of five specific rules applies to it. One general availability test -- would this exist at the real moment of prediction -- covers any feature idea without requiring it to be pattern-matched against a memorized list first.
Mathematical: state the recursive availability condition for a composite feature.
A feature f depending on components c_1..c_n and fitted parameters θ_1..θ_m is available at t_predict iff every c_i is available at t_predict AND every θ_j was estimated using only data available at t_predict -- applied recursively, since any c_i can itself be composite.
Coding: why does check order matter in audit_feature's implementation?
It doesn't change the final verdict (any single failure means LEAKY regardless of order), but returning the FIRST failing check gives a more actionable diagnostic message than silently checking all four and reporting only the worst case -- the engineer sees exactly which rule to go fix first.
Debugging: a feature passed code review because it satisfied "the leakage rule" the reviewer knew. It still leaked. What's missing?
The reviewer likely checked one specific rule (often Check 1 or Check 2, the most commonly taught) without running the other three -- exactly the Tier 2 trap. The fix is a checklist-driven review, not a single remembered heuristic.
System design: how would you encode this checklist into an automated feature-store gate?
Require every new feature definition to declare its origin timing, whether it depends on any fitted statistic (and on what split that statistic was estimated), its anchor dates if any, and its input features if it's a combination -- then run all 4 checks programmatically before the feature is allowed into the training feature set, rejecting on the first failure exactly like audit_feature does.
