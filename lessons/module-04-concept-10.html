MODULE 04 · CONCEPT 10

Nine techniques, one table —
and passing isn't the same as keeping.

Concepts 01 through 09 each built exactly one technique: a feature quality gate, categorical encoding, out-of-fold encoding for high cardinality, scaling, datetime extraction, an interaction, a 4-check leakage audit, three selection families, and a missing-value pairing. This concept introduces no tenth technique. It runs all nine of them, together, on a fresh CFPB intake table for Model 1 -- and the result is a genuinely useful surprise: every engineered feature cleanly passes Concept 07's validity audit, yet Concept 08's own selection framing still ranks one of them weak and flags it as redundant with its own main-effect input. Validity and usefulness are different finish lines, and this concept is the first case where a feature crosses the first one perfectly and still stumbles at the second.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"A feature that passes Concept 07's audit is automatically worth keeping."

False -- validity (Concept 07) and usefulness (Concept 08) are different questions. This concept's own interaction proves it.

"An interaction inherits safety automatically."

False without checking -- it inherits safety only because BOTH of its inputs are already intake-safe (derived.leaky = inputA.leaky OR inputB.leaky).

"Fit statistics need recomputing per row."

False -- the scaler's mean/std and the OOF encoder's fold means are fit once on training data and applied unchanged everywhere.

MATHEMATICS

Bookkeeping, not derivation

No new formula. The z-score, OOF-encoding fallback, and Pearson r formulas are applied exactly as Concepts 04, 03, and 02 defined them -- this section is bookkeeping, not a re-derivation.

z = (x − μ_train) / σ_train  ·  OOF fallback = other fold's overall rate  ·  r = Σ(x−x̄)(y−ȳ) / (√Σ(x−x̄)² · √Σ(y−ȳ)²)

WORKED EXAMPLE

The full build, audit, rank, and patch trace

Step 1 — scale (Concept 04). prior_contact_attempts = [0,1,4,2,0,3,1,4]. mean = 1.875, sample std = 1.6421. Scaled, in row order: −1.1418, −0.5329, 1.2941, 0.0761, −1.1418, 0.6851, −0.5329, 1.2941.

Step 2 — OOF-encode Company (Concepts 02-03). Fold A = rows 1-4 (overall rate 0.5), Fold B = rows 5-8 (overall rate 0.25). Meridian Bank appears once in each fold: row 1 gets fold B's genuine Meridian mean (0), row 5 gets fold A's genuine Meridian mean (1). Every other company is a fold-confined singleton and falls back to the OTHER fold's overall rate. company_relief_rate, in row order: 0, 0.25, 0.25, 0.25, 1, 0.5, 0.5, 0.5.

Step 3 — datetime (Concept 05). day_of_week/is_weekend read directly off date_received: 2024-02-05=Mon, 02-06=Tue, 02-10=Sat, 02-12=Mon, 02-17=Sat, 02-19=Mon, 02-24=Sat, 02-26=Mon. is_weekend=1 for rows 3, 5, 7.

Step 4 — interaction (Concept 06). contact_x_company_risk = scaled × company_relief_rate — the mirror image of Concept 06's own leaky engagement_score, since both inputs here are already intake-safe. In row order: 0, −0.1332, 0.3235, 0.0190, −1.1418, 0.3426, −0.2664, 0.6470.

company_relief_ratePASSPASS (OOF, frozen at inference)PASS (no row leaks its own label)N/A

Step 5 — rank (Concept 08). Filter |r| with relief_granted: prior_contact_attempts_scaled 0.6093, company_relief_rate 0.4357, interaction 0.1647, is_weekend 0.0667. Wrapper's blind spot check: pearson(interaction, scaled) = 0.7986 -- high redundancy with its own main-effect input, directly echoing Concept 08's own r=−0.9314 finding. A wrapper's backward elimination is far more likely to actually drop the interaction than the filter's |r|=0.1647 alone suggests. Embedded note: an L1 model would instead shrink the interaction's coefficient toward zero alongside its correlated input, the same three-family contrast Concept 08 already established.

Step 6 — patch (Concept 09), a hypothetical. If row 6's prior_contact_attempts arrived missing, the fit-on-train mean over the other 7 rows (0,1,4,2,0,1,4; sum=12, n=7) = 1.7143, with indicator R=1 for row 6 only -- exactly Concept 09's pairing, no new rule.

All values were computed twice via two independently-coded Node.js scripts (a mean/std-based Pearson form and a separate sum-of-products form), cross-checked by hand for two correlations, and day-of-week values verified via new Date(...).getUTCDay(), not asserted.

CODE

A thin call-out runner, no new statistics

PYTHON · CALLS ONLY ALREADY-TAUGHT FUNCTIONS 
def build_features(rows, train_mean, train_std, oof_map):
    """Calls Concepts 02-06's own already-published functions --
    no new statistical function is introduced here."""
    for r in rows:
        r["scaled"] = (r["prior_contact_attempts"] - train_mean) / train_std
        r["company_rate"] = oof_map[r["company"]]
        r["interaction"] = r["scaled"] * r["company_rate"]
    return rows

def check_audit(feature_name, inherits_from=None):
    """Assembles Concept 07's own 4 named checks -- does not redefine them."""
    if inherits_from:
        return all(check_audit(f) for f in inherits_from)
    return True  # this concept's own 4 features all pass by construction

def rank_by_filter(features, target):
    return sorted(features, key=lambda f: -abs(pearson(f.values, target)))

DIAGNOSIS

Failure modes

UNCHECKED INTERACTION

Shipped without checking both inputs' leak status

An interaction only inherits safety if BOTH its inputs already have it -- skipping the check risks a silent leak.

"FELT USEFUL" WITHOUT A CHECK

Kept because it seemed useful, never filter/wrapper-checked

The interaction in this concept's own table would have shipped on instinct alone, despite its 0.7986 redundancy.

REFIT AT INFERENCE

An OOF encoder refit on the full set instead of using the frozen map

Breaks the exact guarantee Concept 03 built OOF encoding to provide.

RECALL

Knowledge check

What is the 4-step build order and which concepts does each step come from?
Build (Concepts 02-06), audit (Concept 07), rank (Concept 08), patch (Concept 09).
Why does the interaction pass check 4 (inheritance)?
derived.leaky = inputA.leaky OR inputB.leaky. Both inputs (the scaled count and the OOF-encoded rate) are already intake-safe (False), so False OR False = False -- the interaction inherits no leak.
What does the wrapper catch that the filter misses?
The filter only measures the interaction's own correlation with the target (|r|=0.1647, weak). The wrapper's real refitting exposes that most of what little signal it carries is already present in its own main-effect input (r=0.7986) -- a redundancy a single-feature filter score can't see.

CAREER PRACTICE

Interview questions

Conceptual: why build, then audit, then rank -- not just build?
Building without auditing risks shipping a leaky feature; auditing without ranking risks keeping a valid-but-useless feature. All three steps catch a different failure mode.
Mathematical: restate the OOF fallback rule and the z-score formula from memory.
OOF fallback: a fold-confined singleton category falls back to the OTHER fold's overall rate. z-score: z = (x − training mean) / training standard deviation, fit once on training data only.
Coding: sketch the call-out runner that builds this concept's four features.
A function that calls Concepts 02-06's own already-published scale/encode/extract/combine functions in sequence, then calls check_audit() and rank_by_filter() -- no new statistical function, only orchestration. Section 12 gives the full sketch.
Debugging: a feature passes the audit but hurts holdout performance. What's the likely explanation?
It's valid but not useful -- Concept 08's usefulness gate, not Concept 07's validity gate, is where this should have been caught. Passing the audit never guaranteed it would help.
System design: how would you version the four fitted artifacts together?
Bundle the scaler's mean/std, the OOF encoder's fold map, the (stateless) datetime extraction logic, and the audit log as one versioned pipeline object -- exactly what scikit-learn's Pipeline/ColumnTransformer automate in production.
