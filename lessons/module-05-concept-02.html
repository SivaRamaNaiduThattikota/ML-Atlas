MODULE 05 · CONCEPT 02

Three ways to change the rows.
One rule that applies to all three.

Concept 01 explained the mechanism -- an unweighted objective's free majority-only floor. This concept opens the first actual fix: change the training set's own class balance before a model ever sees it. Random oversampling duplicates existing minority rows until the classes are more balanced. Random undersampling drops majority rows until they match. SMOTE does neither -- it synthesizes brand-new minority points by interpolating between real neighbors in feature space, points that have never literally occurred in the data. All three reach a real balance, and all three are governed by one non-negotiable rule: resample after the split, inside the training fold only. Do it before the split, and a duplicated row can land on both sides of the boundary -- the model doesn't have to generalize to a row it already memorized, and the reported score quietly lies.

02 · WHY IT EXISTS

Removing the cheap incentive directly

Concept 01's free floor exists because the training set itself is lopsided. Resampling directly removes the cheap incentive by changing that balance before training starts, rather than changing the objective or the decision rule.

03 · CONCRETE EXAMPLE

An 18-row stand-in fold, three techniques, three different results

4 minority rows (M1-M4), 14 majority rows -- ratio 3.5:1, close to CFPB's real 3.4843:1 (Module 03 Concept 07, cited). Oversampling: 18 → 28 rows (10 duplicates added). Undersampling: 18 → 8 rows (10 majority rows dropped). SMOTE: 18 → 28 rows too -- but 10 of its 14 minority rows are brand-new synthetic points, not copies.

04 · TECHNICAL MECHANISM

SMOTE: nearest neighbor, then interpolate

For minority row M1=(1,2), its nearest minority neighbor by Euclidean distance is M3=(1,1), distance 1.0000. A synthetic point is placed at λ=0.4 along the segment from M1 toward M3: (1, 2+0.4×(1−2)) = (1, 1.6) -- a value that never literally occurred in the data.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"SMOTE just duplicates rows like oversampling."

False -- it interpolates new points that never literally occurred.

"Resampling can happen anytime before training, even on the raw file."

False -- it must happen after the split, inside each fold's training partition only.

"Undersampling is strictly worse because it discards data."

A real tradeoff, not an absolute -- it's cheap and discards real majority information, not automatically the wrong choice.

04
INTUITION

Photocopying, thinning, and sketching a crowd

Oversampling is photocopying existing photos until the two piles match in size. Undersampling is removing photos from the larger pile until the counts match. SMOTE is an artist sketching a new, plausible photo halfway between two real ones -- a genuinely new image, not a copy.

Analogy boundaryThe photocopy/sketch picture explains what each technique produces. It doesn't capture the k-NN selection or the λ interpolation formula -- Section 09 gives those precisely.

06
MECHANISM

Three techniques, the same 18-row fold

OVERSAMPLING / UNDERSAMPLING

Draw with replacement to pad the minority class (14 total, 10 duplicates added), or drop majority rows at random to shrink it (4 total, 10 dropped).

SMOTE

For each anchor minority point, find its nearest minority neighbor, then place a new point at a random fraction λ along the segment between them.

WORKED EXAMPLE

The full fold, all three techniques, and the leakage demonstration

Stand-in training fold (18 rows, chosen so the arithmetic is exact and traceable by hand): 4 minority rows M1=(1,2), M2=(2,3), M3=(1,1), M4=(4,4) (features: prior_contact_attempts, satisfaction_score); 14 majority rows J1-J14. Ratio 14/4=3.5, close to CFPB's real 3.4843 (Module 03 Concept 07, cited).

TechniqueMinority afterMajority afterTotal
Random oversampling14 (4 real + 10 duplicate)1428
Random undersampling44 (10 dropped)8
SMOTE14 (4 real + 10 synthetic)1428

SMOTE detail. For anchor M1=(1,2): distances to M2/M3/M4 are 1.4142/1.0000/3.6056 -- nearest is M3 (1.0000). Synthetic at λ=0.4: (1, 2+0.4×(1−2)) = (1, 1.6). For anchor M4=(4,4): distances to M1/M2/M3 are 3.6056/2.2361/4.2426 -- nearest is M2 (2.2361). Synthetic at λ=0.4: (4+0.4×(2−4), 4+0.4×(3−4)) = (3.2, 3.6).

Leakage demonstration. WRONG (resample before split): duplicate M1-M4 once each on the full 18-row pool → 22 rows. A concrete random split then sends test={M2′, J14,J13,J12,J11} and train=the remaining 17 rows, including the original M2. M2′ is a byte-for-byte duplicate of M2 -- the model never had to generalize to it, only recognize a row it had already memorized. RIGHT (resample after split): split the original 18-row pool first -- test={M4, J14,J13,J12,J11} (5 rows), train={M1,M2,M3, J1-J10} (13 rows). THEN oversample the train fold only: pad minority from 3 to 10 → train becomes 20 rows. Test stays untouched at 5 rows -- M4 was never duplicated, synthesized, or even looked at during resampling.

VERIFICATION: every number above was computed via a Node.js script, then independently re-derived via a second, differently-structured script (squared-distance-then-sqrt instead of direct subtraction-then-sqrt; fraction-based λ=2/5 instead of decimal 0.4) -- both matched exactly.

12
CODE

All three techniques, from scratch

PYTHON · NO LIBRARIES 
import random, math

def oversample(minority, target_count):
    return minority + random.choices(minority, k=target_count - len(minority))

def undersample(majority, target_count):
    return random.sample(majority, target_count)

def euclid(a, b):
    return math.sqrt((a[0]-b[0])**2 + (a[1]-b[1])**2)

def nearest_neighbor(anchor, pool):
    others = [p for p in pool if p != anchor]
    return min(others, key=lambda p: euclid(anchor, p))

def smote_point(anchor, neighbor, lam):
    return (anchor[0] + lam*(neighbor[0]-anchor[0]),
            anchor[1] + lam*(neighbor[1]-anchor[1]))

# Reproduces this concept's own Section 10 result
M1, M2, M3, M4 = (1,2), (2,3), (1,1), (4,4)
minority = [M1, M2, M3, M4]
n1 = nearest_neighbor(M1, minority)
assert n1 == M3
assert smote_point(M1, n1, 0.4) == (1.0, 1.6)
n4 = nearest_neighbor(M4, minority)
assert n4 == M2
assert smote_point(M4, n4, 0.4) == (3.2, 3.6)

19
RECALL

Knowledge check

Why do oversampling and SMOTE reach the identical final count through different means?
Both pad the minority class to 14 rows to match the majority, but oversampling does it by duplicating 10 of the 4 real rows, while SMOTE generates 10 brand-new synthetic points by interpolation -- same target count, genuinely different composition.
Why does resampling before the split create a leak, specifically?
A row duplicated (or synthesized) before the split can end up split across both train and test -- the model then only has to recognize a row it already memorized in training, not truly generalize to a new one.
Why is undersampling a real tradeoff rather than a strictly worse choice?
It's cheap and simple, but discards real majority-class information that a model might have found useful -- a genuine cost, not automatically outweighed by oversampling or SMOTE's own costs.

23
CAREER PRACTICE

Interview questions

Conceptual: why does SMOTE exist when oversampling already balances the classes?
Oversampling only ever duplicates existing points, which can encourage a model to overfit to those exact rows. SMOTE instead generates genuinely new points by interpolation, giving the model more varied minority-class examples to learn from.
Mathematical: state SMOTE's interpolation formula and what λ controls.
x_new = x_i + λ(x_zi − x_i), where x_zi is x_i's nearest minority neighbor. λ∈[0,1] controls how far along the segment from x_i toward x_zi the new point lands -- λ=0 reproduces x_i exactly, λ=1 reproduces x_zi exactly.
Coding: implement a minimal SMOTE point generator.
Find the nearest neighbor by Euclidean distance among the minority pool, then linearly interpolate between the anchor and that neighbor at a chosen λ -- Section 12 gives the full from-scratch implementation with matching asserts.
Debugging: a model's offline recall looks great after SMOTE but collapses in production. What's the first thing to check?
Whether SMOTE (or any resampling) was fit before the split, leaking synthetic or duplicate information into what should have been held-out rows -- exactly the leak this concept's own lab demonstrates.
System design: how would you correctly integrate resampling into a cross-validation pipeline?
Use a pipeline (e.g. imbalanced-learn's Pipeline) that refits the resampler fresh inside each fold's training partition only, never on the full dataset before splitting -- the same discipline Module 04 Concept 03's out-of-fold encoding already established.
