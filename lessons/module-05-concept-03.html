MODULE 05 · CONCEPT 03

Same rows.
A mistake just costs more now.

Concept 02 fixed imbalance by changing the training rows -- duplicate, drop, or synthesize. This concept leaves every row exactly as it is: same count, no duplicates, no drops, no synthetic points. Instead, it changes the training objective -- a fixed per-class weight multiplies each row's individual loss before those per-row losses are summed into the batch total. A minority-class mistake now costs the optimizer more than an equally-wrong majority-class mistake, purely because of who made it. On CFPB's real 223/777 split, the standard "balanced" weighting gives a ratio of 3.4843 -- the exact same number as Concept 01's own break-even ratio -- and that identical ratio shows up again in the weighted loss, and again in the gradient. Same 18 rows, same predictions, same two mistakes -- only the multiplier changed, and it changed how hard the optimizer gets pulled toward fixing each one.

02 · WHY IT EXISTS

Removing the cheap incentive a different way

An unweighted loss treats every row's error identically (Concept 01's own mechanism). Weighting removes the cheap incentive a naive objective has by making a minority mistake cost more -- not by changing how many minority rows exist.

03 · CONCRETE EXAMPLE

Two equally-wrong rows, one costs 3.48× more after weighting

M1 (minority, y=1) predicted probability 0.35. J1 (majority, y=0) predicted probability 0.65. Both are equally wrong (|p−y|=0.65 each), and both produce the identical unweighted loss (1.0498). After applying the "balanced" weight, M1's mistake now costs the optimizer 3.4843× more than J1's.

04 · TECHNICAL MECHANISM

The balanced formula, applied to CFPB's real split

w_c = N / (n_classes × n_c). For CFPB's 223/777 split: w_minority = 1000/(2×223) = 2.2422, w_majority = 1000/(2×777) = 0.6435. Ratio = 2.2422/0.6435 = 3.4843 -- the exact same number as Concept 01's own break-even ratio.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Weighting removes rows too."

False -- the row count never changes, always.

"Any weight ratio works as well as any other."

False -- there's a principled default ("balanced"), and departing from it needs a reason.

"Computing weights from train+test together is exactly as bad as Concept 02's leak."

False -- much milder. A class weight is a single global scalar derived from a distributional summary, not a duplicated row -- but still best fit on the training fold only.

09
MATHEMATICS

The balanced formula, the weighted loss, and the gradient identity

w_c = N / (n_classes × n_c)
L_weighted = Σ w_{y_i} × loss(p_i, y_i)
∂loss/∂z = p − y (stated, not derived -- Module 06/09 give the full mechanism)
weighted gradient contribution = w_{y_i} × (p_i − y_i)

When two rows share identical unweighted loss, their weighted-loss ratio equals their weight ratio exactly -- the shared base loss cancels algebraically.

10
WORKED EXAMPLE

Weights, a matched pair, the gradient, and a 3-row batch

Step 1 -- weights. w_minority = 1000/(2×223) = 2.2422. w_majority = 1000/(2×777) = 0.6435. Ratio = 3.4843 -- identical to Concept 01's break-even ratio and Concept 02's fold ratio.

Step 2 -- matched pair. M1 (minority, y=1, p=0.35): unweighted loss = −ln(0.35) = 1.0498. J1 (majority, y=0, p=0.65): unweighted loss = −ln(0.35) = 1.0498 -- identical by construction (both equally wrong). Weighted(M1) = 2.2422×1.0498 = 2.3539. Weighted(J1) = 0.6435×1.0498 = 0.6756. Ratio = 3.4843 exactly -- the shared base loss cancels.

Step 3 -- gradient. Unweighted (p−y): M1 = −0.65, J1 = 0.65 -- identical magnitude, opposite sign. Weighted: M1 = 2.2422×(−0.65) = −1.4574, J1 = 0.6435×0.65 = 0.4183. Ratio of magnitudes = 3.4843 again -- the same ratio propagates from loss to gradient.

Step 4 -- a 3-row batch. Add J2 (majority, y=0, p=0.05, well-classified): unweighted loss = −ln(0.95) = 0.0513. Unweighted batch total = 1.0498+1.0498+0.0513 = 2.1509. Weighted batch total = 2.3539+0.6756+0.6435×0.0513 = 3.0624. M1's share of the total: unweighted 1.0498/2.1509 = 48.81%, weighted 2.3539/3.0624 = 76.86% -- still exactly 3 rows, same 3 predictions, only the multiplier changed.

VERIFICATION: every number above was computed via a Node.js script, then independently re-derived a second time via a differently-structured script (an alternate logarithm path with an exp() round-trip check, reordered summation, and a fraction-based ratio cross-check) -- both matched to full float precision.

12
CODE

Balanced weights and weighted loss, from scratch

PYTHON · NO LIBRARIES 
import math

def compute_balanced_weight(n_samples, n_classes, class_count):
    return n_samples / (n_classes * class_count)

def weighted_log_loss(y, p, weight):
    loss = -math.log(p) if y == 1 else -math.log(1 - p)
    return weight * loss

# Reproduces this concept's own Section 10 result
w_min = compute_balanced_weight(1000, 2, 223)
w_maj = compute_balanced_weight(1000, 2, 777)
assert round(w_min, 4) == 2.2422
assert round(w_maj, 4) == 0.6435
assert round(w_min / w_maj, 4) == 3.4843

assert round(weighted_log_loss(1, 0.35, w_min), 4) == 2.3539
assert round(weighted_log_loss(0, 0.65, w_maj), 4) == 0.6756
13
ECOSYSTEM

The real formula, the per-row parameter, and the production tool

scikit-learn's compute_class_weight confirms the exact "balanced" formula: weights = n_samples / (n_classes × np.bincount(y)). log_loss's sample_weight parameter grounds "multiply each row's loss, then sum/average" -- weighting happens per-sample, before aggregation. Wikipedia's Cross-entropy page grounds the formal loss definition stated (not derived) here, since Module 06 hasn't taught logistic regression yet. LogisticRegression's class_weight parameter ('balanced' or a custom dict) is the real, current tool applying this technique automatically.

REALITY

Production implications

  • Document the chosen weighting scheme (ratio, and whether "balanced" or custom) alongside the model version -- mirroring Concept 02's own "document the technique" discipline.
  • A retrained model must refit weights from the new training fold's own class counts, not reuse a stale ratio.
19
RECALL

Knowledge check

Why do M1 and J1 produce the identical unweighted loss?
Both are equally wrong by construction -- |p−y|=0.65 for each -- and binary cross-entropy for equally-wrong predictions on opposite classes produces the same loss value: −ln(0.35) in both cases.
Why does only the ratio between the two weights matter, not their absolute values?
Scaling both weights by the same constant scales every row's loss and gradient by that constant uniformly -- it changes the overall learning rate effectively, not the relative pull between classes, which depends only on the ratio.
Why is fitting weights on train+test combined milder than Concept 02's own leak, but still wrong?
A class weight is a single global scalar derived from a distributional summary (class counts), not a row-level duplicate that can literally appear on both sides of the split -- but it still uses information from the test set to shape training, violating the fold-only discipline.

23
CAREER PRACTICE

Interview questions

Conceptual: why reweight the loss instead of the rows?
Reweighting avoids resampling's own costs -- no duplicated rows to overfit to, no discarded majority information, no synthetic points to generate -- while still removing the naive objective's cheap incentive to ignore the minority class.
Mathematical: state the balanced formula and the weighted-gradient identity.
w_c = N/(n_classes×n_c). The weighted gradient contribution of a row is w_{y_i}×(p_i−y_i) -- the same (p−y) identity as the unweighted case, scaled by the row's class weight.
Coding: implement weighted log-loss from scratch.
Compute the standard binary cross-entropy loss for the row, then multiply by that row's class weight before it enters the batch sum -- Section 12 gives the full from-scratch implementation with matching asserts.
Debugging: a model's minority recall didn't improve after adding class_weight='balanced'. What's the first thing to check?
Whether the training loop or library call actually respects sample/class weights at all -- some custom training loops silently ignore a weight parameter, in which case setting it has no effect regardless of the value chosen.
System design: how would you keep a fold-only-fitted weighting scheme reproducible across retrains?
Recompute the balanced weights fresh from each new training fold's own class counts at retrain time, and log the resulting weights and ratio alongside the model version -- never hardcode or reuse a stale ratio from a previous training run.
