MODULE 05 · CONCEPT 04

Same model.
A different point on its own curve.

Concepts 02 and 03 both required a full retraining run -- Concept 02 changed which rows the model trained on, Concept 03 changed how much each row's mistake cost during training. This concept touches neither. A trained model has already produced a probability for every row (Module 02 Concept 06's own framing: a raw output is a probability), and the 0.5 cutoff that turns that probability into a class prediction is a convention, not a law. Moving it doesn't retrain anything -- it just commits to a different point on the same ROC/PR curve Module 02 Concept 04 already showed how to sweep. Model H, a model that actually separates the classes, trades 10.0 points of precision for 33.4 points of recall by moving from t=0.50 to t=0.30. Model Z, a model whose ROC-AUC is barely above a coin flip, shows why this lever has a hard limit: no threshold anywhere on its curve gets precision above 33.3%, because the model never learned to separate the classes to begin with.

02 · WHY IT EXISTS

A probability, and a convention on top of it

Module 02 Concept 06 already established that a model's raw output is a probability. The 0.5 cutoff that turns that probability into a class prediction is a convention sitting on top of it, not a law -- nothing stops picking a different one.

03 · CONCRETE EXAMPLE

Model H: the same model, two committed points

At t=0.50: Precision 50.0%, Recall 33.3%, F1 40.0%. Moving to t=0.30, with no retraining at all: Precision 40.0%, Recall 66.7%, F1 50.0%. Recall roughly doubles; precision drops 10 points -- a real trade, not a free improvement.

04 · TECHNICAL MECHANISM

Only the rows in the band change sides

Moving from t=0.50 down to t=0.30 only reclassifies the three rows whose score falls in the band [0.30, 0.50): one true positive newly caught (score 0.38), and two new false positives (scores 0.44 and 0.35). Every other row -- above 0.50 or below 0.30 -- keeps its original classification. Nothing else changed.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Moving the threshold requires retraining."

False -- zero retraining, always. The same probabilities are simply cut at a different point.

"Lower is always better for the minority class."

False -- it's a real precision-for-recall trade, not a strictly-improving move.

"If accuracy or AUC looks fine, some threshold must give both good precision and good recall."

False -- Model Z's ROC-AUC≈0.43 is a concrete counterexample. The ceiling is set by discrimination, not by how many thresholds you try.

MECHANISM

Compute at a threshold, then move it

COMPUTING AT A THRESHOLD

Partition rows by score≥t, tally TP/FP/FN/TN from that partition.

MOVING THE THRESHOLD

Identify the band between the old and new cutoff, recompute only ΔTP/ΔFP from rows in that band, add to the old counts.

09
MATHEMATICS

Precision and recall as functions of t

Precision(t) = TP(t) / (TP(t) + FP(t))
Recall(t) = TP(t) / (TP(t) + FN(t))
TP(t) + FN(t) = n_minority — constant in t (mirrors Concept 01's own TP+FN=n_minority fact)
Band identity: ΔTP = #{positives with score in [t2, t1)}, ΔFP = #{negatives with score in [t2, t1)}, for t2 < t1

Recall is non-decreasing as t decreases, since n_minority is fixed and TP(t) can only grow. Precision is not guaranteed to move monotonically in general -- it trends downward as weaker-scored rows get swept in, but that is a trend, not a strict guarantee.

10
WORKED EXAMPLE

Model H's real trade, and Model Z's discrimination floor

Model H -- a model that separates the classes. 10 scored rows, 3 minority (relief-granted) / 7 majority, a 30% minority share (matching Model D's own 3/10 toy proportion in Module 02 Concept 04). At t=0.50: flagged={0.72,0.61}, TP=1, FP=1, FN=2, TN=6 → Precision=1/2=50.0%, Recall=1/3=33.3%, F1=2/5=40.0% exactly. At t=0.30: flagged adds 0.44, 0.38, 0.35 → TP=2, FP=3, FN=1, TN=4 → Precision=2/5=40.0%, Recall=2/3=66.7%, F1=1/2=50.0% exactly. Band check: the only rows crossing from unflagged to flagged are 0.38 (a true positive, ΔTP=1) and 0.44, 0.35 (two false positives, ΔFP=2) -- old TP 1+1=2 and old FP 1+2=3, both match the direct recount.

Model Z -- a model that never learned to separate the classes. Same shape (3 minority / 7 majority) but positives spread through the distribution rather than clustered at the top. Rank-based ROC-AUC (Module 02 Concept 04's own formula, cited, not re-derived): of the 3×7=21 positive/negative score pairs, 9 have the positive scoring higher = 9/21 = 0.4286 -- statistically indistinguishable from a coin flip on a sample this small. At t=0.50: TP=1, FP=4, FN=2, TN=3 → Precision=1/5=20.0%, Recall=1/3=33.3%, F1=1/4=25.0% exactly. At t=0.30: TP=2, FP=5, FN=1, TN=2 → Precision=2/7=28.6%, Recall=2/3=66.7%, F1=2/5=40.0% exactly.

The discrimination floor, verified across the entire threshold range, not just these two points. Sweeping every threshold from 0.05 to 0.95 in steps of 0.01, Model Z's precision never exceeds 1/3 = 33.3% anywhere on its curve -- the ceiling is set by ROC-AUC≈0.43, not by which threshold gets tried. Model H has no such ceiling: at a high enough threshold it reaches 100% precision (at the cost of recall falling to 33.3%). That contrast -- a real ceiling for Z, no ceiling for H -- is the load-bearing limitation this concept names.

A precise, non-conflated nuance on "badly calibrated" vs. "genuinely undiscriminating": discrimination (ROC-AUC/PR-AUC, Module 02 Concept 04) sets the SHAPE of the curve and is invariant to any monotonic rescaling of the scores (Module 02 Concept 06's own stated fact). Calibration (Module 02 Concept 06) only affects what a given score VALUE claims to mean, not where points sit on the precision/recall curve. So: (a) a genuinely undiscriminating model (Model Z, ROC-AUC≈0.43) has no good threshold ANYWHERE -- the structural limitation. (b) A well-discriminating but badly-calibrated model still has a good operating point SOMEWHERE on its curve -- the raw score value at that point just won't mean what it superficially claims, so the threshold has to be found empirically against a validation set rather than trusted at face value.

VERIFICATION: every confusion matrix above was computed via an executed Node.js script using an automated confusionAt(threshold) function looping over the 10 rows, independently re-verified via a second, separately-written manual loop with its own TP/FP/FN/TN counters -- both matched exactly at every threshold checked. F1 values were additionally cross-checked by hand-deriving exact fractions (1/2, 1/3, 2/5, 2/3 for Model H; 1/5, 1/3, 2/7, 2/3 for Model Z) and applying the harmonic-mean formula symbolically. The discrimination-floor claim was verified by sweeping all 91 threshold values from 0.05 to 0.95 in a separate script and confirming the maximum precision reached anywhere on Model Z's curve.

A clean fit, a boundary case, and a mistake

CLEAN FIT

Model H's 0.50→0.30 move

A real, worthwhile trade -- recall roughly doubles for a 10-point precision cost.

BOUNDARY CASE

A threshold below the minimum score

Flags every row -- recall hits 100%, precision collapses to exactly the dataset's own positive rate, tying back to Module 02 Concept 04's own PR-AUC baseline fact.

MISTAKE TO AVOID

Treating Model Z's poor precision as a threshold-choice problem

Trying more thresholds will not help -- the ceiling is set by ROC-AUC≈0.43, not by search effort.

12
CODE

Threshold sweep and the band identity, from scratch

PYTHON · NO LIBRARIES 
def confusion_at(rows, t):
    tp = fp = fn = tn = 0
    for score, label in rows:
        pred = 1 if score >= t else 0
        if pred == 1 and label == 1: tp += 1
        elif pred == 1 and label == 0: fp += 1
        elif pred == 0 and label == 1: fn += 1
        else: tn += 1
    return tp, fp, fn, tn

def precision_recall_f1(tp, fp, fn):
    p = tp / (tp + fp) if (tp + fp) else 0.0
    r = tp / (tp + fn) if (tp + fn) else 0.0
    f1 = 2 * p * r / (p + r) if (p + r) else 0.0
    return p, r, f1

def band_delta(rows, t1, t2):
    # t2 < t1: rows with score in [t2, t1) are the only ones that flip
    d_tp = sum(1 for s, y in rows if t2 <= s < t1 and y == 1)
    d_fp = sum(1 for s, y in rows if t2 <= s < t1 and y == 0)
    return d_tp, d_fp

# Reproduces this concept's own Section 10 result for Model H
model_h = [(0.72,1),(0.61,0),(0.44,0),(0.38,1),(0.35,0),
           (0.25,0),(0.20,0),(0.18,1),(0.12,0),(0.05,0)]
tp, fp, fn, tn = confusion_at(model_h, 0.50)
assert (tp, fp, fn, tn) == (1, 1, 2, 6)
p, r, f1 = precision_recall_f1(tp, fp, fn)
assert round(p, 4) == 0.5 and round(r, 4) == 0.3333 and f1 == 0.4

tp2, fp2, fn2, tn2 = confusion_at(model_h, 0.30)
assert (tp2, fp2, fn2, tn2) == (2, 3, 1, 4)
d_tp, d_fp = band_delta(model_h, 0.50, 0.30)
assert (d_tp, d_fp) == (1, 2)
assert tp + d_tp == tp2 and fp + d_fp == fp2

REALITY

Production implications

  • A threshold can change via a config value in serving code with no model redeployment -- the cheapest lever in the whole module.
  • Document the exact threshold value alongside the model version, the same discipline Concepts 02-03 established for their own choices.

19
RECALL

Knowledge check

Why does moving the threshold require no retraining?
The model's probabilities were computed once, in a single pass. Moving the threshold only changes which side of a cutoff counts as "flagged" on those already-computed numbers -- no new model artifact is produced.
Why does Model Z have no good threshold anywhere?
Its ROC-AUC≈0.43 means its scores carry almost no ranking information between the two classes -- the curve itself hugs the random diagonal, so no point on it delivers usable precision, regardless of where the threshold is dragged. This is a discrimination problem, not a calibration problem.
What exactly changes between two thresholds?
Only the rows whose score falls in the band between the two cutoffs -- everything above the higher cutoff and everything below the lower cutoff keeps its original classification.

CAREER PRACTICE

Interview questions

Conceptual: why is threshold moving cheaper than resampling or class weighting?
Both resampling and class weighting require a full retraining run on modified rows or a modified loss, producing a new model artifact each time. Threshold moving only changes which side of a cutoff an already-computed probability falls on -- no retraining, no new artifact, often a one-line config change.
Mathematical: state the band identity.
Moving the threshold from t1 down to t2 (t2 < t1) only reclassifies rows whose score falls in the half-open band [t2, t1) -- positives in that band become new true positives, negatives in that band become new false positives, and every row outside the band is unaffected.
Coding: implement the threshold-sweep confusion-matrix function.
Loop over scored rows, classify each as positive if score≥t, and tally TP/FP/FN/TN against the true label -- Section 12 gives the full from-scratch implementation with matching asserts.
Debugging: a team keeps lowering the threshold on a model whose recall won't budge past 40%. What's the first thing to check?
The model's discrimination -- ROC-AUC or PR-AUC -- not more threshold values. If the curve itself is weak, no threshold on it will deliver much more recall without destroying precision; the fix is a better model or better features, not a different cutoff.
System design: how would you monitor a deployed threshold for staleness?
Track the scored-population's distribution over time and compare it against the distribution the threshold was originally tuned on, alerting on meaningful drift -- the same statistical drift-detection idea Module 17 covers in full, named forward only here.
