MODULE 05 · CONCEPT 05

Not the class ratio.
The actual cost of being wrong.

Concepts 02-04 each fixed imbalance procedurally -- resample the rows, weight the loss, move the threshold -- without ever asking what a false negative actually costs versus a false positive, in real business terms. This concept opens that question directly: define an explicit cost matrix (the dollar cost of each of the four outcomes), and derive the decision threshold that minimizes expected cost, t* = C(FP)/(C(FP)+C(FN)). On CFPB's relief-granted problem, a missed valid relief case costing $500 and a wrongly flagged non-relief case costing $50 give a cost ratio of 10 -- deliberately NOT the 3.4843 class ratio Concepts 01 and 03 diagnosed and reused. Threshold moving (Concept 04) sweeps an already-computed curve to find a good point; this concept derives the point directly, in closed form, from the costs themselves -- and proves that "balanced" class weighting is the one special case where those costs are silently assumed to equal the inverse class frequency.

02 · WHY IT EXISTS

The question every prior fix skipped

Concepts 02-04 each fixed imbalance procedurally without ever asking what a false negative actually costs versus a false positive, in real business terms. This concept opens that question -- and shows the answer is usually NOT the class ratio those earlier concepts diagnosed and reused.

03 · CONCRETE EXAMPLE

CFPB's relief-granted cost matrix

C(FN) = $500 -- the cost of missing a valid relief case (consumer harm, escalation risk). C(FP) = $50 -- the cost of wrongly flagging a non-relief case for manual review (about 30 minutes of analyst time). Cost ratio = 500/50 = 10 -- explicitly NOT the 3.4843 class ratio Concepts 01 and 03 diagnosed and reused.

04 · TECHNICAL MECHANISM

Derive the threshold directly from the costs

t* = C(FP) / (C(FP)+C(FN)) -- a direct function of the two costs, no class-ratio input anywhere in the formula. Plugging in CFPB's numbers: t* = 50/(50+500) = 50/550 = 1/11 ≈ 0.0909 (9.09%). Predicting positive is the cheaper choice exactly when a row's probability exceeds this threshold.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"The cost ratio must equal the class imbalance ratio."

False -- CFPB's own numbers are the counterexample: cost ratio 10 ≠ class ratio 3.4843.

"'Balanced' class weighting is always cost-optimal."

False -- only when the real costs happen to match inverse class frequency, which is a coincidence, not a guarantee.

"C(TP) and C(TN) are always exactly zero."

Usually true by convention in this lesson, but stated as a convention, not a law -- a true positive can still trigger a costly downstream action.

09
MATHEMATICS

Deriving t* from expected-cost minimization

E[cost | predict positive] = (1−p)·C(FP)
E[cost | predict negative] = p·C(FN)
Predict positive iff (1−p)·C(FP) < p·C(FN) ⟺ p > C(FP)/(C(FP)+C(FN)) = t*
General 4-term form: t* = [C(FP)−C(TN)] / {[C(FP)−C(TN)] + [C(FN)−C(TP)]}

With C(TP)=C(TN)=0, the general form collapses to t*=C(FP)/(C(FP)+C(FN)). Class-weighting special-case identity: w_majority/(w_majority+w_minority) = n_minority/N for the balanced formula, for ANY N/n_minority/n_majority -- an exact algebraic identity, not a coincidence of CFPB's particular numbers.

10
WORKED EXAMPLE

Cost matrix, derived threshold, and the special-case proof

Step 1 -- the cost matrix. C(TP)=C(TN)=$0 (convention, stated not assumed). C(FN)=$500, C(FP)=$50. Cost ratio = 500/50 = 10 exactly.

Step 2 -- contrast against the class ratio. Module 03 Concept 07 / Concepts 01/03 all cite n_majority/n_minority = 777/223 = 3.4843 (4dp). 10 ≠ 3.4843 -- confirmed by direct comparison.

Step 3 -- derive t*. t* = C(FP)/(C(FP)+C(FN)) = 50/550 = 1/11 ≈ 0.0909 (9.09%).

Step 4 -- class weighting is a special case, proved two independent ways. Derivation A: substitute the class ratio as if it were the cost ratio -- 1/(1+3.4843) = 1/4.4843 = 0.223 exactly. Derivation B: plug Concept 03's own balanced weights directly into the same formula -- w_majority/(w_majority+w_minority) = 0.6435/(0.6435+2.2422) = 0.6435/2.8857 = 0.223 exactly. Both land on exactly 223/1000 = 0.223 -- the minority class's own base rate. "Balanced" class weighting implicitly sets the decision threshold to the minority base rate, regardless of what the real dollar costs are.

Step 5 -- the stakes, on a fixed 10-row toy set (3 minority scores {0.30, 0.20, 0.10}; 7 majority scores {0.19, 0.15, 0.12, 0.05, 0.03, 0.02, 0.01}, matching Concepts 01/04's own 3-minority/7-majority convention). At the class-ratio-implied threshold t=0.223: TP=1, FP=0, FN=2, TN=7 → cost = 2×500 = $1,000. At the true-cost-derived threshold t*≈0.0909: TP=3, FP=3, FN=0, TN=4 → cost = 3×50 = $150. Using the wrong-ratio threshold costs 6.67× more under the identical real cost matrix.

Verification method: every confusion matrix and cost total above was computed via an executed Node.js script using an automated confusionAndCost(threshold) function looping over the 10 rows, independently re-verified via a second, separately-written manual loop with its own TP/FP/FN/TN counters -- both matched exactly at both thresholds. The base-rate identity (0.223) was independently confirmed two ways: algebraic substitution of the class ratio into the t* formula, and direct plug-in of Concept 03's own already-computed balanced weights -- both landed on exactly 223/1000.

12
CODE

Optimal threshold and the special-case proof, from scratch

PYTHON · NO LIBRARIES 
def optimal_threshold(c_fn, c_fp):
    return c_fp / (c_fp + c_fn)

def confusion_and_cost(rows, threshold, c_fn, c_fp):
    tp = fp = fn = tn = 0
    for score, label in rows:
        pred = 1 if score >= threshold else 0
        if pred == 1 and label == 1: tp += 1
        elif pred == 1 and label == 0: fp += 1
        elif pred == 0 and label == 1: fn += 1
        else: tn += 1
    cost = fn * c_fn + fp * c_fp
    return tp, fp, fn, tn, cost

# Reproduces this concept's own Section 10 result
t_star = optimal_threshold(500, 50)
assert round(t_star, 4) == 0.0909

rows = [(0.30,1),(0.20,1),(0.10,1),(0.19,0),(0.15,0),
        (0.12,0),(0.05,0),(0.03,0),(0.02,0),(0.01,0)]
assert confusion_and_cost(rows, 0.223, 500, 50)[:4] == (1, 0, 2, 7)
assert confusion_and_cost(rows, 0.223, 500, 50)[4] == 1000
assert confusion_and_cost(rows, t_star, 500, 50)[:4] == (3, 3, 0, 4)
assert confusion_and_cost(rows, t_star, 500, 50)[4] == 150

# Class-weighting special-case identity
w_min, w_maj = 1000/(2*223), 1000/(2*777)
assert round(w_maj / (w_maj + w_min), 4) == 0.223

19
RECALL

Knowledge check

Why isn't the cost ratio automatically the class ratio?
The class ratio is a fact about the data (n_majority/n_minority); the cost ratio is a business input (C(FN)/C(FP)) -- CFPB's own numbers (10 vs. 3.4843) show they can differ substantially.
What does "balanced" class weighting implicitly assume about costs?
It implicitly sets the decision threshold to exactly the minority base rate, which is mathematically equivalent to assuming the cost ratio equals the inverse class-frequency ratio -- a specific, common, but not universally correct choice.
Derive t* from the two expected-cost expressions.
Predicting positive costs (1−p)·C(FP) in expectation; predicting negative costs p·C(FN). Positive is cheaper exactly when p exceeds C(FP)/(C(FP)+C(FN)) = t*.

21
FEEDBACK

Solution and teach-back

Open the worked solution
t* = 40/(40+800) = 40/840 = 1/21 ≈ 0.0476 (4.76%). At t*: flagged={0.15(TP), 0.10(FP), 0.06(FP)}, unflagged={0.03(FN), 0.02(TN), 0.01(TN)} → TP=1, FP=2, FN=1, TN=2 → cost = 1×800 + 2×40 = $880. At the naive default t=0.5 (no row reaches it): TP=0, FP=0, FN=2, TN=4 → cost = 2×800 = $1,600. The cost-derived threshold beats the naive default by clearing a much lower bar -- because a missed fraud allegation is 20× as costly as a wrongly-flagged review, the optimal rule flags aggressively.

Teach-back: why does a 20:1 cost ratio push the optimal threshold so far below 0.5?

CAREER PRACTICE

Interview questions

Conceptual: why generalize weighting and thresholding into a cost matrix?
Both class weighting and threshold moving implicitly encode an assumption about relative costs -- a cost matrix makes that assumption explicit and lets it be set from real business input instead of derived from the data's own class frequencies.
Mathematical: derive t* from expected costs.
E[cost|predict positive]=(1−p)C(FP); E[cost|predict negative]=p·C(FN). Predicting positive is cheaper iff p > C(FP)/(C(FP)+C(FN)) = t*.
Coding: implement optimal_threshold and confusion_and_cost.
Section 12 gives the full implementation, reproducing this concept's own Section 10 numbers via assert statements.
Debugging: a team assumes "balanced" is cost-optimal. What's the first thing to check?
Whether the actual dollar costs of a false negative and false positive match the inverse class-frequency ratio "balanced" silently assumes -- if they don't, a custom cost matrix and t* should replace it.
System design: how would you keep a deployed cost-derived threshold current as business costs change?
Recompute t* from the updated cost matrix and push it as a config update -- zero retraining required, echoing Concept 04's own production-implications point.
