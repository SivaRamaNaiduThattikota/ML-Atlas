MODULE 05 · CONCEPT 07

Same problem.
A tool with no classical analogue.

Concepts 01-06 built every fix and evaluation caveat on classical ML's own territory -- a single fold, a fixed feature set, one training pass. This concept asks which of those fixes actually transfer to deep learning at all. Resampling and threshold moving still apply conceptually, but naive oversampling at deep-learning scale can mean the same minority example repeats many times within a single mini-batch. Class weighting transfers directly, unchanged. But deep learning also has a fix with no classical-ML analogue: focal loss (Lin et al., 2017), which down-weights already-easy examples automatically, per example, by a factor of (1-p_t)^γ -- not by a fixed per-class multiplier the way Concept 03's weighting does. And at γ=0, focal loss collapses EXACTLY onto Concept 03's own class weighting -- an exact algebraic identity, verified on this lesson's own numbers, not an approximation.

01 · CONCEPT FIRST

A per-example fix with no classical-ML analogue

TRANSFERS DIRECTLY

Class weighting (Concept 03) -- a per-CLASS multiplier, unchanged by scale. Threshold moving (Concept 04) -- architecture-agnostic, applies to any model's output probability.

DOES NOT EXIST IN CLASSICAL ML

Focal loss -- a per-EXAMPLE multiplier, (1-p_t)^γ, that automatically down-weights whichever rows the model already classifies confidently, regardless of class.

First memory: class weighting reweights by WHICH CLASS a row belongs to; focal loss reweights by HOW EASY that specific row already is.
02 · WHY IT EXISTS

A fixed per-class weight can't tell easy rows from hard ones

Class weighting (Concept 03) gives every minority row the identical multiplier, whether the model already gets it right easily or struggles with it. At deep-learning scale, with millions of examples per epoch, most rows -- majority AND minority -- become easy long before training ends. Focal loss exists to keep training focused on the rows that are still hard, automatically, without hand-picking a class-level ratio.

03 · CONCRETE EXAMPLE

Same matched pair, a very different multiplier

Reusing Concept 03's own matched pair: M1 (minority, y=1, p=0.35) and J1 (majority, y=0, p=0.65) -- both equally wrong, unweighted loss 1.0498 each. Plain focal loss (γ=2, α=1) gives BOTH the identical value, 0.4435 each -- because focal loss doesn't know or care which class a row belongs to; it only looks at how wrong the prediction was.

04 · TECHNICAL MECHANISM

γ=0 recovers class weighting, exactly

FL(p_t) = −α·(1−p_t)^γ·log(p_t). At γ=0, (1−p_t)^0 = 1 for any row, so FL(p_t) = −α·log(p_t) -- exactly Concept 03's own weighted cross-entropy. Plugging in Concept 03's own weight w_minority=2.2422 as α for M1 gives focal loss = 2.3539 -- the identical number Concept 03 already computed. This is an exact identity, not an approximation.

06 · IMPORTANT DISTINCTIONS

Per-class vs. per-example, and a real batch-scale wrinkle

PairingThe real difference
Focal loss vs. class weighting (Concept 03)Per-EXAMPLE multiplier based on current difficulty vs. a fixed per-CLASS constant -- the single most important contrast in this concept
Resampling (Concept 02) at classical vs. DL scaleSame duplication idea, but at DL scale with small mini-batches, the SAME minority row can recur multiple times within one batch, not just across an epoch
Threshold moving (Concept 04) at classical vs. DL scaleUnchanged -- it's architecture-agnostic, applied entirely after training, to any model's output probability
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Focal loss is just class weighting with a fancier name."

False -- class weighting is a special case of focal loss (γ=0), but γ>0 adds a genuinely new per-example mechanism class weighting cannot express.

"Threshold moving needs to be redone for deep learning."

False -- it's architecture-agnostic and applies identically post-hoc to any model's probability output.

"Oversampling works identically at any batch size."

False -- at small mini-batch sizes, the same minority row can appear multiple times within a single batch, not just across an epoch.

INTUITION

A tutor who stops repeating problems you've already mastered

Class weighting is like telling a tutor "spend more time on word problems in general" -- a fixed instruction regardless of which specific word problem a student already nailed. Focal loss is a tutor who notices, problem by problem, which ones the student still gets wrong, and focuses there automatically.

06
MECHANISM

Two independent knobs, one automatic per-row factor

α — WHICH CLASS

A fixed per-class multiplier, identical in spirit to Concept 03's w_c.

γ — HOW HARD THIS ROW STILL IS

(1−p_t)^γ shrinks automatically as p_t rises -- no class lookup needed, recomputed fresh every forward pass.

09
MATHEMATICS

The formula, and the γ=0 identity

FL(p_t) = −α·(1−p_t)^γ·log(p_t)
At γ=0: (1−p_t)^0 = 1 for any row ⟹ FL(p_t) = −α·log(p_t) — exactly Concept 03's weighted cross-entropy

Cited from Lin et al. (2017), "Focal Loss for Dense Object Detection" -- γ=2 is the paper's own reported best-performing value, paired with α=0.25 in their real experiments. Deriving the gradient of focal loss is out of scope here, cited forward to Module 09.

10
WORKED EXAMPLE

Two down-weighting factors, one formula, and an exact identity

Step 1 -- plain focal loss is class-blind. M1 (minority, y=1, p=0.35) and J1 (majority, y=0, p=0.65) -- both equally wrong. Plain cross-entropy: both 1.0498221244986778 (Concept 03's own number, reused). Focal loss (γ=2, α=1): both give the IDENTICAL 0.44354984760069144 -- focal loss with α=1 doesn't distinguish class at all, only p_t.

Step 2 -- automatic down-weighting scales with how easy a row already is. An easy, already-confident-correct row (p=0.95, y=1): CE=0.05129329438755058, focal(γ=2,α=1)=0.00012823323596887666 -- CE/focal = exactly 400 (since (1−0.95)²=0.0025, 1/0.0025=400). For the harder M1 row: CE/focal = 2.3668639053254434 (since (1−0.35)²=0.4225, 1/0.4225=2.3669) -- a much smaller down-weighting, because M1 is still hard.

Step 3 -- the γ=0 identity, proved exactly. focal(M1, γ=0, α=1) = 1.0498221244986778 = plain CE(M1) exactly. focal(M1, γ=0, α=2.242152466367713) = 2.3538612656921027 = Concept 03's own weighted M1 loss, to full float precision -- not approximately equal, IDENTICAL.

Step 4 -- combining α and γ preserves Concept 03's own ratio. focal(M1, γ=2, α=w_minority=2.242152466367713) = 0.9945063847549135. focal(J1, γ=2, α=w_majority=0.6435006435006435) = 0.2854246123556573. Ratio = 3.4843049327354256 -- the identical class ratio Concepts 01/03 already established, even with γ=2's extra per-example scaling layered on top.

Verification method: every number above was computed via an executed Node.js script using a focal(p, y, gamma, alpha) function, independently re-verified via a second, separately-written script computing p_t and each factor ((1−p_t)^γ, −log(p_t)) as separate intermediate steps rather than inline -- both matched exactly on every value. The Lin et al. (2017) paper's own γ=2/α=0.25 defaults were confirmed by direct inspection of the paper's full text via the ar5iv mirror (HTTP 200, "γ=2 to work best in our experiments," "α=0.25" both present verbatim).

11
CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

Dense object detection (focal loss's own origin)

Millions of easy background examples versus a handful of hard object examples per image.

BOUNDARY CASE

γ=0

Collapses focal loss to exactly Concept 03's class weighting -- recovering the classical fix as a special case of the DL-only one.

MISTAKE TO AVOID

Treating focal loss as a drop-in replacement for class weighting

γ>0 changes training dynamics in a way a fixed per-class weight cannot replicate -- it isn't a pure substitute.

12
CODE

Focal loss and the γ=0 identity, from scratch

PYTHON · NO LIBRARIES 
import math

def p_t(p, y):
    return p if y == 1 else 1 - p

def cross_entropy(p, y):
    return -math.log(p_t(p, y))

def focal_loss(p, y, gamma, alpha):
    pt = p_t(p, y)
    return -alpha * (1 - pt) ** gamma * math.log(pt)

# Reproduces this concept's own Section 10 result
M1, J1 = (0.35, 1), (0.65, 0)
assert round(focal_loss(*M1, gamma=2, alpha=1), 4) == round(focal_loss(*J1, gamma=2, alpha=1), 4)

# The gamma=0 identity: focal loss with alpha=w_minority equals Concept 03's weighted CE
w_min = 1000 / (2 * 223)
assert round(focal_loss(*M1, gamma=0, alpha=w_min), 4) == 2.3539
assert round(w_min * cross_entropy(*M1), 4) == 2.3539

The real paper, and the DL-only training context

No classical tabular-ML library (scikit-learn's gradient boosting, logistic regression) exposes an equivalent per-example focusing parameter -- confirming this concept's own claim that focal loss has no classical-ML analogue.

REALITY

Production implications

  • Choosing focal loss's γ and α is itself a tuning decision, distinct from choosing whether to resample or threshold-move -- document all of them together, not just one.
  • A model architecture switch (classical → deep learning) can reopen which imbalance fixes are even available, not just how well they work.
19
RECALL

Knowledge check

Why does a fixed per-class weight fail to distinguish an easy row from a hard one?
A class weight is looked up once per class and applied identically to every row in that class -- it has no way to know how confidently correct any individual row's prediction already is.
Why is the easy example's down-weighting factor (400×) so much larger than the hard example's (2.3669×)?
The down-weighting factor is 1/(1−p_t)^γ. The easy example's p_t=0.95 makes (1−p_t) tiny (0.05), so its power (0.0025 at γ=2) is tiny too, giving a huge down-weighting factor. The hard example's p_t=0.35 makes (1−p_t)=0.65, a much larger power (0.4225), so its down-weighting stays modest.
Why does threshold moving transfer to deep learning completely unchanged?
It operates entirely after training on a model's output probability, with no reference to the model's internal architecture -- the same rule applies whether the probability came from logistic regression, gradient boosting, or a neural network.

23
CAREER PRACTICE

Interview questions

Conceptual: why doesn't class weighting have a per-example equivalent in classical gradient boosting?
Classical tabular models like gradient boosting fit on a fixed feature set with sample weights set once before or during training, not recomputed per forward pass the way a neural network's loss is -- there's no repeated per-example difficulty signal to plug an (1−p_t)^γ term into the same way.
Mathematical: prove the γ=0 identity.
FL(p_t)=−α(1−p_t)^γlog(p_t). At γ=0, (1−p_t)^0=1 for any p_t in (0,1), so FL(p_t)=−α·log(p_t), which is exactly α times the plain cross-entropy loss -- identical to Concept 03's weighted loss when α equals that concept's own class weight.
Coding: implement focal_loss and verify the gamma=0 identity.
Section 12 gives the full implementation, with asserts reproducing this concept's own Section 10 numbers.
Debugging: a team switches from gradient boosting to a neural network and reuses their old class_weight='balanced' setting. What's the first thing to reconsider?
Whether focal loss (or another per-example mechanism now available) might serve the same imbalance-fixing goal better than a straight port of the classical per-class weight, since deep learning training now recomputes a difficulty signal every forward pass that classical training never had access to.
System design: how would you choose between class weighting and focal loss for a new deep-learning model?
Start with class weighting (γ=0 case) as a simple baseline, then check whether training plateaus because most examples have become easy while a minority stay hard -- if so, introduce γ>0 and tune it alongside α, rather than assuming one always beats the other.
