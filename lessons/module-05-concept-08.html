MODULE 05 · CONCEPT 08

Ship the fix.
Then the world moves.

Concepts 01-07 each chose and evaluated an imbalance fix once -- on one fold, against one cost matrix, at one point in time. This concept asks a question none of them asked: what happens to that same fix months after it ships, once the real world it was built against stops holding still? CFPB deployed Concept 05's own threshold, t*=C(FP)/(C(FP)+C(FN))=50/550=1/11≈0.0909, and it has stayed live, unchanged, for 18 months. A new compliance-review requirement then quietly raises the real cost of a wrongly flagged non-relief case from $50 to $200 -- nobody revisits the deployed number when this happens. The true cost-optimal threshold today is 200/700=2/7≈0.2857, but the system is still running at 0.0909. On this concept's own fixed 10-row set, staying stale costs $1,000 versus $200 if the threshold had been recomputed the moment the real cost changed -- a 5x gap, purely from a decision nobody revisited, with the model itself untouched throughout.

01 · CONCEPT FIRST

Choosing a fix, versus living with it

CONCEPTS 01-07

Choose and evaluate an imbalance fix -- resample, weight, threshold-move, cost-optimize -- once, on one fold, against one cost matrix.

THIS CONCEPT

What happens to that same fix months later, once the real costs or the real class balance it was built against no longer hold still.

First memory: a threshold or cost matrix is a snapshot of one moment, not a permanent fact -- the moment can pass while the number stays exactly where it was set.
02 · WHY IT EXISTS

A number derived from costs is only correct for those costs

Concept 05's t*=C(FP)/(C(FP)+C(FN)) is only ever correct for the specific dollar figures plugged into it the day it was computed. If the real cost of a false positive or false negative moves after deployment -- or if the real class balance shifts -- the old threshold quietly stops being optimal. Nothing in the deployed system flags that on its own; the number simply keeps running, unaware anything changed.

03 · CONCRETE EXAMPLE

0.0909, eighteen months later

CFPB deployed Concept 05's threshold, t*≈0.0909, derived from C(FN)=$500 and C(FP)=$50. Eighteen months pass with no review. A compliance-review requirement then raises the real cost of a wrongly flagged non-relief case to $200 -- the true cost-optimal threshold today is 200/700=2/7≈0.2857, but production is still running at 0.0909. On a fixed 10-row set, staying at the stale threshold costs $1,000 today; recomputing to 0.2857 would cost only $200 -- a 5x gap from a number nobody revisited.

04 · TECHNICAL MECHANISM

Three ways a shipped fix can go stale

1. Cost/threshold staleness -- t*=C(FP)/(C(FP)+C(FN)) stops being optimal the moment either real dollar cost drifts, and nothing detects that automatically; Module 17 ("Drift & monitoring") owns the actual detection statistics, not this concept. 2. Documentation/reproduction discipline -- Concept 02's fold-scoped resampling rule and Concept 03's exact balanced-weight formula (w_c=n/(2·n_c)) must be RE-RUN on new data at retraining time, not reused as hardcoded historical numbers. 3. Class-balance drift -- Concept 05 already proved "balanced" weighting implicitly sets the threshold to the minority base rate; if that base rate moves, "balanced" silently means something different than it did on deployment day.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Once we pick a threshold, it's set forever."

False -- the worked $1,000-vs-$200 gap exists purely because a correct threshold was left frozen while its underlying costs moved.

"Balanced class weighting adapts to drift automatically."

False -- the weights must be recomputed from the current class balance using Concept 03's own formula; they do not self-update as the data shifts.

"Cost drift and class-balance drift are the same failure."

False -- either one alone can invalidate a deployed threshold, independently of the other.

01
ORIENTATION

The first concept in this module to look past deployment day

Concepts 01-07 each built and checked an imbalance fix at a single point in time -- one fold, one cost matrix, one training pass. This concept looks past that moment: it covers what can happen to ANY of those fixes -- a threshold, a weight ratio, a resampling recipe -- once the real world they were built against keeps moving. It is not a new fix; it is what happens to the old ones.

04
INTUITION

A thermostat set once, for a house that keeps changing

A thermostat set once for a house's old insulation keeps running at that same setting even after the insulation is upgraded -- the setting doesn't know anything changed, and stays wrong until someone resets it. A deployed threshold or weight ratio behaves the same way: it was correct for the costs or class balance that existed the day it was computed, and it will happily keep running long after those numbers move, with nothing forcing a reset.

Analogy boundaryThe thermostat picture explains why a frozen number can silently stop being right. It doesn't capture the exact cost-ratio arithmetic -- Sections 09/10 give that precisely.

09
MATHEMATICS

t* is a function of two inputs that can each move independently

t*(C_FP,C_FN) = C_FP / (C_FP+C_FN)
A threshold computed once from (C_FP,C_FN) is only valid for that exact pair -- if either input moves after deployment, t* recomputed against TODAY's pair is a different number, even though the formula itself hasn't changed at all.

Nothing here changes Concept 05's derivation -- the formula is identical. What's new is treating (C_FP,C_FN) as values that can move AFTER the formula was applied, not just inputs chosen once at design time.

10
WORKED EXAMPLE

The frozen threshold, and what it costs when real costs drift

Step 1 -- the frozen threshold. CFPB deployed t*_old=C(FP)/(C(FP)+C(FN))=50/(50+500)=50/550=1/11≈0.0909, derived from Concept 05's own cost matrix (C(FN)=$500, C(FP)=$50). That threshold has stayed deployed, unchanged, for 18 months.

Step 2 -- the drift. A new compliance-review requirement raises the real cost of a wrongly flagged non-relief case from $50 to $200 (extra staff review time triggered by every false flag); C(FN) stays $500. Nobody revisits the deployed threshold when this happens. The true cost-optimal threshold today is t*_new=200/(200+500)=200/700=2/7≈0.2857 -- but production is still running at the stale 0.0909.

Step 3 -- the cost, on a fixed 10-row set. Positive rows (label=1): 0.90, 0.70, 0.30 (all comfortably above both thresholds -- no false negatives appear at either, isolating the false-positive-cost consequence of staleness specifically). Negative rows (label=0): 0.50, 0.20, 0.18, 0.15, 0.12, 0.05, 0.02. At the STALE threshold (0.0909), under today's real costs ($500/$200): predicted positive={0.90,0.70,0.30,0.50,0.20,0.18,0.15,0.12} → TP=3, FP=5, FN=0, TN=2 → cost=5×200=$1,000. At the RECOMPUTED threshold (2/7≈0.2857), under the same today's costs: predicted positive={0.90,0.70,0.30,0.50} → TP=3, FP=1, FN=0, TN=6 → cost=1×200=$200.

Step 4 -- the gap, and the boundary check. Staying at the stale threshold costs $1,000 versus $200 if recomputed the moment the false-positive cost changed -- 5x more, purely from not revisiting a number that was only ever correct for the cost structure that existed the day it was derived. At zero drift (C(FP) still $50), both thresholds coincide exactly (0.0909=0.0909) and the gap is exactly $0 -- the clean boundary case showing this is a staleness effect, not an artifact of the toy set.

Secondary, illustrative point -- reproducing a technique, not a number. Concept 03's exact "balanced" weights (w_minority=2.242152466367713, w_majority=0.6435006435006435, ratio 3.4843049327354256) were computed from the 223/777 split via w_c=n/(2·n_c). If CFPB retrains later on a hypothetical retrain split where the relief-granted share has moved to 260/740, applying that SAME documented formula (not the old hardcoded constants) gives w_minority=1000/(2×260)=1.9230769230769231, w_majority=1000/(2×740)=0.6756756756756757, a new ratio of 2.8461538461538463 -- correctly reflecting the new imbalance. Reusing the stale 3.4843 ratio after the data shifted would silently reintroduce the imbalance the fix was meant to remove.

CONCRETE USE

A clean fit, a boundary case, and a mistake

CLEAN FIT

A regulatory or operational cost change

A new compliance requirement changes the real cost of a false positive, but nobody propagates that change to the deployed threshold.

BOUNDARY CASE

C(FP) drifts back to exactly $50

Gap is exactly $0 -- recovering "no staleness cost when nothing actually drifted."

MISTAKE TO AVOID

Assuming "balanced" adapts on its own

Balanced class weighting must be recomputed from the current class balance -- it does not adapt to a new split automatically.

12
CODE

The frozen-vs-live cost table, from scratch

PYTHON · NO LIBRARIES 
rows = [
    (0.90, 1), (0.70, 1), (0.30, 1),
    (0.50, 0), (0.20, 0), (0.18, 0), (0.15, 0),
    (0.12, 0), (0.05, 0), (0.02, 0),
]

def confusion_and_cost(rows, threshold, c_fn, c_fp):
    tp = fp = fn = tn = 0
    for score, y in rows:
        pred = 1 if score >= threshold else 0
        if pred == 1 and y == 1: tp += 1
        elif pred == 1 and y == 0: fp += 1
        elif pred == 0 and y == 1: fn += 1
        else: tn += 1
    return tp, fp, fn, tn, fn * c_fn + fp * c_fp

FROZEN_T = 1 / 11          # Concept 05's deployed threshold, ≈0.0909
LIVE_T = 200 / 700         # today's true optimum once C(FP) drifts to $200

frozen = confusion_and_cost(rows, FROZEN_T, 500, 200)
live = confusion_and_cost(rows, LIVE_T, 500, 200)

assert frozen == (3, 5, 0, 2, 1000)
assert live == (3, 1, 0, 6, 200)
assert frozen[-1] - live[-1] == 800
assert round(frozen[-1] / live[-1], 1) == 5.0

# Boundary case: no drift, both thresholds coincide, gap is exactly zero
no_drift_frozen = confusion_and_cost(rows, FROZEN_T, 500, 50)
no_drift_live = confusion_and_cost(rows, FROZEN_T, 500, 50)
assert no_drift_frozen[-1] - no_drift_live[-1] == 0

DIAGNOSIS

Failure modes

SILENTLY DRIFTED COST STRUCTURE

Nobody re-derives t* after a cost changes

The deployed threshold keeps running at its original value while the real cost it was optimized for has already moved -- the $1,000-vs-$200 gap.

18
REALITY

Production implications

  • Assign a named owner and a recompute cadence to every deployed threshold or weight ratio -- "we set it once" is not a maintenance plan.
  • Version-control the exact resampling or weighting RECIPE, not just the resulting numbers, so it can be correctly re-run on new data rather than reused verbatim.
  • Treat "ship the fix" as day one of an ongoing responsibility, not a final answer -- Module 17's drift-detection statistics are the forward-referenced mechanism for catching this automatically; nothing here builds that monitoring.
19
RECALL

Knowledge check

Why does the $1,000-vs-$200 gap prove a threshold isn't set forever once chosen?
The threshold itself never changed -- only the real cost of a false positive did. Because the threshold stayed frozen at a number optimized for the old cost, it kept making the same predictions on rows whose true cost had already risen, producing $800 more expected cost than recomputing would have.
Why doesn't "balanced" class weighting adapt to a new class balance on its own?
w_c=n/(2·n_c) is computed from whatever n_c values are plugged in at the time it's run. If nobody re-runs it on the new split, the old weights simply keep being used -- the formula doesn't monitor the data or recompute itself.
What happens at the boundary case where C(FP) drifts back to exactly $50?
The frozen threshold (0.0909) and the live-recomputed threshold coincide exactly, since $50 is the cost that produced 0.0909 in the first place -- the gap is exactly $0, confirming this is a genuine staleness effect and not an artifact of the toy data.

CAREER PRACTICE

Interview questions

Conceptual: why can a cost-optimal threshold become wrong without the model changing at all?
t* is a function of the real dollar costs (C_FP,C_FN), not of the model's parameters. If those real costs move after deployment, the formula's output for TODAY's costs differs from the frozen value the system is still running, even though nothing about the trained model changed.
Mathematical: derive the direction of the gap as C_FP rises, holding C_FN fixed.
t*=C_FP/(C_FP+C_FN) is increasing in C_FP, so as C_FP rises, the true optimal threshold rises too, predicting positive on fewer rows. A threshold frozen at the OLD, lower t* keeps predicting positive on rows that are now more expensive to falsely flag, so the frozen threshold's cost grows relative to the live one -- the gap widens monotonically as C_FP drift widens, exactly as Section 10's sweep shows.
Coding: implement the frozen-vs-live cost comparison.
Section 12 gives the full implementation, with asserts reproducing this concept's own Section 10 numbers and the zero-drift boundary case.
Debugging: a team retrains and reuses the old class_weight numbers verbatim. What's wrong?
Concept 03's weights were computed from the ORIGINAL class split via w_c=n/(2·n_c). If the split has since moved, the old numbers no longer reflect the current imbalance -- the formula needs to be re-run on the new n_c values, not copied forward from the last run.
System design: how would you operationalize revisiting a deployed threshold, without yet building Module 17's actual monitoring?
Assign a named owner and a fixed review cadence tied to known cost-changing events (e.g. a compliance policy update), and require the cost matrix itself -- not just the resulting threshold -- to be version-controlled so a review can recompute t* directly from documented inputs rather than guessing at the original numbers.
