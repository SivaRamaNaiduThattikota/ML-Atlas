MODULE 06 · CONCEPT 04

A straight line can't be a probability.
The sigmoid is the fix.

Concepts 01-03 predicted a continuous number, case_age_days, scored by SSE -- and that output could land anywhere on the real line, -50 or +900, which is fine for a day-count but meaningless as a probability. This concept predicts a class instead: relief_granted, granted or not. The mechanism keeps Concepts 01-03's own linear combination of features, z=w0+w1x1+w2x2, but feeds it through one new squashing step, the sigmoid sigma(z)=1/(1+e^-z), so the output is always strictly between 0 and 1 -- never touching either endpoint, no matter how extreme z gets. Five fresh CFPB rows (prior_contact_attempts, satisfaction_score) under already-fitted weights w0=-4, w1=1.5, w2=-0.5 give a mean binary cross-entropy loss of 0.3455 across the five rows, with one row alone responsible for about 76% of that total -- the row the model got confidently wrong.

01 · CONCEPT FIRST

Same linear combination, one new squashing step

LINEAR REGRESSION (Concepts 01-03)

Output is any real number, scored by SSE. Nothing stops it from being -50 or +900.

LOGISTIC REGRESSION (this concept)

Output is squashed into (0,1) by sigma(z)=1/(1+e^-z), read as a probability, scored by cross-entropy (cited from Module 05 Concept 03).

First memory: sigma(z) is always strictly between 0 and 1, never touching either endpoint, no matter how extreme z gets.
02 · WHY IT EXISTS

An unbounded number can't be read as a probability

relief_granted is a class -- granted or not -- not a number. Concepts 01-03's unbounded linear output can't be read as a probability directly: it could come out as -50 or +900, and neither means anything as "how likely is relief." Logistic regression keeps the exact same "linear combination of features" mechanism Concepts 01-03 already built, and adds one squashing step so the output is a valid probability, in the sense Module 02 Concept 06 already defined -- a number between 0 and 1 that is supposed to mean something about likelihood, cited directly here rather than re-explained.

04 · TECHNICAL MECHANISM

z first, then squash

The linear score z uses the exact same shape Concepts 01-03 already used -- a weighted sum of the features plus an intercept. What changes is what happens next: instead of reading z directly as the output, it feeds into the sigmoid.

z = w0 + w1·x1 + w2·x2 (same linear-combination shape as Concepts 01-03)
sigma(z) = 1 / (1 + e^-z) (the new squashing step)

The weights here (w0=-4, w1=1.5, w2=-0.5) are stated as already fitted -- given, not derived from these five rows. The procedure that would actually find those weights from data (maximum likelihood / gradient descent) is out of scope for this concept.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"sigma(z) landing in (0,1) means it's already calibrated."

No -- (0,1) is a mathematical guarantee of the sigmoid's shape, not a promise about accuracy. Whether the number is trustworthy is Module 02 Concept 06's own, separate question.

"Squash each raw feature individually, then combine."

No -- the sigmoid squashes the single combined linear score z, after the weighted sum is taken, never the raw inputs one at a time.

"Sigmoid and softmax are the same thing."

Not covered here -- softmax generalizes this idea to more than two classes, and is named forward only to Concept 09.

Explain in one sentence why sigma(z) can equal 0.5 exactly but never exactly 0 or 1

At z=0, e^-z=1, so sigma(0)=1/(1+1)=0.5 exactly; but e^-z is strictly positive for every finite z, so 1/(1+e^-z) can get arbitrarily close to 0 or 1 without ever reaching either.

04
INTUITION

A dimmer switch, not an on/off switch

z is how hard you push the switch. sigma(z) is how bright the bulb gets -- capped between fully off and fully on, but never quite reaching either, no matter how hard you push. Push very hard in one direction and the bulb gets very close to fully on; push very hard the other way and it gets very close to fully off. It just never actually clicks all the way to either extreme.

Analogy boundaryThe dimmer-switch picture explains WHAT sigma does to a raw score -- squashes it toward, but never onto, either extreme. It doesn't by itself prove WHY that specific functional form was chosen; that's the symmetry and derivative identities made precise in Section 09.

MATHEMATICS

The sigmoid's formal properties, and the loss

z = w^T x + b
sigma(z) = 1 / (1 + e^-z) ; range (0,1), exclusive
sigma(-z) = 1 - sigma(z) (symmetry)
sigma'(z) = sigma(z)·(1 - sigma(z)) (derivative)
BCE = -[y·ln(p) + (1-y)·ln(1-p)] (cited verbatim from Module 05 Concept 03)

CONCRETE USE

A clean case, a boundary case, and a mistake

CLEAN CASE

Rows A and E -- confident and correct

A: sigma(z)=0.0110, y=0, loss=0.0110. E: sigma(z)=0.9890, y=1, loss=0.0110. Both sit near the sigmoid's flat ends, and both are on the correct side.

BOUNDARY CASE

z exactly 0 -- maximally uncertain

At z=0, sigma(z)=0.5 exactly -- the sigmoid's own midpoint. None of the five worked rows land exactly here, but it's the point where the model is offering no lean either way. Not framed as a decision boundary -- that term belongs to Concept 06.

MISTAKE TO AVOID

Treating sigma(z) as automatically calibrated

sigma(z) in (0,1) is a mathematical guarantee of the sigmoid's own shape, not evidence that the number is trustworthy as a real-world probability -- corrected via Module 02 Concept 06's own, separate calibration check.

CODE

An overflow-safe sigmoid, and all five rows

PYTHON · NO LIBRARIES 
import math

# Naive 1/(1+math.exp(-z)) can overflow for very negative z, since
# exp(-z) grows huge. The sign-split form below avoids that by only
# ever exponentiating a non-positive number.
def sigmoid(z):
    if z >= 0:
        return 1.0 / (1.0 + math.exp(-z))
    ez = math.exp(z)
    return ez / (1.0 + ez)

def bce(p, y):
    return -(y * math.log(p) + (1 - y) * math.log(1 - p))

W0, W1, W2 = -4.0, 1.5, -0.5
rows = [
    ("A", 1, 4, 0),
    ("B", 2, 3, 0),
    ("C", 3, 3, 1),
    ("D", 4, 2, 1),
    ("E", 6, 1, 1),
]

losses = []
for label, x1, x2, y in rows:
    z = W0 + W1 * x1 + W2 * x2
    p = sigmoid(z)
    loss = bce(p, y)
    losses.append(loss)
    print(label, round(z, 4), round(p, 4), round(loss, 4))

mean_bce = sum(losses) / len(losses)
assert round(mean_bce, 4) == 0.3455

# Symmetry identity: sigma(-z) == 1 - sigma(z).
assert round(sigmoid(1.0), 6) == round(1 - sigmoid(-1.0), 6)

DIAGNOSIS

Where the sigmoid itself goes wrong

PERFECTLY SEPARABLE DATA

Weights driven toward infinity

If a feature perfectly separates the two classes, the fitting procedure can push its weight toward infinity, sharpening the sigmoid into a near-step function -- a well-known, citable fact, stated conceptually here, mitigated by regularization (Concept 03, named).

NAIVE OVERFLOW

exp(-z) for very negative z

A naive 1/(1+e^-z) implementation can overflow computing e^-z when z is very negative -- fixed by the sign-split implementation in Section 12.

MISTAKING (0,1) FOR CALIBRATED

The recurring beginner error

Landing in (0,1) is a shape guarantee, not an accuracy guarantee -- Module 02 Concept 06's own, separate check is what actually verifies trustworthiness.

CAREER PRACTICE

Interview questions

Conceptual: why squash the linear score at all?
An unbounded real number can't be read as a probability -- it could land anywhere from -infinity to +infinity. The sigmoid guarantees the output is always strictly between 0 and 1, so it can be interpreted as "how likely," which a raw linear score never can be on its own.
Mathematical: derive sigma'(z) from the quotient rule.
sigma(z)=1/(1+e^-z). Let u=1, v=1+e^-z; the quotient rule gives sigma'(z)=(u'v-uv')/v^2=(0·v-1·(-e^-z))/(1+e^-z)^2=e^-z/(1+e^-z)^2. Rewriting e^-z=(1+e^-z)-1 and factoring gives sigma'(z)=sigma(z)·(1-sigma(z)) exactly.
Coding: implement an overflow-safe sigmoid.
Section 12 gives the full implementation -- split on the sign of z, so the code only ever computes e raised to a non-positive power, avoiding the overflow a naive 1/(1+math.exp(-z)) hits for very negative z.
System design: serving predict_proba for CFPB's relief-risk model.
Use the overflow-safe sigmoid at serving time, monitor the predicted-probability distribution for drift (Module 17, named forward), and check calibration (Module 02 Concept 06) before any threshold or business rule is built on top of the raw probability.
Production scenario: predict_proba comes back looking suspiciously confident -- what do you check first?
Check calibration first (Module 02 Concept 06, named) -- a reliability diagram or Brier score will show whether "90% confident" predictions are actually right about 90% of the time. Landing in (0,1) alone says nothing about that.
