MODULE 06 · CONCEPT 08

Same binary question. Asked K times, or K(K-1)/2 times.
The two answers don't have to agree.

Concepts 04-07 all built machinery for exactly two classes -- the sigmoid, the odds ratio, the boundary line, the Bayes'-rule Gaussian split. This concept doesn't invent a new mechanism for K>2 classes; it reuses what already exists, more than once. One-vs-rest (OvR) trains K classifiers, each asking "is it me, or everyone else," and predicts whichever gives the highest score. One-vs-one (OvO) trains one classifier per PAIR of classes -- K(K-1)/2 of them -- and predicts by majority vote. On a genuine 3-class CFPB example, the two schemes land on opposite predictions at the exact same point.

PROGRESSIVE BEGINNER CORE

Reuse the binary question. Combine the answers.

Every model built so far in this module answers exactly one question: "is it class 0 or class 1?" Real problems often have three or more outcomes. Rather than invent a new algorithm, this concept asks the SAME binary question several times and combines the results two different ways.

01 · CONCEPT FIRST

Two ways to combine already-binary classifiers

ONE-VS-REST (OvR)

Train K classifiers, each answering "is it me, or everyone else." Predict whichever classifier scores highest -- argmax.

ONE-VS-ONE (OvO)

Train one classifier per PAIR of classes -- K(K-1)/2 total. Each casts a vote; predict the class with the most votes -- majority vote.

First memory: Concepts 04-07 all answered a two-way question once. This concept doesn't invent a new mechanism for K>2 classes -- it asks the SAME binary question K or K(K-1)/2 times and combines the answers.
02 · WHY IT EXISTS

Real targets often have more than two outcomes

Concepts 04-07's own sigmoid, odds, boundary and Gaussian machinery were all built assuming exactly two classes. But this module's own CFPB target itself, company_response, genuinely has more than two outcomes. Rather than derive a brand-new algorithm from scratch, OvR and OvO both reuse the binary machinery already built, more than once, and combine the results.

04 · TECHNICAL MECHANISM

Argmax vs. majority vote, cited from scikit-learn's own documentation

OvR (scikit-learn, Multiclass classification): "fitting one classifier per class... only n_classes classifiers are needed... the most commonly used strategy and is a fair default choice." Predict whichever classifier's own score z_k=w0^(k)+w1^(k)x1+w2^(k)x2 is highest. OvO (same page): "constructs one classifier per pair of classes. At prediction time, the class which received the most votes is selected... requires n_classes*(n_classes-1)/2 classifiers." At x1=3, x2=5: OvR's three scores are z0=0, z1=1.0, z2=1.9 -- class 2 wins by argmax. OvO's three pairwise scores are z01=-0.8 (votes class 0), z02=-0.4 (votes class 0), z12=-0.2 (votes class 1) -- class 0 wins 2 votes to 1. The two schemes disagree: class 2 vs. class 0.

05 · ARCHITECTURE / FLOW

Combining existing machinery, not building new machinery

Concept 07 — a boundary derived a different way, still exactly 2 classes→ This concept — the same binary machinery, reused K or K(K-1)/2 times, combined by argmax or majority vote→ Concept 09 — softmax, one model instead of many classifiers, named forward

06 · IMPORTANT DISTINCTIONS

OvR vs. OvO, and "extension" vs. "genuinely multiclass"

PairingThe real difference
OvR vs. OvOOvR needs only K classifiers (linear cost) but each one's own score scale can differ from the others'. OvO needs K(K-1)/2 classifiers (quadratic cost), but each one solves an easier, more balanced sub-problem.
"Extension" (this concept) vs. "genuinely multiclass" (Concept 09)OvR/OvO combine several already-binary classifiers after the fact. Softmax (Concept 09, named forward only) is one single model that handles all K classes at once -- no combination step at all.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"OvO must be strictly better, since it trains more classifiers."

False. OvO's cost grows quadratically in K for a benefit -- easier per-classifier sub-problems -- that doesn't always translate into a better final prediction.

"OvR and OvO, trained on the same data, must always predict the same class."

False, demonstrated directly: at x1=3, x2=5, OvR predicts class 2 and OvO predicts class 0, using the exact same underlying weights.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

State OvR's and OvO's classifier-count formulas

OvR needs K classifiers. OvO needs K(K-1)/2 -- at K=3 the two counts happen to coincide (3=3), the only K where that's true.

Classify x1=3, x2=5 under both without recomputing

OvR: z=[0, 1.0, 1.9], argmax=class 2. OvO: votes=[2, 1, 0], majority=class 0. The two schemes DISAGREE.

Explain why OvR's own scores aren't directly comparable across classifiers

Each classifier is trained on a different, typically unbalanced split (its own class vs. everyone else), so nothing guarantees the resulting scores sit on the same scale.

04
INTUITION

K separate committees, or a round-robin tournament

OvR is like K separate committees, each asked only "is it me, or not" -- whichever committee answers most confidently wins. OvO is like a round-robin tournament among every pair of classes -- whichever class wins the most head-to-head matches takes it.

Analogy boundaryBoth analogies explain the MECHANISM correctly -- unlike Concept 07's density-crossing analogy, which needed an algebra caveat. But neither analogy by itself explains why the two schemes can disagree; that's Section 10's worked example.

06
MECHANISM

Two steps, traced once for OvR and once for OvO

STEP 1 -- SCORE EVERY CLASSIFIER

OvR: three independent scores, z_k=w0^(k)+w1^(k)x1+w2^(k)x2, one per class. OvO: three independent pairwise scores, z_ij=w0^(ij)+w1^(ij)x1+w2^(ij)x2, one per class pair.

STEP 2 -- COMBINE THE SCORES INTO ONE PREDICTION

OvR: predict argmax_k z_k -- whichever classifier scored highest. OvO: each z_ij>=0 votes for class j, z_ij<0 votes for class i; predict whichever class collected the most votes (ties broken by aggregate confidence).

09
MATHEMATICS

K vs. K(K-1)/2, and the one point where they coincide

OvR needs exactly K classifiers -- one per class. OvO needs one classifier per unordered pair of classes: choosing 2 of K, order doesn't matter, so C(K,2)=K(K-1)/2.

OvR classifier count = K
OvO classifier count = K(K-1)/2 = C(K,2)

Setting the two counts equal, K=K(K-1)/2, gives 2K=K^2-K, so K^2=3K, so K=3 (the only positive integer solution, since K=0 is degenerate). This module's own worked example sits exactly at K=3 -- the one class count where OvR and OvO cost the same, before OvR's linear growth and OvO's quadratic growth diverge:

The main disagreement, traced. At x1=3, x2=5: OvR's three scores are z0=1-1(3)+0.4(5)=0, z1=-2+0.5(3)+0.3(5)=1.0, z2=-3+0.8(3)+0.5(5)=1.9 -- argmax is class 2. OvO's three pairwise scores are z01=0.5-0.6(3)+0.1(5)=-0.8 (negative, votes class 0), z02=-1.5+0.2(3)+0.1(5)=-0.4 (negative, votes class 0), z12=0.5+0.1(3)-0.2(5)=-0.2 (negative, votes class 1). Votes: class0=2, class1=1, class2=0 -- majority is class 0. OvR says class 2; OvO says class 0.

The tie, traced. At x1=0, x2=0 (each score reduces to its own w0): OvO's z01=0.5 votes class 1, z02=-1.5 votes class 0, z12=0.5 votes class 2 -- a genuine three-way 1-1-1 tie (the only possible tie shape at K=3, since each class appears in exactly 2 of the 3 pairs). Aggregate confidence sums each pair's signed score into both classes it involves: class 0 nets -z01-... precisely, summing +z into the favored class and -z into the other across all 3 pairs gives agg0=1.0, agg1=0.0, agg2=-1.0 -- class 0 wins the tie-break, matching OvR's own unambiguous class-0 call at this exact point (a genuine, verified consistency, not engineered to always happen).

Verification methodEvery score, vote, and aggregate-confidence sum above was computed via a Node.js script implementing the argmax and vote-counting rules directly as functions, then cross-checked with a brute-force grid scan that independently located both the clean-agreement point and the exact tie point (rather than having them hand-picked blind). Floating-point noise (e.g. 1.9000000000000004) was confirmed to sit at machine-precision level, not a real discrepancy.

CONCRETE USE

A clean case, a boundary case, and a genuine caveat

CLEAN CASE

x1=1, x2=0 -- both models agree

OvR and OvO both predict class 0 here -- disagreement isn't universal, just possible.

BOUNDARY CASE

x1=0, x2=0 -- OvO ties, resolved by aggregate confidence

A genuine 3-way vote tie, broken by summing signed pairwise scores -- not an arbitrary tiebreaker, and it happens to agree with OvR here.

MISTAKE TO AVOID

Treating OvR's three z-scores as directly comparable confidences

Wikipedia's own cited critique states the confidence scale can differ classifier to classifier -- OvR's argmax still works, but reading the gap between z1 and z2 as a calibrated confidence gap is not justified by the method itself.

CODE

OvR's argmax and OvO's vote-plus-tiebreak, implemented directly

PYTHON · OvR ARGMAX, OvO MAJORITY VOTE + AGGREGATE-CONFIDENCE TIEBREAK 
OVR_WEIGHTS = [(1, -1, 0.4), (-2, 0.5, 0.3), (-3, 0.8, 0.5)]
OVO_WEIGHTS = {(0, 1): (0.5, -0.6, 0.1), (0, 2): (-1.5, 0.2, 0.1), (1, 2): (0.5, 0.1, -0.2)}

def score(w, x1, x2):
    w0, w1, w2 = w
    return w0 + w1 * x1 + w2 * x2

def ovr_predict(x1, x2):
    scores = [score(w, x1, x2) for w in OVR_WEIGHTS]
    return scores.index(max(scores)), scores

def ovo_predict(x1, x2):
    votes = [0, 0, 0]
    agg = [0.0, 0.0, 0.0]
    zs = {}
    for (i, j), w in OVO_WEIGHTS.items():
        z = score(w, x1, x2)
        zs[(i, j)] = z
        winner = j if z >= 0 else i
        votes[winner] += 1
        agg[j] += z
        agg[i] -= z
    top = max(votes)
    tied = [c for c, v in enumerate(votes) if v == top]
    predicted = tied[0] if len(tied) == 1 else max(tied, key=lambda c: agg[c])
    return predicted, votes, zs, agg

ovr_class, ovr_scores = ovr_predict(3, 5)
ovo_class, ovo_votes, _, _ = ovo_predict(3, 5)
assert ovr_class == 2 and ovo_class == 0  # the worked example's own disagreement

tie_class, tie_votes, _, tie_agg = ovo_predict(0, 0)
assert tie_votes == [1, 1, 1] and tie_class == 0  # the tie, broken by aggregate confidence

ECOSYSTEM

scikit-learn's OneVsRestClassifier and OneVsOneClassifier

sklearn.multiclass.OneVsRestClassifier and OneVsOneClassifier both wrap any base binary estimator automatically, fitting and predicting the full K or K(K-1)/2 ensemble without the caller managing individual classifiers by hand -- this lesson's own hand-specified weights stand in for whatever those wrapped estimators would have fit from real data. scikit-learn's own multiclass.html page states OvR is "the most commonly used strategy and is a fair default choice," while OvO "may be advantageous for algorithms... which don't scale well with n_samples... because each individual learning problem only involves a small subset of the data" -- a real, citable reason to prefer OvO for specific base estimators, not just a generic trade-off.

18
REALITY

Production implications

  • Adding one new class to an OvR system means training one new classifier; adding one new class to an OvO system means training K brand-new pairwise classifiers -- a real, growing maintenance cost difference as K grows.
  • OvR's own per-classifier score comparability is a real calibration risk in production dashboards that report a single "confidence" number across classes -- echoing Module 02's own calibration concept by name only.
  • OvO's O(K^2) classifier count is a real reason to prefer OvR by default for large K, exactly as scikit-learn's own documentation states -- reserving OvO for base estimators that specifically benefit from smaller, more balanced sub-problems.

CAREER PRACTICE

Interview questions

Conceptual: why can OvR and OvO disagree even though both combine the same kind of binary classifier?
Because they combine the underlying scores through structurally different rules -- OvR takes an argmax over K independent scores, OvO takes a majority vote over K(K-1)/2 pairwise duels -- and nothing in either mechanism guarantees the two combination rules land on the same class.
Mathematical: derive K(K-1)/2 from first principles and find the K where it equals K.
Choosing an unordered pair from K items is C(K,2)=K!/(2!(K-2)!)=K(K-1)/2. Setting K=K(K-1)/2 gives 2K=K^2-K, so K^2=3K, so K=3 is the unique positive-integer solution.
Coding: implement the aggregate-confidence tie-break for an arbitrary K, not just K=3.
For every pair (i,j) with i<j, add its signed pairwise score to class j's aggregate and subtract it from class i's aggregate (Section 12's own agg[j]+=z / agg[i]-=z pattern generalizes directly to any K), then among the classes tied for the most votes, pick the one with the highest aggregate.
System design: when would you prefer OvR, OvO, or softmax (named forward) for a real multiclass pipeline?
OvR by default for large K or when the base estimator scales well with sample count (scikit-learn's own "fair default choice"); OvO specifically when the base estimator doesn't scale well with n_samples, since each OvO sub-problem only sees a small subset of the data; softmax (Concept 09) when a single, jointly-trained probabilistic model across all K classes is preferable to combining separately-trained binary classifiers at all.
