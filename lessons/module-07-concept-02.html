01 · CONCEPT FIRST

The pivot, named plainly

Concept 01 used Euclidean distance throughout, without ever naming the choice. This concept makes the choice itself the subject: KNN needs some notion of "close," and there is more than one legitimate way to define it.

First memory: distance metric is a modeling choice with the same status as k. On the right dataset, at the right k, the same query gets a different prediction depending purely on which distance function is used.
02 · WHY IT EXISTS

When "nearest" isn't obvious

Walking diagonally across a park (a straight line, Euclidean) and walking city blocks (a grid, Manhattan) get you to the same destination by different-length paths. That difference can change which stored point counts as "nearest" to a query -- exactly the effect this concept measures directly.

03 · CONCRETE EXAMPLE

The same query, two rulers, two different answers

Four points, query Q=(0,0), k=3: Fixed1(0, 0.5, Escalate), Fixed2(-0.5, 0, Resolve), D(1, 1, Escalate), X(1.6, 0, Resolve). Under Euclidean distance, the three nearest are Fixed1, Fixed2, D -- 2 Escalate votes to 1, predicting Escalate. Under Manhattan distance, the three nearest are Fixed1, Fixed2, X instead -- 1 Escalate vote to 2, predicting Resolve. Nothing about the data changed -- only the ruler did.

04 · TECHNICAL MECHANISM

Two formulas, one geometric reason

Euclidean distance is the straight-line length: sqrt of the sum of squared differences. Manhattan distance is the grid-walk length: the sum of absolute differences. D sits on the diagonal (1,1) from the query -- Euclidean's straight line shortens it to sqrt(2)≈1.414, while Manhattan's grid-walk cost stays at 1+1=2. X sits on an axis (1.6, 0) -- both metrics agree exactly, 1.6=1.6. That's enough to swap the third-ranked neighbor and flip the vote.

05 · ARCHITECTURE / FLOW

A third ruler that ignores size entirely

Concept 01 — Euclidean distance, unnamed→ This concept — the metric itself becomes the subject→ Concept 03 — Naive Bayes, a probability-based family, named forward

Cosine distance asks "do these point the same way," not "how far apart are the tips." U=(1,2) and V=(4,8)=4×U point in the exact same direction -- cosine similarity is 1.0 exactly, even though Euclidean distance between them is 6.71 and Manhattan is 9.00.

06 · IMPORTANT DISTINCTIONS

Distance metric vs. k

DialWhat it controls
k (Concept 01)How many neighbors get a vote.
Distance metric (this concept)Who even counts as near in the first place. Two independent dials, not the same choice.
07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Distance is distance -- the metric doesn't matter."

False, directly refuted by this concept's own worked example: the same query at the same k flips its prediction purely from the metric change.

"Manhattan is just a worse approximation of Euclidean."

False -- it's a different, equally legitimate geometry, not an approximation. Neither is "more correct" in general.

The same pipeline, one swappable parameter

KNN's own distance-sort-vote pipeline (Concept 01, cited unchanged) stays exactly the same -- only the distance function used in the first step becomes an explicit, swappable parameter. k, sort, and vote never change; only which points end up in the top-k can change when the metric changes.

MATHEMATICS

The exact mechanical root of the flip

D=(1,1) from Q=(0,0): Euclidean = sqrt(2) ≈ 1.414214; Manhattan = 1+1 = 2.000000
X=(1.6,0) from Q=(0,0): Euclidean = 1.600000; Manhattan = 1.600000 (agree exactly, on-axis)

Euclidean top-3: Fixed1, Fixed2, D -- 2 Escalate votes to 1 -- predicts Escalate. Manhattan top-3: Fixed1, Fixed2, X -- 1 Escalate vote to 2 -- predicts Resolve. Mechanical reason: D sits on the diagonal where Euclidean's straight-line measure shortens it (√2≈1.414) relative to Manhattan's grid-walk cost (2.000); X sits on an axis where both metrics agree exactly (1.6=1.6). That's enough to swap the third neighbor and flip the vote, since the other two seats split 1-1.

Cosine addendum (a separate illustration, not part of the vote-flip demo). U=(1,2), V=(4,8)=4×U. Euclidean(U,V)=6.708204, Manhattan(U,V)=9.000000, cosine similarity=(U·V)/(‖U‖‖V‖)=20/20=1.0 exactly. Euclidean and Manhattan both call U and V far apart; cosine calls them identical, because it only sees direction -- exactly why cosine distance is standard for text/embedding similarity, where vector length often tracks incidental factors rather than meaning.

Verification methodEvery distance value above was computed and independently verified via a Node.js script (Math.sqrt/Math.abs/dot-product/norm implementations), with the ranked orders and vote counts confirmed programmatically, not by hand alone.
11
CONCRETE USE

A clean fit, a boundary case, and a genuine caveat

CLEAN FIT

Cosine for text/embedding similarity

Magnitude is noise, not signal, for most embedding comparisons -- cosine's own invariance is exactly the right property.

BOUNDARY CASE

k=3, Euclidean vs. Manhattan

The same query, the same k, a real vote flip -- nothing else changed.

GENUINE CAVEAT

Unscaled features distort either metric

A feature on a much larger numeric scale can dominate both Euclidean and Manhattan sums unless features are standardized first -- a real risk independent of which metric is chosen.

12
CODE

The vote flip, reproduced directly

PYTHON · EUCLIDEAN, MANHATTAN, COSINE -- REPRODUCES THIS CONCEPT'S OWN NUMBERS EXACTLY 
POINTS = {"Fixed1": (0, 0.5, 1), "Fixed2": (-0.5, 0, 0), "D": (1, 1, 1), "X": (1.6, 0, 0)}

def euclid(x1, x2):
    return (x1 ** 2 + x2 ** 2) ** 0.5

def manhattan(x1, x2):
    return abs(x1) + abs(x2)

def vote(distance_fn, k=3):
    ranked = sorted(POINTS.items(), key=lambda kv: distance_fn(kv[1][0], kv[1][1]))
    top = ranked[:k]
    escalate = sum(1 for _, (_, _, y) in top if y == 1)
    return [name for name, _ in top], escalate, k - escalate

eu_top, eu_esc, eu_res = vote(euclid)
man_top, man_esc, man_res = vote(manhattan)
assert eu_top == ["Fixed1", "Fixed2", "D"] and eu_esc == 2
assert man_top == ["Fixed1", "Fixed2", "X"] and man_esc == 1

# Cosine addendum.
U, V = (1, 2), (4, 8)
dot = U[0] * V[0] + U[1] * V[1]
norm_u = (U[0] ** 2 + U[1] ** 2) ** 0.5
norm_v = (V[0] ** 2 + V[1] ** 2) ** 0.5
cosine_sim = dot / (norm_u * norm_v)
assert round(cosine_sim, 6) == 1.0

18
REALITY

Production implications

  • The metric argument is a real, consequential config choice in any nearest-neighbor system -- recommenders, search, complaint-similarity lookups all make it explicitly.
  • Text/embedding pipelines default to cosine for the magnitude-invariance reason established here.
  • Changing a deployed system's metric can change live predictions the same way changing k can -- it belongs in model versioning and change review, not treated as a silent default.

RECALL

Knowledge check

Why does D flip between Euclidean and Manhattan in this concept's own worked example?
D sits off-axis at (1,1); Euclidean's straight-line measure shortens it to √2≈1.414, while Manhattan's grid-walk cost stays at 2.000 -- that gap is enough to swap D in or out of the top-3.
Why does cosine treat U=(1,2) and V=(4,8) as identical?
Cosine measures only direction, not length -- V is exactly 4x longer than U but points the same way, so their cosine similarity is exactly 1.0.
Name one production system where cosine is the standard choice, and why.
Text/embedding similarity systems -- vector length in that setting often tracks incidental factors (like document length) rather than meaning, so ignoring magnitude is the correct behavior, not a limitation.

23
CAREER PRACTICE

Interview questions

Conceptual: when would you choose cosine over Euclidean distance?
When vector magnitude carries no meaningful signal -- text/embedding similarity is the standard case, since document length or embedding-norm variation shouldn't change how "similar" two pieces of content are judged to be.
Mathematical: does changing the distance metric in KNN require retraining?
No -- KNN has no training phase at all (Concept 01, cited); changing the metric only changes how distance is computed at prediction time.
Mathematical: what is the geometric relationship between Manhattan, Euclidean, and Minkowski distance?
Minkowski distance generalizes both with a parameter p: p=1 recovers Manhattan exactly, p=2 recovers Euclidean exactly.
Coding: extend Section 12's script to compute Minkowski distance for a general p.
def minkowski(x1, x2, p): return (abs(x1) ** p + abs(x2) ** p) ** (1 / p) -- calling it with p=1 reproduces manhattan()'s own output exactly, and p=2 reproduces euclid()'s own output exactly.
