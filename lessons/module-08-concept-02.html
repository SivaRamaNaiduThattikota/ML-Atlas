PROGRESSIVE BEGINNER CORE

What a tree does when no split comes out clean

Concept 01 got lucky: its own 10-row set happened to have one feature that perfectly separated the classes, so the recursion stopped after a single split. This concept covers the normal case -- what a tree does when the best available split still leaves both sides mixed, and why letting it keep splitting anyway is exactly how it overfits.

First memory: Concept 01's own Section 16 named this exact stop: "On real CFPB-scale data the best available split at the root almost always leaves both children impure, and the recursion keeps going... Concept 02 covers what a tree does when neither condition arrives quickly -- it keeps splitting, and that is exactly how a tree overfits." This concept is that named stop, arrived at.
02 · WHY IT EXISTS

A tree with no stopping rule can always reach 0% training error

Every split is a strict refinement of whatever partition already exists -- it can only carve a node into two smaller pieces, never make a node's own error worse than before the split. Repeat that enough times and a tree can always keep going until every leaf holds rows that all share the same label, at which point training error hits exactly zero. That is not a sign of a good model; it just means the tree has enough leaves to give every training row its own private answer. On real data, some of those leaves end up defined by a single outlier row rather than any real pattern -- and a tree that has memorized an outlier will confidently misjudge the next case that merely resembles it.

04 · TECHNICAL MECHANISM

Two knobs, one problem: stop early, or cut back afterward

Pre-pruning stops the recursion before it fully grows -- a depth limit (max_depth), a minimum node size before splitting is allowed (min_samples_split), or a minimum leaf size (min_samples_leaf). The branch that would isolate an outlier is simply never grown. Post-pruning does the opposite: grow the tree all the way out, then remove branches afterward if they cost more complexity than they're worth, measured by minimal cost-complexity pruning's own ccp_alpha. Both are real knobs on scikit-learn's DecisionTreeClassifier; Section 15 tables every one of them.

05 · ARCHITECTURE / FLOW

Same root, different depth, opposite held-out answer

Walk the held-out row (prior_contact_attempts=2, case_age_days=10) down each tree above. In the stump it goes left at the root and stops -- that leaf's majority vote (3 resolve vs. 1 escalate) predicts resolve -- correct. The full tree has lower training error (0% vs. 12.5%) and the worse held-out answer.

06 · IMPORTANT DISTINCTIONS

Pre-pruning and post-pruning are different mechanisms -- here, they agree

ApproachThe real difference
Pre-pruning (max_depth, min_samples_leaf, min_samples_split)Stops the recursion before the outlier-isolating branch is ever grown. Cheaper -- the branch never exists.
Post-pruning (ccp_alpha, minimal cost-complexity)Grows the full tree first, then removes the branch afterward once its added cost outweighs its impurity reduction, measured by alpha_eff.

They are not the same search, and in general they don't have to land on the same tree. On this concept's own 8-row set they do: Section 13 shows pruning at ccp_alpha=0.1875 reproduces the identical stump built by capping max_depth=1 -- a genuine coincidence of this dataset, not a general guarantee.

07 · COMMON MISTAKES

What beginners often assume, and shouldn't

"Lower training error always means a better tree."

False, and this concept's own head-to-head disproves it directly: the full tree's 0% training error is worse on the held-out check than the stump's 12.5%.

"This one held-out row proves shallower trees always generalize better."

No -- the held-out point was deliberately constructed to sit next to outlier D. It illustrates the mechanism; it is not a statistical guarantee that depth-1 beats depth-3 on any other dataset.

06
MATHEMATICS

Why training error can never increase as depth grows

Every split at depth d takes one existing leaf and partitions its rows into two new leaves at depth d+1. Nothing about a split can make either new leaf's own error worse than the parent leaf's error was, because the split-finding search (Concept 01's own exhaustive scan) only accepts a split if it reduces weighted impurity -- and a leaf's own misclassification count under a majority vote can only fall or stay the same as its impurity falls. So the sequence of training errors across depths 1, 2, 3, ... is non-increasing by construction: it can plateau, but it can never go back up. This is the formal version of Section 02's own bias-variance framing -- depth is this model family's own complexity dial, exactly as k was for KNN in Module 07 Concept 01, except the dial here always moves training error the same direction.

WORKED EXAMPLE

Grown without a stopping rule: the full tree

Root (8 rows, Gini 0.46875) → split at x1 ≤ 2.5 → Left {A,B,C,D} Gini 0.375, Right {E,F,G,H} Gini 0
Left is still mixed, so the recursion splits it again: x2 ≤ 7 → Left-left {A,B,C} Gini 0 (all resolve), Left-right {D} Gini 0 (escalate, alone)
Right is already pure, so it is never split further -- 3 leaves total, every one of them pure

Every training row is now correctly classified by its own leaf: 0% training error, 3 leaves. Outlier row D has been given its own private leaf, defined by nothing except its own two feature values.

12
MATHEMATICS

Minimal cost-complexity pruning

Rα(T) = R(T) + α|T̃| -- scikit-learn's own cost-complexity measure, where R(T) is the tree's total sample-weighted leaf impurity and |T̃| is its leaf count
alpha_eff(t) = (R(t) - R(Tt)) / (|T| - 1) -- the effective alpha at which pruning subtree Tt back to a single leaf t first becomes worthwhile

scikit-learn's own documentation is explicit that this R(T) -- total sample-weighted impurity of the terminal nodes -- is its specific choice, not the only possible definition; some textbooks define cost-complexity pruning's R(T) instead as a plain misclassification rate. Both are valid formulations of the same idea; this concept uses scikit-learn's own weighted-impurity version throughout, cited from Section 1.10.9 of its user guide.

13
CODE

Node verification 4 -- alpha_eff for both internal nodes, and the collapse

JAVASCRIPT · COMPUTES R(T) FOR ALL THREE PRUNING STAGES AND BOTH alpha_eff VALUES 
function R(leafGinis) {
  // sum over leaves of (n_leaf / N) * Gini_leaf
  return leafGinis.reduce((sum, [n, g]) => sum + (n / 8) * g, 0);
}

const rFullTree = R([[3, 0], [1, 0], [4, 0]]);          // 0       (3 pure leaves)
const rStump    = R([[4, 0.375], [4, 0]]);               // 0.1875  (2 leaves)
const rRootOnly = R([[8, 0.46875]]);                     // 0.46875 (1 leaf)

const alphaEffLeft = (rStump - rFullTree) / (2 - 1);     // 0.1875
const alphaEffRoot = (rRootOnly - rFullTree) / (3 - 1);  // 0.234375

console.log(alphaEffLeft, alphaEffRoot);   // 0.1875 0.234375

alpha_eff(Left) is smaller, so as ccp_alpha rises from 0, "Left" is the weakest link and gets pruned first. Pruning at ccp_alpha=0.1875 removes exactly the branch that isolates D, collapsing the 3-leaf full tree into the identical 2-leaf stump already built by capping max_depth=1 in Section 10 -- same leaves, same held-out prediction. Raising ccp_alpha further to 0.234375 prunes the remaining split too, collapsing the stump into a single root leaf (majority escalate, 5 of 8).

Scrutinize this like any other number hereThese two alpha_eff values were computed fresh for this concept, not carried over from Concept 01's own verified scan -- they match an independent by-hand check, but they deserve the same skepticism as every other number on this page, not automatic trust because the formula looks official.

DIAGNOSIS

An honest caveat: the depth-sweep dataset is synthetic, not real CFPB records

This concept's own 8-row set only needs two splits to fully memorize itself -- there isn't enough data in it to show a multi-depth U-curve. The lab's depth sweep therefore uses a separate, larger, explicitly synthetic 60-row set instead: a seeded linear-congruential generator (seed 10007, fully reproducible -- the same seed reprints the same 60 rows every run) generates CFPB-style rows from the rule "escalate if prior_contact_attempts ≥ 3, or if prior_contact_attempts = 2 and case_age_days ≥ 8," with 20% of labels flipped by the same generator to simulate real-world noise. Feature names echo this concept's own CFPB convention; the rows themselves do not come from real complaint records, exactly the way Concept 01's own Section 16 disclosed its own toy set's unusual cleanliness rather than letting it pass as real data.

MECHANICS

Where DEPTH_DATA actually comes from

The lab's table of train/validation error and leaf count per depth is not looked up from a textbook curve or fabricated to look plausible -- it is copied directly from the printed output of nb_scratch/m08c02_depth_sweep_verify.js, a rerunnable script with a fixed seed (10007). That script generates the same 60 rows every time it runs, splits them 40 train / 20 validation, fits a real recursive Gini-splitting tree (the same mechanics as Concept 01's own scanFeature, an exhaustive threshold scan on both features) at max_depth 1 through 8, and reports training error, validation error, and leaf count at each depth. "Jump to best depth" moves the slider to whichever depth has the lowest validation error in that same table -- depth 3, here -- computed from the data, not hardcoded as "3."

REALITY

Production implications

  • scikit-learn's own documentation suggests min_samples_leaf=5 as a reasonable starting value for many datasets, rather than its own default of 1 -- a real starting point, not this concept's own invention.
  • cost_complexity_pruning_path(X, y) plus a validation set (or cross-validation) is the real way to pick ccp_alpha in production -- not guessing a value, and not reading it off a training-accuracy curve, which Section 06 already showed can only look better as depth grows.
  • Tuning max_depth by watching training accuracy alone is exactly the trap Section 08-11's head-to-head demonstrates: the metric that looks best on training data is not the model that will perform best in production.

CAREER PRACTICE

Interview questions

Conceptual: why must training error be monotone non-increasing in max_depth?
Every additional split strictly refines an existing partition of the training rows -- it can only reduce or preserve a leaf's own error under a majority vote, never increase it, so the sequence of training errors across increasing depth can plateau but never rise.
Mathematical: derive alpha_eff for a two-child internal node from R_alpha(T) = R(T) + alpha|T~|.
Set the cost of keeping the node's own subtree equal to the cost of collapsing it to one leaf: R(subtree) + alpha·(leaves in subtree) = R(node-as-leaf) + alpha·1. Solving for alpha gives alpha_eff = (R(node-as-leaf) - R(subtree)) / (leaves in subtree - 1) -- exactly the formula Section 12 states and Section 13 applies.
Coding: extend Section 07's own scanFeature to also report leaf count and training error at a given max_depth.
Recurse: at each call, check whether the current depth equals max_depth or the node is already pure; if so, stop and count it as one leaf with its own majority-vote error, otherwise call scanFeature again on each child and sum their leaf counts and errors -- the same recursive structure Section 19's depth-sweep script already runs.
System design: when would you prefer pre-pruning over post-pruning in a real pipeline, or the reverse?
Pre-pruning (max_depth, min_samples_leaf) is cheaper -- the outlier-isolating branch is never grown, which matters at scale. Post-pruning (ccp_alpha via cost_complexity_pruning_path) searches a finer-grained space of trees after the fact and can find a better cutoff than a single depth number allows, at the cost of growing the full tree first. Section 13's own result -- that both land on the same tree here -- is a property of this dataset, not a reason to treat them as interchangeable in general.
23
CORRECTION

Common misconception

"Pruning after growing the full tree is strictly worse than just capping max_depth up front."Section 12-13's own result contradicts that directly: on this concept's own 8-row tree, pruning at ccp_alpha=0.1875 after growing the full tree produces the exact same stump that capping max_depth=1 produces from the start. Pre-pruning and post-pruning are different search strategies over the same hypothesis space of possible trees, not a strictly-better/worse pair -- one never grows the branch, the other grows it and removes it by a cost calculation, and here they agree.
