MODULE 08 · CONCEPT 04

One feature keeps winning every split.
A forest has to be told, sometimes, to look away from it.

Concept 03 fixed a single tree's instability by resampling rows -- three bootstrap draws, three independent stumps, one vote. That fix has a blind spot: if every one of those bootstrap trees can still see every feature, and one feature is simply the best predictor in the dataset, all three trees tend to rediscover the same split anyway. This concept keeps the bootstrap resampling and adds a second randomization on top of it: at every split, hide a random subset of features from the tree being fit. The trees that result don't just see different rows -- they're forced to sometimes reason about a different feature. The result is a forest whose trees disagree with each other measurably more than a bagged ensemble's trees do, on the exact same bootstrap draws.

Ten trees that all saw the same best feature just vote as one

01 · CONCEPT FIRST

A committee that keeps agreeing isn't much of a committee

A single decision tree stares at the same 8 CFPB rows and, given all 3 features, always finds the same winning split. Building ten trees the same way -- same rows, same features available -- just gets you ten copies of the same opinion wearing different hats. They vote as one voter, not ten.

First memory: Bagging changes which rows a tree sees. A random forest changes that and which features a tree is even allowed to consider at each split.
02 · WHY IT EXISTS

Bagging, in one paragraph

Bootstrap aggregation (bagging) builds many trees, each fit on its own bootstrap resample of the training rows -- N rows drawn from N with replacement, so any one draw repeats some rows and skips others entirely. Concept 03 built exactly three such resamples on an 8-row toy set and voted across the resulting stumps. That mechanism is reused unchanged below; what's new here is a second layer of randomness stacked on top of it.

BAGGING & RANDOM FORESTS (this module)

04 · TECHNICAL MECHANISM

Why bagging alone doesn't disagree enough

If every bootstrap tree still sees all 3 features, and one feature is simply the strongest predictor in the data, that feature tends to win the scan on nearly every resample -- the rows differ, but the winning question doesn't. Bagged trees built this way end up looking alike even though they were technically fit on different data.

05 · ARCHITECTURE / FLOW

Random forest's fix: hide features, not just rows

At every single split, a random forest picks a random subset of the available features and lets the tree choose its best split from only that subset -- never the full feature list. When the dominant feature happens to be hidden, a weaker feature is forced to win instead. Repeated across many splits and many trees, this is what actually makes trees disagree, on top of whatever disagreement the bootstrap resampling already provides.

06 · IMPORTANT DISTINCTIONS

Voting is voting, but the ballots are different now

Every tree in the forest still just casts one vote -- relief or no relief -- on a new row, exactly like bagging's stumps did in Concept 03. Majority vote across the forest is still the prediction. What's different is what went into each ballot: a bagged tree's vote reflects a different sample of rows; a random forest tree's vote reflects a different sample of rows and a restricted view of the features, so two trees can land on genuinely different reasoning, not just different data.

07 · COMMON MISTAKES

"If the trees disagree, something's broken"

"Trees disagreeing means the model is unstable in a bad way."

Not necessarily. When each tree's mistakes are less correlated with the others', averaging cancels some of them out instead of every tree confirming the same wrong answer. Disagreement is the raw material a vote needs to be worth taking.

"More trees automatically means more disagreement."

False -- Section 22 covers this directly. Adding trees without restricting features just adds more copies of the same opinion; the feature restriction is what actually does the decorrelating.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

State what a random forest adds on top of bagging

Bagging resamples rows only. A random forest resamples rows and restricts which features are available at every individual split.

Explain why that restriction lowers correlation between trees

Hiding the dominant feature sometimes forces a different, weaker feature to win a split, so trees stop reliably converging on the same question.

Say the honest thing about accuracy at this scale

On this concept's own 8-row example, the single tree, bagging, and the random forest all score exactly 0.875. The disagreement structure changes; the score doesn't, at this size.

Teach-back questions

  1. What does a random forest do at each split that a bagged ensemble of trees does not?
  2. Why can two trees fit on the exact same bootstrap draw still end up with different splits?
  3. Why is it wrong to say this concept's random forest "performed better" than the single tree or the bagged ensemble?

01
ORIENTATION

From one tree to a committee

A single decision tree commits hard to whichever split looks best on its exact training rows, with no mechanism to hedge that bet -- change the rows even slightly and the whole tree can change downstream of one flipped split. Concept 03 addressed part of that: fit several trees on several bootstrap resamples and vote. This concept addresses the part bagging leaves untouched -- if every one of those resampled trees can still see every feature, the strongest feature tends to win the split search on nearly every resample anyway, and the committee ends up voting together more often than its member trees' independent data would suggest.

02
RECAP

Bootstrap aggregation, recapped in full

Bagging draws a bootstrap sample: N rows sampled from an N-row training set with replacement, so any one draw both repeats some rows and omits others. Concept 03's own worked example ran this exact mechanic on an 8-row toy set, fitting one stump per bootstrap draw and combining the three stumps' predictions by majority vote. Nothing about that mechanism changes here -- every bootstrap draw below is produced the same way, and every tree fit on one still uses Concept 01's own Gini-based exhaustive threshold scan, unmodified. This section restates the mechanism in full, rather than assuming it, so this concept reads standalone even for anyone jumping in without Concept 03 open in another tab.

WORKED EXAMPLE

The single tree, walked by hand

Root: p0=5/8=0.625, p1=3/8=0.375 → Gini = 1 - (0.625² + 0.375²) = 0.468750

An exhaustive scan of every candidate threshold on all three features finds one winning split: x1 (prior_contact_attempts) ≤ 2.5, Gini gain 0.281250 (giniAfter 0.187500) -- the best any single feature and threshold can do at this root. Left {A,B,D,F} is pure (all no-relief, Gini 0). Right {C,E,G,H} is 3 relief / 1 no-relief, Gini 0.375: majority vote there is relief. That one no-relief row on the right -- row H (3 contacts, 50 days, not timely, true label no-relief) -- gets predicted relief anyway, because it falls on the wrong side of x1=2.5 for its true label. 7 of 8 rows correct: accuracy 0.875.

08
DIAGNOSIS

Same score, different miss

The same 0.875 accuracy, a different mistake.The single tree and the 3-tree bagged ensemble both score 7/8 on this dataset -- but the single tree misses row H and bagging misses row C. Bagging changed which mistake gets made before it changed how many mistakes get made. That distinction -- not a score improvement -- is the entire setup for the next section: if resampling rows alone can shuffle which row gets missed, what does restricting features on top of that do?
09
ECOSYSTEM

max_features, verbatim from scikit-learn

scikit-learn's RandomForestClassifier and RandomForestRegressor both expose a max_features parameter controlling exactly the restriction this concept is about -- the number of features to consider when looking for the best split. Per the library's own documentation: 'sqrt' uses max(1, int(sqrt(n_features))) features (the classifier's default); 1.0 or None considers max(1, n_features) features, i.e. all of them (the regressor's default); 'log2' uses max(1, int(log2(n_features))); an int value is used as an exact count; a float value f is interpreted as max(1, int(f * n_features_in_)) features. The documentation also flags a changed-in-1.1 note: the default for classifiers changed from 'auto' to 'sqrt' in scikit-learn 1.1.

13
DIAGNOSIS

An honest limit: accuracy doesn't move at this scale

Accuracy ties at 0.875 across the single tree, bagging, and the random forest.Do not read this as random forests failing to beat bagging in general, and do not read it as bagging failing to beat a single tree in general. At n=8 rows and 3 trees, decorrelation shows up in the correlation structure and in which row gets missed -- not in an accuracy improvement. Accuracy gains from decorrelation typically emerge at larger sample sizes and with more trees, which this hand-checkable toy example is not built to demonstrate. This is a stated boundary of the worked example, not a general claim about random forests.
14
CONTRAST

Pasting, bagging, random subspaces, random patches, random forest

scikit-learn's own BaggingClassifier documentation lays out a small taxonomy of resampling axes, each one a different combination of "which rows" and "which features" an ensemble member sees:

NameWhat varies per estimator
PastingA subset of samples, drawn without replacement.
BaggingA subset of samples, drawn with replacement (this concept's Section 07 and Concept 03's own worked example).
Random SubspacesA fixed subset of features, drawn once per estimator and reused for every split that estimator makes.
Random PatchesBoth a subset of samples and a subset of features, again fixed per estimator.
Random ForestBootstrap samples of rows, plus a fresh random feature subset drawn at every individual split -- not once per tree, at every split. This is the mechanism Section 10 above walks by hand.

The distinguishing detail is easy to miss: Random Subspaces and Random Patches fix their feature subset once per estimator, while a random forest redraws it at every split inside a tree. That per-split redraw is what this concept has been calling "the feature restriction" throughout.

17
MATHEMATICS

Feature importance: mean decrease in impurity

Mean decrease in impurity (MDI) ranks a feature by how much, on average across every split in every tree where that feature was used, splitting on it reduced Gini impurity -- weighted by how many training rows reached that split. A feature used in many high-gain splits across the forest scores high; a feature never chosen scores near zero.

This concept does not compute an MDI score for the 8-row worked example -- three trees is too small a forest for the number to mean much. Looking forward instead: Module 04 Concept 10 ranked four engineered CFPB features by their absolute correlation with the outcome -- prior_contact_attempts_scaled (|r|=0.6093), company_relief_rate (|r|=0.4357), contact_x_company_risk (|r|=0.1647), and is_weekend (|r|=0.0667). A random forest fit on those same features would plausibly rank them in a similar order by MDI, since both correlation and impurity reduction tend to favor a feature's raw predictive signal -- but this is a hedged, forward-looking narrative, not a computed importance number. No MDI value has been calculated for those features in this concept's scope, and none should be assumed.

18
DIAGNOSIS

MDI's own documented caveats

scikit-learn's own user guide states MDI's limitations directly, and they carry over here verbatim rather than getting softened: impurity-based feature importances are computed on training-set statistics and therefore do not necessarily reflect a feature's usefulness for predicting on held-out data; MDI is also known to be biased toward high-cardinality features (features with many possible values). The documented alternative is permutation importance, which measures the drop in a fitted model's score when a feature's values are shuffled -- named here as the alternative, but not built out in this concept's scope.

19
TECHNICAL MECHANISM

Out-of-bag scoring, defined but not computed here

Because each bootstrap draw omits some rows, every tree in a random forest has an "out-of-bag" (OOB) set -- rows it never trained on -- that can be used to estimate generalization error without a separate validation split. scikit-learn exposes this through oob_score=True, and the resulting oob_score_ and oob_decision_function_ attributes. The documentation also flags a real failure mode: if n_estimators is too small, some training rows might never be left out of any tree's bootstrap sample, and the corresponding OOB prediction can come back as NaN.

Honesty check: this concept's 3-tree hand example is far too small for a reliable OOB estimate -- with only 3 trees, it is entirely plausible that most or all 8 rows appear in at least one tree's bootstrap sample and several appear in all three. OOB claims in this concept stay conceptual and definitional; no OOB score is computed on the toy forest above, and none should be inferred from it.

MECHANICS

Reading the lab's own verdict

The lab reports what fraction of the current forest's trees got forced off prior_contact_attempts and onto satisfaction_score, then classifies that diversity into three tiers, matching Section 12's own hand-verified correlation drop: 0% forced off the dominant feature means the forest is acting like several near-copies of one tree -- the same failure mode Section 08's bagging table showed, just more extreme with no feature restriction at all. 22
CORRECTION

More trees alone does not decorrelate a forest

"Just add more trees, they'll disagree eventually."

False. Resampling rows (bagging) is necessary but not sufficient -- Section 07 already showed all three bagged trees picking the same feature, x1, on three different bootstrap draws. Adding a fourth or fifth bagged tree with every feature still available would very plausibly do the same thing again.

"The feature restriction is optional polish on top of bagging."

It's the load-bearing second layer, not polish. Section 12's own numbers make this concrete: the exact same bootstrap draws produce average pairwise correlation 0.5367 with every feature available and 0.1667 with a restricted subset. The rows didn't change; only the feature restriction did.

23
CAREER PRACTICE

Interview questions

Conceptual: what does a random forest do that a bagged ensemble of trees does not?
It draws a fresh random subset of features at every individual split, on top of the bootstrap row resampling bagging already does -- not once per tree, but once per split inside each tree.
Mathematical: why can two trees fit on the exact same bootstrap sample end up with different splits?
If each tree's split search only sees a random subset of the available features, the feature that would otherwise win (because it's genuinely the strongest predictor) can simply be unavailable to one tree and available to another -- forcing different, weaker features to compete for the win.
Mathematical: state the difference between MDI and permutation importance.
MDI averages how much each feature reduced impurity across every split it was used in, computed purely from training-set statistics. Permutation importance instead measures how much a fitted model's actual score drops when a feature's values are shuffled -- a held-out-data-aware alternative that avoids MDI's high-cardinality bias.
System design: when would you reach for a random forest instead of plain bagging?
Whenever bagging's own trees keep converging on the same splits because one or a few features dominate the impurity-reduction search -- exactly the scenario Section 07's bagging table demonstrates. If the base trees are already meaningfully diverse (few strongly dominant features, or few enough total features that restricting further would leave almost nothing to split on), the extra randomization buys less.
