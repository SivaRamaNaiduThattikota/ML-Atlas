MODULE 08 · CONCEPT 05

A forest votes. It also, quietly, keeps score.
Feature importance is that scorecard, read out loud.

Concept 04 built a 3-tree forest, named mean decrease in impurity (MDI) as the way a forest ranks its own features, named permutation importance as the documented alternative -- and computed neither, calling three trees too small a forest for the number to mean anything. This concept picks up exactly there. The same three trees, the same bootstrap draws, the same feature restriction: this time, every split's impurity drop gets tallied per feature, and every feature gets independently shuffled and re-scored. Two different ways of asking the same question -- which feature is this forest actually leaning on -- computed for real, on a forest small enough to check by hand.

Which feature is this forest actually leaning on?

Concept 04 built a committee of trees that vote. This concept asks a different question about that same committee: not what it decided, but what it was paying attention to while deciding.

01 · CONCEPT FIRST

Every split a forest ever made is a vote for some feature mattering

A forest is a pile of trees, and every tree is a pile of splits, and every split picked exactly one feature to ask a question about. Feature importance just tallies that up: across every split in every tree, which features kept getting chosen, and how much impurity did choosing them actually remove? A feature no tree ever split on scores at the bottom. A feature that won high-gain splits again and again scores at the top.

First memory: Feature importance doesn't need a new model. It's a scorecard read off a forest that already exists.
02 · WHY IT EXISTS

The question Concept 04 left open on purpose

Concept 04's forest scored 0.875 accuracy, same as a single tree, same as bagging -- an honest toy-scale tie. That number alone doesn't say why the forest made the calls it made, or which of the three CFPB features it actually leaned on. Concept 04 named two ways to answer that -- mean decrease in impurity, and permutation importance -- and explicitly declined to compute either, calling a 3-tree forest too small to bother. This concept argues the opposite: three trees is exactly small enough to compute both by hand and check that the arithmetic is real.

03 · CONCRETE EXAMPLE

Two different questions, same three trees

MDI (TRAINING-SIDE QUESTION)

"Across every split this forest made, how much impurity did each feature remove, weighted by how many rows reached that split?" Answered by looking inside the trees -- no new predictions needed.

PERMUTATION IMPORTANCE (SHUFFLE-SIDE QUESTION)

"If I scramble this feature's values so it becomes noise, how much worse does the forest's own vote get?" Answered from outside the trees, by breaking one feature at a time and re-scoring.

04 · TECHNICAL MECHANISM

MDI: read the gain off every split, credit the feature that made it

Each of Concept 04's three stumps made exactly one split. Tree 3 split on x1 with gain 0.281250; Trees 1 and 2 split on x2 and x3 with gain 0.208333 each, because x1 was hidden from them. MDI credits each tree's gain entirely to whichever feature that tree's split actually used, weights it by how many rows reached the split (all 8, here, since these are root splits), then averages across the forest's 3 trees.

05 · ARCHITECTURE / FLOW

Permutation importance: break a feature, watch the vote wobble

Take the forest exactly as fit -- no retraining. Shuffle one feature's 8 values across the 8 rows, so that feature becomes pure noise while everything else stays put. Re-run the forest's vote on all 8 (now-scrambled-in-one-column) rows and check accuracy. Do that shuffle several times, since one shuffle is one random draw, and average the accuracy drop. A feature the forest actually depends on will hurt when scrambled; a feature the forest never really uses won't move the score much either way.

06 · IMPORTANT DISTINCTIONS

Agreeing here isn't the same as agreeing always

Both methods rank this forest's features the same way -- x1, then x2, then x3. That agreement is this dataset's own result, not a property either method guarantees. MDI is computed purely from training rows and is known to inflate high-cardinality features; permutation importance is computed by actually breaking a feature and watching a real score move, which is closer to what you'd trust on held-out data. They can and do disagree on real datasets -- this concept's own numbers happening to line up is a reportable fact about this forest, not proof the methods are interchangeable.

07 · COMMON MISTAKES

"High importance score means the feature is good"

"A feature with high MDI must be genuinely predictive."

Not necessarily -- MDI is computed only from the rows the forest trained on, so it can reward a feature that happens to fit the training data well without generalizing. Section 18 covers the documented caveats directly.

"Permutation importance and MDI will always rank features the same way."

False in general. They agree on this particular 8-row forest; Section 17 shows exactly why that's a coincidence of these numbers, not a rule.

09 · WHAT YOU SHOULD UNDERSTAND

Readiness check before moving on

State what MDI measures

The average, sample-weighted impurity drop credited to a feature across every split in every tree of the forest where that feature was used.

State what permutation importance measures

How much a fitted forest's own accuracy drops when one feature's values are shuffled into noise and everything else is left alone.

Say the honest thing about the two methods agreeing here

Both rank x1 highest on this 8-row forest. That's this dataset's result -- not a guarantee the two methods always agree, since MDI is training-only and permutation importance isn't.

Teach-back questions

  1. What does MDI credit to a feature, and where does that credit come from?
  2. Why does permutation importance require no retraining of the forest?
  3. Why is it wrong to conclude from this concept alone that MDI and permutation importance always agree?

01
ORIENTATION

From a vote to a scorecard

Concept 04 built a 3-tree forest that votes 0.875 accuracy on an 8-row CFPB relief table, and left two questions dangling on purpose: how much did each feature actually contribute to those votes, and is there more than one honest way to answer that? This concept answers both, without touching the forest itself -- no new trees get fit, no new bootstrap draws get taken. Everything below reads a scorecard off a forest that already exists.

02
RECAP

The forest, recapped in full

Three bootstrap draws (Boot1, Boot2, Boot3), each fit as a single stump restricted to a random 2-of-3 feature subset: Tree 1 saw {x2, x3} and split x2 ≤ 35 (gain 0.208333); Tree 2 saw {x2, x3} and split x3 ≤ 0.5 (gain 0.208333); Tree 3 saw {x1, x3} and split x1 ≤ 2.5 (gain 0.281250). Majority vote across the original 8 rows scores 7/8 (0.875), missing row H. None of this changes here -- it's restated in full so this concept reads standalone, and rebuilt from the same rows in Section 05 rather than retyped from Concept 04's own prose.

03
CONTRAST

Two questions that sound alike and aren't

MDI

Looks inside the trees. Tallies impurity reduction credited to each feature across every split, using only the rows the forest already trained on. Free to compute -- no new predictions, no re-fitting.

PERMUTATION IMPORTANCE

Looks at the forest from outside. Breaks one feature at a time by shuffling it, then re-scores the exact same fitted forest on the resulting scrambled rows. Costs one full re-scoring pass per shuffle, per feature.

Both answer "which feature matters," but MDI answers it from the training process's own bookkeeping, while permutation importance answers it by empirically breaking things and watching what happens -- a distinction that matters most when the two methods disagree, which Section 18 covers directly.

06
MATHEMATICS

MDI, defined precisely

MDI(feature f) = (1 / T) × ∑trees t ∑splits in t on f [ gain × (nnode / N) ]

For each split in each tree that used feature f, take that split's Gini gain, weight it by the fraction of the total training rows (N) that reached that split's node, sum across every such split in a tree, then average across all T trees in the forest. A feature no tree ever split on contributes zero to every term and scores exactly 0.

07
WORKED EXAMPLE

MDI, weighted by rows reached

Every split in this 3-stump forest is a root split, so every node has all N=8 rows -- the weighting term nnode/N is 1 for all three splits. That simplifies the sum to the raw gain for each tree's chosen feature: Tree 1 contributes 0.208333 to x2; Tree 2 contributes 0.208333 to x3; Tree 3 contributes 0.281250 to x1. This is the one place a deeper forest (splits below the root) would actually make the weighting term matter -- flagged here rather than silently assumed away.

09
WORKED EXAMPLE

MDI, averaged over the forest's 3 trees

MDI(x1) = 0.281250 / 3 = 0.093750 MDI(x2) = 0.208333 / 3 = 0.069444 MDI(x3) = 0.208333 / 3 = 0.069444

Dividing by 3 (the number of trees, not the number of splits that used each feature) is the standard scikit-learn convention -- a feature used in zero trees scores exactly 0 under this averaging, not undefined.

DIAGNOSIS

The MDI ranking

MDI ranks x1 > x2 = x3.x1 leads at 0.093750; x2 and x3 tie exactly at 0.069444 each, because Trees 1 and 2's forced splits happened to land on identical gain values. That tie is a fact about this dataset's specific numbers -- not a property of MDI, and not something to expect on a different toy example with different split gains.
11
ECOSYSTEM

feature_importances_, verbatim from scikit-learn

Every fitted RandomForestClassifier and RandomForestRegressor exposes a feature_importances_ attribute -- an array the same length as the number of input features, each entry the MDI computed exactly as above, averaged across every tree in the actual fitted forest (not 3 trees -- n_estimators=100 by default, per Concept 04's own Section 16 constructor table). The documentation states plainly that these values sum to 1.0 and are computed as "the normalized total reduction of the criterion brought by that feature."

12
DIAGNOSIS

MDI's own documented caveats, restated and not resolved here

Concept 04 Section 18 already quoted scikit-learn's own two caveats verbatim: MDI is computed from training-set statistics only, so it doesn't necessarily reflect held-out usefulness; and it's biased toward high-cardinality features. Neither caveat gets a fresh number in this concept -- this toy dataset's three features (x1: 5 distinct values, x2: 8 distinct values, x3: 2 distinct values) actually vary enough in cardinality that a real cardinality-bias demonstration would be possible, but building one is out of this concept's scope and is named forward rather than faked with an invented number.

13
MATHEMATICS

Permutation importance, defined precisely

PermImportance(feature f) = mean over R repeats of [ baseline_accuracy − accuracy(forest, rows with f shuffled) ]

Fit the forest once. Compute its baseline accuracy on the training rows. Then, for feature f, shuffle that one column's values across all rows (breaking any real relationship between f and the outcome while leaving every other feature untouched), re-run the same fitted forest's predictions, and record the accuracy drop. Repeat R times with independent shuffles and average, because any single shuffle is one random draw and can over- or under-state the true effect.

14
WORKED EXAMPLE

The forest's baseline accuracy, unshuffled

Running the rebuilt 3-tree forest's majority vote on the original, unshuffled 8 rows reproduces Concept 04's own number exactly: 7/8 correct, baseline accuracy 0.875000, missing row H. This is the number every shuffle below gets compared against.

15
WORKED EXAMPLE

Shuffling one feature, by hand for one draw

Take x3's column -- [1,1,0,1,0,0,1,0] for rows A-H -- and shuffle it across the 8 rows using a documented mulberry32 PRNG continuing Concept 04's own seed (20260828, offset by +1000 so this concept's draws are distinct from Concept 04's already-consumed stream, not a fresh unseeded generator). Re-running the forest's vote with x3 scrambled and x1, x2 untouched changes which rows land on which side of Tree 2's x3 ≤ 0.5 split and Tree 3's tie-breaking, which can flip individual predictions. One shuffle is one data point; Section 16 runs 20 of them per feature and averages.

That's the concrete value permutation importance adds even when the top-line ranking agrees: finer resolution, grounded in the model's actual behavior rather than its training-time bookkeeping.

18
DIAGNOSIS

Why this agreement isn't guaranteed in general

Do not generalize "MDI and permutation importance agree" from this one forest.They agree on the top spot here because x1 genuinely drove the highest-gain split found anywhere in this forest, on either method's terms. On real datasets, a high-cardinality feature can score artificially high on MDI while scoring low on permutation importance, precisely because MDI's training-set-only bias (Section 12) doesn't apply to a method that actually re-scores the model. This concept's own agreement is a fact about this 8-row example, not evidence the two methods are interchangeable in general.

22
CORRECTION

One shuffle is not permutation importance

"I shuffled a feature once, the accuracy barely moved, so that feature doesn't matter."

One shuffle is one random draw and can land anywhere -- Section 15 shows exactly this: a single shuffle of x3 can flip individual row predictions in either direction depending on which rows happened to swap. Section 16's 20-shuffle average, not any one draw, is the actual importance estimate.

"MDI and permutation importance are just two names for the same computation."

They're computed from entirely different information -- MDI from the trees' own training-time impurity bookkeeping, permutation importance from re-scoring the fitted model on deliberately broken data. Section 17's table shows them producing different exact numbers even while agreeing on ranking.

23
CAREER PRACTICE

Interview questions

Conceptual: what does MDI credit to a feature, exactly?
The sample-weighted Gini (or other criterion) gain from every split, in every tree of the forest, that used that feature -- summed per tree, then averaged across all trees in the forest.
Mathematical: why does permutation importance require re-scoring rather than looking inside the trees?
Because it measures how much the model's actual predictive accuracy depends on a feature having real (non-shuffled) values -- a question about the fitted model's behavior on data, not about the training-time bookkeeping the trees themselves recorded.
Mathematical: name one documented failure mode of MDI that permutation importance avoids.
MDI is biased toward high-cardinality features and is computed purely from training-set statistics; permutation importance, by actually re-scoring the model, doesn't inherit the training-set-only limitation, though it has its own costs (compute, and correlated-feature effects not covered in this concept's scope).
System design: you have two candidate features with similar MDI scores. What would you check next before deciding which to keep?
Whether permutation importance agrees -- Section 17 and Section 18 show the two methods can and do diverge, especially when cardinality differs between the candidates, so a close MDI call is exactly when the second method earns its extra compute cost.
