Ten concepts named a dozen knobs.
Which ones actually moved the number?

Concepts 02, 03, 04, and 08 each introduced a hyperparameter as a side effect of explaining a mechanism -- max_depth while explaining pruning, n_estimators and max_features while explaining bagging and random forests, learning_rate while explaining gradient boosting. None of those concepts ranked the knobs against each other. This one does, on the same 8-row CFPB relief table, using nothing but numbers an actual tree-building script computed: max_depth clearing 1 is worth more than anything else tried here, min_samples_split can erase that entire gain, and learning_rate trades directly against n_estimators -- all confirmed, none of it a universal claim beyond this one small table.

01 · CONCEPT FIRST

A ranking, not a new mechanism

This concept introduces no new algorithm. It takes four hyperparameters this module already built -- max_depth (Concept 02), n_estimators and max_features (Concepts 03-04), learning_rate (Concept 08) -- and asks a question none of those concepts asked on its own: on the SAME dataset, which knob's movement changes the outcome the most?

First memory: Depth clearing 1 is worth more than anything else tried here. Turning min_samples_split too strict can undo that entire gain. Everything else is a smaller effect on this table.
02 · WHY IT EXISTS

Because "just tune it" isn't an answer

A real project has a grid search budget, not infinite compute. Knowing that max_depth tends to matter more than max_features on a given problem shape -- and that some knobs actively fight each other, like learning_rate against n_estimators -- changes where a limited search actually looks first.

03 · CONCRETE EXAMPLE

One jump, then a plateau

On the 8-row relief table, a depth-1 stump gets 7 of 8 rows right, no matter how min_samples_split is set. Moving to depth 2 alone jumps that to 8 of 8. Depth 3 and depth 4 add nothing further -- the table is already fully explained by depth 2. That's the single largest jump measured anywhere in this concept.

04 · TECHNICAL MECHANISM

Hold everything else fixed, move one knob

Each ranking claim below comes from holding every other setting fixed and sweeping exactly one knob across a small grid, then reading off train accuracy or SSE from an actual rebuilt tree or boosted ensemble -- never from intuition about what "should" happen.

05 · ARCHITECTURE / FLOW

Four knobs, four different jobs

max_depthhow expressive one tree is allowed to be
min_samples_splithow much evidence a split needs to happen at all
n_estimators / learning_ratehow many rounds, how big a step each round
max_featureshow correlated the ensemble's trees are with each other
06 · IMPORTANT DISTINCTIONS

"Moves accuracy" is not the same as "moves the model"

max_features is ranked last for THIS table specifically because it doesn't move train accuracy at all here (0.875 whether trees are decorrelated or not, per Concept 04) -- even though it moves something else real, the average pairwise correlation between trees, by a large margin (0.5367 down to 0.1667). A knob can matter for generalization or ensemble diversity without showing up in a single accuracy number.

07 · COMMON MISTAKES

"This ranking is universal"

"max_depth always matters more than max_features."

False as a general claim -- it's true on THIS 8-row table, where 3 features already separate the classes by depth 2. A wider, noisier dataset could easily reverse which knob matters more.

"A stricter min_samples_split can only help, since it prevents overfitting."

False here -- min_samples_split=6 caps accuracy at 7/8 on the TRAINING set itself, on a table this small. Regularization strength has a real cost, not just a benefit.

ORIENTATION

Concepts 01-08 built the mechanisms: splitting and impurity, pruning, bagging, random forests, feature importance, boosting's sequential idea, AdaBoost, gradient boosting. 02
RECAP

Where each knob was already named

max_depth appeared in Concept 02 as the lever that controls overfitting via pruning (cost-complexity alpha_eff values 0.1875 and 0.234375 there). n_estimators appeared in Concepts 03-04 as "how many bootstrap trees." max_features appeared in Concept 04 as the random-forest decorrelation lever (correlation 0.5367 → 0.1667). learning_rate appeared in Concept 08, fixed at 0.5 throughout that concept's own worked rounds.

03
SCOPE

What this concept deliberately does not do

This is not a general hyperparameter-tuning guide, and not a claim about any real-world dataset.Every ranking claim below is scoped to the same 8-row toy table this module has reused since Concept 03. A different dataset shape -- more rows, more noise, more features -- can and often will change which knob dominates. The value of this concept is the METHOD (hold everything fixed, move one knob, read off a real number), not a portable leaderboard.
04
METHOD

One-knob-at-a-time, everything else held fixed

Every comparison below rebuilds either a plain decision tree (exhaustive Gini split search, exact same code shape as Concept 01) or a gradient-boosted ensemble (exhaustive SSE-reduction stump search, exact same code shape as Concept 08), sweeping exactly one setting per comparison. No number in this concept is looked up from a library's default behavior without also being reproduced by hand-written search code.

08
DIAGNOSIS

Why depth 3 and depth 4 add nothing here

Once depth 2 reaches 8/8, every leaf already has Gini impurity 0 -- the recursion's own stopping rule ("stop once a leaf is pure," the same rule Concept 01 used) means no further split is even attempted. Depth 3 and 4 are not "wasted" in some abstract sense; on THIS table they are simply never reached, because there's nothing left to split.

10
DIAGNOSIS

Reading the grid: two knobs, two very different shapes

max_depth produces a step function: flat at 7 for depth 1, then flat at 8 (or 7, if split is strict) for depth 2 and beyond. min_samples_split produces a threshold effect: nothing changes until it crosses 6, at which point it caps the WHOLE row of the grid regardless of depth. Neither knob behaves like a smooth dial on this table -- both have a specific crossing point where the number actually moves.

14
DIAGNOSIS

The rate/rounds trade-off, named directly from these numbers

learning_rate and n_estimators are not two independent knobs -- they're one budget split two ways. A lower rate needs more rounds to reach the same place a higher rate reaches faster; on this table, lr=0.1 simply hadn't gotten there yet by round 3, while lr=0.5 and lr=1.0 both had. This is exactly why production libraries expose both, and why the trade-off is a genuinely different comparison from "which single number is bigger."

CORRECTION

Both numbers already carry Concept 04's own verification; this concept treats them as a reference point, not a fresh computation.
16
DIAGNOSIS

Why max_features ranks last, on THIS table specifically

Despite that large correlation drop, Concept 04's own train accuracy TIED at 0.875 across the single tree, the 3-tree bagged ensemble, and the feature-restricted random forest. On an 8-row table this separable, decorrelating the trees changes how much the ensemble members agree with each other, but not whether the ensemble gets the training rows right. A wider, noisier dataset is exactly where that gap would be expected to matter for held-out accuracy instead -- not demonstrated here, flagged as the reason not to over-read this ranking.

18
ECOSYSTEM

Real defaults, cited

Confirmed live against scikit-learn's own current documentation: DecisionTreeClassifier defaults max_depth=None (nodes expand until pure or min_samples_split is not met) and min_samples_split=2; GradientBoostingRegressor defaults learning_rate=0.1, n_estimators=100 (Concept 08's own citation); RandomForestClassifier defaults max_features='sqrt' for classifiers.

19
REALITY

GridSearchCV and RandomizedSearchCV, named not built

scikit-learn's own GridSearchCV exhaustively tries every combination of a supplied parameter grid, exactly the same shape as Section 09's 4x3 grid but cross-validated instead of read off a single training accuracy. RandomizedSearchCV samples the same kind of grid instead of enumerating it, useful once the grid is too large to exhaust. Neither tool was invoked here -- the grid above was built by hand-written search code specifically so every cell is independently checkable.

20
REALITY

A practical search order, grounded in Section 17's ranking

Given a limited tuning budget: widen max_depth (or the equivalent capacity knob) first and check whether it's under- or overfitting; only then adjust regularization strength (min_samples_split/min_samples_leaf, or cost-complexity alpha per Concept 02); for boosted models, treat learning_rate and n_estimators as one joint search, not two independent ones; leave max_features for a later pass focused on generalization rather than training fit. This order follows directly from Section 17's ranking -- it is not an independent industry rule cited from elsewhere.

REALITY

Caveats, restated on purpose

This ranking is one worked example on 8 rows and 3 features. It is not a claim that max_depth outranks max_features on every dataset, nor that learning_rate=1.0 is a safe default -- a rate that high on a noisier, larger dataset commonly overfits, a risk Concept 08 named and this concept does not re-demonstrate. Use the METHOD (isolate one knob, rerun, read the real number) on the actual dataset in front of you, not this concept's specific numbers.

24
CAREER PRACTICE

Interview questions, then references and checkpoint

Conceptual: given a limited tuning budget, which hyperparameter would you check first, and why?
Model capacity first (max_depth or the equivalent), since Section 09's grid shows it produces the single largest jump on this table; regularization strength and ensemble-diversity knobs come after, once capacity is confirmed adequate.
Conceptual: why treat learning_rate and n_estimators as one joint search rather than two separate ones?
Section 12-14's numbers show they trade against each other directly -- a lower rate reaches the same accuracy ceiling with more rounds, not a worse ceiling; tuning one without the other misses that relationship.
Conceptual: why might max_features matter on a real dataset even though it didn't move accuracy here?
It changed ensemble correlation substantially (Concept 04's own 0.5367→0.1667); on a noisier or larger dataset, that reduced correlation is exactly what improves held-out generalization, even when it doesn't change training accuracy on a small, separable toy table.
Mathematical: why does min_samples_split=6 cap accuracy at 7/8 regardless of max_depth?
Because the stopping rule checks BEFORE attempting a split whether a node has enough samples; once a node falls under that threshold, no depth budget remaining can force a split that the min_samples_split rule already disallowed.
