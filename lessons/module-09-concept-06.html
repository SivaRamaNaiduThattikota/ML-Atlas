01 · CONCEPT FIRST

Forward propagation is four equations, run in a fixed order, on one real input

Given a layer's weights (W) and bias (b), forward propagation is: multiply the input by W, add b, get a pre-activation (z); squash z through an activation function to get that layer's actual output (a); feed a into the next layer's own W and b; repeat. For Concept 03's [3,4,1] shape, that is exactly two rounds of this: z1=W1x+b1, a1=activation(z1), z2=W2a1+b2, a2=activation(z2).

First memory: forward propagation is not a new algorithm -- it's Concept 02's single-unit z=w.x+b, run twice in a row, once per layer, with an activation squashed in between.
02 · DEFINITION

Forward propagation, formally: an affine transform then an activation, layer after layer, nothing else in it

Forward propagation, formally, is the deterministic function a network computes: at each layer, an affine transform z = Wx + b followed by an elementwise activation a = f(z), applied layer after layer from input to output, with no error term, no gradient, and no parameter update anywhere in it. That's the precise, library-level meaning of the term (PyTorch's own nn.Sequential(Linear, activation, Linear, activation) is exactly this pattern) -- not just "running numbers through the network" in the loose sense b01 used.

03 · PREREQUISITE CHECK

Three things from earlier in the module this concept assumes are already solid

Before this concept makes sense, three specific things from earlier in the module need to already be solid: Concept 02's single-unit arithmetic z=w·x+b (this concept is that, run twice); Concept 03's [3,4,1] shapes -- W1 4×3, b1 length 4, W2 1×4, b2 length 1 -- taken as given, not re-derived; and Concept 04's sigmoid/tanh/ReLU closed forms plus its dead-gradient tally, needed to follow why ReLU gets picked below. If any of those three isn't fresh, that's the gap to close first, not this concept.

04 · WHY IT EXISTS

Concept 03 built the shape. Nobody has run a single real number through it yet

Concept 03 was explicit: "no training anywhere in this lesson" -- it counted parameters (21 of them) and confirmed shapes, but W1, b1, W2 and b2 never held an actual value. This concept is the first place that changes. Before any training (Concept 07 onward) can make sense, a real forward pass -- real weights, real input, real numbers all the way through -- has to exist to train against.

06 · TECHNICAL MECHANISM

z1 → a1 → z2 → a2, in that order, and nothing else

z1 = W1·x + b1 (4 numbers, one per hidden unit). a1 = activation(z1), applied elementwise (still 4 numbers). z2 = W2·a1 + b2 (1 number, the output layer's pre-activation). a2 = activation(z2) (1 number, the network's final output for this row). Every one of the four steps is exactly the single-perceptron arithmetic from Concept 02, just repeated at a different layer with a different-shaped W.

07 · ARCHITECTURE / FLOW

3 inputs, 4 hidden units, 1 output -- with real numbers riding through it

Input x(3, 15, 0)
Hidden z1 → a13 units live, 1 dead (unit 3)
Output z2 → a220.269262

Annotating that middle node directly: hidden unit 3's own weight row is (−0.247334, −0.482561, −0.921218) -- all three negative, and every CFPB feature is non-negative, so unit 3's raw dot product is negative on every one of the 8 rows without exception. Run all 8 rows through the same net (Section 14 of the advanced lesson): unit 3's z1 is negative on all 8, so its ReLU output is exactly 0 on all 8. That is a dead unit found by nothing more than an unlucky random draw -- not training, not a vanishing gradient yet, just this concept's own seed=906 numbers.

08 · IMPORTANT DISTINCTIONS

"a1, computed" is not "the gradient flowing back through a1"

Everything in this concept moves forward: input to z1 to a1 to z2 to a2. Nothing here computes how a mistake at a2 would flow backward to adjust W1, b1, W2 or b2 -- that's the chain rule, and it's explicitly Concept 07's job. This concept's own "dead unit" (Step 07) is about a forward-pass output landing at exactly 0, which is a necessary condition for a dead gradient later, not the gradient computation itself.

09 · COMMON MISTAKES

"A dead unit today means training can never fix it"

"Unit 3 is dead now, so it's dead forever."

Not quite what this concept shows. Unit 3 is dead at these specific drawn weights, on these specific 8 rows, before a single training step. Whether it can recover depends on how training actually updates W1's third row -- a backprop question, deferred to Concept 07.

"Choosing ReLU means every unit stays alive."

False, and this concept's own Section 07 is the counterexample: ReLU avoids sigmoid/tanh's two-sided saturation, but it has its own one-sided dead zone (Concept 04's own finding), and unit 3 fell straight into it.

06
MATHEMATICS

The forward-pass equations, defined

z1 = W1·x + b1
a1 = f(z1)
z2 = W2·a1 + b2
a2 = f(z2)

x is the 3-feature input row. z1 and a1 are each length-4 vectors, one entry per hidden unit. z2 and a2 are each length-1, the single output unit. f is whichever activation function is applied -- Section 07 picks it. This is exactly PyTorch's own nn.Sequential(nn.Linear(3,4), activation, nn.Linear(4,1), activation) pattern, run by hand instead of by a framework.

07
THE CHOICE

Choosing the activation to trace: ReLU, justified by Concept 04's own numbers

Concept 04 already found that sigmoid and tanh go dead (|derivative|<0.01) on every one of Concept 02's 8 CFPB-scale pre-activations, and stay alive only on small XOR-scale ones; ReLU alone stayed alive regardless of scale, on the positive side. This concept's own drawn weights, run on real CFPB features (case_age_days alone ranges 10-60), produce pre-activations in the same tens-to-hundreds range Concept 04 already flagged as sigmoid/tanh's dead zone (checked directly in Section 15). Tracing sigmoid step by step here would mostly produce values already indistinguishable from exact 0 or 1 -- true, but not illustrative of the actual arithmetic. ReLU is traced instead, precisely because Concept 04's own tally says it's the one still doing something at this scale.

14
FINDING

Hidden unit 3 is dead on every one of the 8 rows

Unit 3's own weight row is the reason, not any one input row. W1's third row is (−0.247334, −0.482561, −0.921218) -- all three weights negative. Every CFPB feature (x1, x2, x3) is non-negative by construction (counts and a 0/1 flag), so unit 3's raw dot product W1[3]·x can never be positive for this table, regardless of which row is fed in; adding b1[3]=0.153214 isn't enough to push any of the 8 rows' sums above zero (Section 13's own column: −5.8409 down to −29.2951, all negative). Unit 3 is dead -- ReLU output exactly 0, derivative exactly 0 by Concept 04's convention -- on 8 of 8 rows, discovered purely from this concept's own random draw, before a single training step exists.

16
CORRECTION

Unstandardized features let one unit's raw dot product dwarf the others

This is a feature-scale artifact, not a property of the weights alone. x2 (case_age_days) ranges 10-60 across the 8 rows, roughly 10-60× larger than x1 (1-5) or x3 (0-1). Drawn at the same std=1 as every other weight, unit 2's W1[2,2]=1.706991 gets multiplied by that much larger x2, producing a raw dot product an order of magnitude past the other three units' on every single row (Section 13's own z1 column: unit 2 is always the largest, by a wide margin). This is exactly the kind of feature/weight-scale interaction that a real init scheme has to account for -- Concept 05's job, unbuilt. Nothing here corrects it; it's flagged, not fixed.
17
SCOPE HEDGE

What this concept did not compute: any gradient

Every number in this concept -- z1, a1, z2, a2, for one row or all eight -- is a forward-pass value. None of it says how a mistake at a2 would flow backward to change W1, b1, W2 or b2. Unit 3 being "dead" here (Section 14) is a necessary but not sufficient condition for a dead gradient during real training; the actual chain-rule computation that would confirm or contradict that is Concept 07's entire job, not attempted here.

18
NAMED FORWARD

What's deferred: a real init scheme, and the chain rule

Named forward, not built here: a principled weight-initialization scheme -- Concept 05 has since shipped exactly that, Xavier and He, on standardized inputs, without retroactively replacing this concept's own ad hoc seed=906 draw; and backpropagation -- the chain-rule computation that would tell W1's dead third row whether and how it can recover during training (Concept 07). Nothing about either mechanism is covered here.

Conceptual: why trace ReLU here instead of sigmoid or tanh?
Concept 04 already found sigmoid and tanh dead (|derivative|<0.01) on every CFPB-scale pre-activation it tried, alive only at XOR's small scale; ReLU stayed alive at any positive z regardless of scale. This concept's own drawn weights, run on real CFPB features, land in that same dead zone for sigmoid/tanh (confirmed directly in Section 15, 2 of 4 units already saturated) -- ReLU is the one still doing real, illustrative arithmetic at this scale.
Practical: hidden unit 3 is dead on all 8 training rows before training starts. What would you check first?
Whether that's a property of the weights (unit 3's own row is all-negative against non-negative CFPB features, Section 14) or of the data (features aren't standardized, so some units dominate others, Section 16) -- both are true here simultaneously. Then whether a real init scheme (Concept 05, not yet built) or feature standardization would change it, and whether the unit could ever recover once real training starts, which needs backprop (Concept 07) to actually answer.
