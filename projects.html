PROJECT 01 · PRODUCTION LEVEL

CFPB Consumer Complaint Copilot

Two models serving one complaint-ops copilot: a tabular relief-risk scorer and a narrative auto-triage classifier, both carried through EDA, leakage-free features, tuning, calibration, explainability, and monitored deployment.

P1IN PROGRESS
CFPB API→Weekly pull→EDA→Leakage-free features→Model 1 / Model 2→Tuning + calibration→SHAP + MLflow→FastAPI + Docker→Drift monitoring
BUSINESS SCENARIO

A bank or fintech CX analyst needs to triage complaints before they escalate.

Every complaint needs two answers fast: which product/team should own it (triage) and how likely it is to end in monetary or non-monetary relief (risk). Both answers have to be trustworthy enough to act on, not just plausible.

WHY THIS IS PRODUCTION LEVEL
  • Real, live government data pulled weekly, not a frozen CSV
  • Genuine class imbalance that varies by product (4.3%–35.6% relief rate)
  • Two model types (gradient boosting + fine-tuned transformer) with different failure modes
  • Temporal train/test splitting, not a random shuffle
  • Calibrated probabilities and SHAP explanations, not just a raw score
  • MLflow experiment tracking and a real model registry
  • FastAPI serving behind Docker, deployed to Azure Container Apps
  • Evidently-based drift monitoring on every weekly pull
CORE MODEL FLOWS
  1. Pull the latest week's complaints from the live CFPB API.
  2. Re-run EDA checks — imbalance, missingness, drift red flags.
  3. Engineer leakage-free features (OOF target encoding, temporal features).
  4. Score relief risk (Model 1) and predict product/triage (Model 2).
  5. Attach calibrated probabilities and a SHAP explanation to every score.
  6. Log the run to MLflow; promote to the registry only if metrics hold.
REQUIRED EVIDENCE
  • EDA report with the real imbalance and missingness numbers
  • A no-leakage feature-engineering writeup
  • PR-AUC / recall-leaning threshold justification
  • SHAP explanations for a sample of real predictions
  • MLflow experiment history and registry stages
  • A drift report from at least one real weekly pull cycle

Programming foundation

Purpose and why it was chosen

The CFPB Consumer Complaint Copilot is a real, already-running system on the live CFPB Consumer Complaint Database — not a synthetic or frozen dataset. It was chosen specifically because it forces the full discipline this course teaches: real class imbalance that varies by product, genuine missing-narrative and redaction issues, a temporal structure that breaks naive cross-validation, and two very different model types (tabular gradient boosting and a fine-tuned text classifier) that both have to reach production.

Most beginner ML projects stop at train_test_split → model.fit() → accuracy_score(). That proves you can call a library, not that you can ship something a business could actually rely on. This project's real EDA already surfaced exactly the kind of problem that separates the two: an overall 22.3% relief rate that hides a 4.3%–35.6% range by product, meaning a single global threshold would be badly miscalibrated for at least one product.

The production problems you must solve

Each item is a separate engineering problem with its own tests and evidence:

Changing dataWeekly incremental pulls, per-product cursors, and re-running EDA checks on every new batch.
Imbalance that variesA 22.3% overall relief rate that ranges 4.3%–35.6% by product — no single threshold or resampling ratio is correct everywhere.
Leakage riskHigh-cardinality fields (Company: 636 values) and temporal ordering both create realistic ways to accidentally leak the answer into training.
Two model types, one systemA tabular gradient-boosted model and a fine-tuned DistilBERT text classifier must both reach the same reliability bar.
Trustworthy scoresCalibrated probabilities and SHAP explanations, not a raw model score, for a regulated-adjacent domain.
Production operationMLflow tracking, a real registry, FastAPI serving, Docker, Azure deployment, and Evidently-based drift monitoring on every weekly pull.
What completing this project proves

Completion means you can present evidence — not merely claim — that you can:

  • Turn a real, messy government API into a leakage-free modeling dataset.
  • Diagnose and correctly handle class imbalance that varies by segment, not just overall.
  • Build both a gradient-boosted tabular model and a fine-tuned text classifier to production quality.
  • Tune hyperparameters systematically (Optuna) without overfitting the validation set.
  • Calibrate probabilities and explain individual predictions with SHAP.
  • Track experiments and manage model versions with MLflow's registry.
  • Serve a model behind a real API, containerized and cloud-deployed.
  • Detect and respond to data drift on a live, recurring data pull.

This is the primary employment-ready project because it demonstrates the full discipline of shipping ML, not just training a model that scores well once.

Build sequence and definition of done
  1. Data foundation: weekly pull, EDA, and a documented imbalance/missingness profile — already done.
  2. Leakage-free features: encoding, scaling, and temporal features with an explicit leakage audit.
  3. Model 1 baseline → tuned: a logistic baseline, then Optuna-tuned gradient boosting against PR-AUC.
  4. Model 2 baseline → escalated: a TF-IDF classifier, then a fine-tuned DistilBERT if it measurably helps.
  5. Trust layer: calibration, thresholding, and SHAP explanations for both models.
  6. Lifecycle wiring: MLflow tracking/registry, then FastAPI + Docker + Azure serving.
  7. Closed loop: Evidently drift monitoring on a real weekly pull, with a documented retraining trigger.

Done means evidence, not features: another person can reproduce the metrics, inspect a SHAP explanation, and see a real drift report from an actual weekly pull.

The CFPB Complaint Copilot follows standard practice for imbalanced tabular ML (scale-sensitive boosting, PR-AUC-first evaluation), calibration and explainability (Platt/isotonic scaling, SHAP), and MLOps (experiment tracking, model registries, statistical drift detection). It is a real system already in progress, not a hypothetical brief.
